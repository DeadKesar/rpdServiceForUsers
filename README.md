# RpdFos — АС создания РПД и ФОС (прототип)

Прототип к магистерской ВКР: автоматизированная система формирования рабочих программ дисциплин (РПД)
и фондов оценочных средств (ФОС).

Стек: .NET 10, ASP.NET Core (Carter, вертикальные срезы), EF Core + PostgreSQL 17,
ASP.NET Core Identity + OpenIddict (OpenID Connect, authorization code + PKCE), Blazor WebAssembly.

## Структура

```
src/RpdFos.Core                      прикладное ядро: сущности, AppDbContext, миграции, перехватчик версий
src/RpdFos.Api                       хост: модули Carter, сервер авторизации OpenIddict, страница входа,
                                     OpenAPI + Swagger UI; раздаёт веб-клиент
src/RpdFos.Web                       веб-клиент Blazor WebAssembly — отдельно не запускается
src/DisciplineDataExtractor          библиотека разбора исходных файлов: учебный план, список и матрица
                                     компетенций, должности сотрудников
tests/RpdFos.Api.Tests               тесты API и правил домена
tests/DisciplineDataExtractor.Tests  тесты разбора на реальных файлах (tests/fixtures)
docs/                                проект, задания этапов, runbook-и, журнал разработки
```

## Запуск

Нужны .NET SDK 10 (версия — в `global.json`) и Docker.

```
dotnet dev-certs https --trust          # один раз: OpenIddict принимает только HTTPS
docker compose up -d db converter mail  # база, конвертер DOCX -> PDF и почтовая ловушка
dotnet user-secrets set "Seed:AdminEmail" "admin@rpdfos.local" --project src/RpdFos.Api
dotnet user-secrets set "Seed:AdminPassword" '<пароль>' --project src/RpdFos.Api
dotnet run --project src/RpdFos.Api
```

Порядок: сначала сервисы `docker compose` (база нужна для миграций при старте, конвертер — для PDF, ловушка — для почты), затем хост.
Без конвертера всё работает, кроме PDF: задача формирования PDF завершится с причиной «Конвертер PDF недоступен».
Без ловушки уведомления работают в интерфейсе, а письма о них ждут: отправка повторяется каждую минуту.

Сервисы `docker-compose.yml`:

| Сервис | Образ | Назначение |
| --- | --- | --- |
| `db` | `postgres:17-alpine` | База данных, порт 5432 |
| `converter` | `gotenberg/gotenberg:8.38.1` (MIT, ~2,5 ГБ) | DOCX → PDF: LibreOffice в режиме headless за HTTP API, порт 3000. Times New Roman в образе нет — подставляется метрически совместимый Liberation Serif |
| `mail` | `axllent/mailpit:v1.33.1` (MIT, ~14 МБ) | Почтовая ловушка для разработки: SMTP на порту 1025, письма видны на http://localhost:8025. Настоящий сервер — этап 8 |

- https://localhost:5081 — веб-клиент, https://localhost:5081/swagger — Swagger UI, `/health` — проверка.
- Профиль `https` из `Properties/launchSettings.json` включает окружение Development: при старте
  применяются миграции и создаются роли, клиент OIDC `rpdfos-web` и первый администратор.
- Импорт исходных данных — страница «Импорт данных» (методист и администратор): комплект из трёх файлов —
  учебный план (.xlsx), список и матрица компетенций (.docx); разбор идёт в фоне. Строки матрицы без дисциплины
  плана привязываются к дисциплинам на этой же странице.
- Справочник сотрудников — страница «Справочник сотрудников» (администратор): записи, места подписантов, смена
  человека на должности; там же загрузка файла должностей (.xlsx) — необязательная начальная загрузка, разбор в фоне.
  Председатель УМК задаётся по направлению подготовки, один действующий на направление: лист согласования
  РПД и ФОС печатает председателя направления плана дисциплины, в том числе по действующим шаблонам.
  Председателя направления нет — место печатается пустым, отчёт формирования предупреждает. Запись
  председателя без направления документов не подписывает и помечена в списке; загрузка файла должностей
  переопределяет категорию записей из файла и снимает с них направление.
- Пароль администратора хранится в user-secrets и в репозиторий не попадает. Требования: не короче
  8 символов, заглавная и строчная буквы, цифра и спецсимвол. Остальные учётные записи создаёт
  администратор на странице «Пользователи»; там же — новый временный пароль и отключение учётной записи.
  Ролей у учётной записи может быть несколько (заведующий кафедрой — преподаватель и утверждающий): они
  отмечаются флажками при создании и по кнопке «Изменить роли» и действуют со следующего входа.

## Проверка и согласование

| Роль | Страницы меню, кроме общих «Главной» и «Шаблонов» |
| --- | --- |
| Преподаватель | «Мои документы» |
| Методист | «Мои документы», «Проверка», «Импорт данных» |
| Утверждающий | «Согласование» |
| Администратор | «Мои документы», «Импорт данных», «Пользователи», «Справочник сотрудников» |

У учётной записи с несколькими ролями меню объединяет страницы её ролей.

- Автор отправляет РПД на проверку — документ попадает в очередь методиста на странице «Проверка». Методист
  возвращает его автору с замечаниями или принимает (с подтверждением).
- Приём запускает параллельное электронное согласование по электронным местам листа согласования шаблона;
  согласующих находят те же правила, что при печати. В шаблоне нет электронных мест — принятый документ
  сразу «Согласован».
- Согласующий для места не найден — документ остаётся «Принят». Методист или администратор назначает его
  вручную в панели «Согласование» на странице документа (поиск по справочнику), затем методист нажимает
  «Запустить согласование». Так же заменяют отсутствующего, пока его отметка ждёт. Назначение действует
  в пределах текущего круга; печатный лист согласования по-прежнему строится по правилам шаблона.
- Утверждающий на странице «Согласование» видит документы, которые ждут его отметки, и отмеченные им.
  На странице документа — «Согласовать» (с подтверждением) или «Вернуть на проверку» с обязательным
  комментарием. Заведующий кафедрой согласует и собственный РПД.
- Все отметки поставлены — документ «Согласован»: правки закрыты, печать — автору, методисту и согласующим.
  Возврат заканчивает круг: документ снова у методиста, в очереди «Проверка» он помечен «с согласования»;
  следующий приём начинает новый круг.
- Уведомления — колокольчик в шапке: число непрочитанных, последние уведомления со ссылкой на документ,
  «Прочитано» и «Прочитать все». Автору — взят на проверку, возвращён на доработку (в том числе после
  исправления данных плана), принят, согласован; методистам — отправлен на проверку, возвращён
  с согласования, согласован; утверждающему — документ ждёт его отметки (при старте круга и при назначении).
  Лента обновляется опросом сервера раз в минуту и при переходах между страницами.
- Почта — раздел `Mail` конфигурации (сервер, порт, отправитель, адрес системы для ссылок). Письмо с темой, текстом
  и ссылкой на документ уходит на email учётной записи фоновой задачей в пределах минуты после события, если оно
  требует действия получателя: возвращён на доработку (в том числе после исправления данных плана), ждёт согласования,
  возвращён с согласования. По остальным событиям письма нет; прочитанное в интерфейсе и старше суток (`Mail:MaxAgeHours`)
  не отправляется. Сбой отправки событие не отменяет — попытка повторяется каждую минуту. В разработке письма
  принимает ловушка `mail`, читать их — http://localhost:8025.

## Сборка и тесты

```
dotnet build                            # без ошибок и предупреждений
dotnet test                             # нужен запущенный Docker
```

Интеграционные тесты (`tests/RpdFos.Api.Tests/Integration`) поднимают чистую PostgreSQL 17 в контейнере
(Testcontainers) и применяют к ней миграции; база разработки не используется. Аутентификация в них —
тестовая схема (роль из заголовка `X-Test-Role`), политики доступа — рабочие.

## Миграции

Миграции живут в ядре (`-p`), конфигурацию берут из хоста (`-s`):

```
dotnet tool install --global dotnet-ef
dotnet ef migrations add <Имя> -p src/RpdFos.Core -s src/RpdFos.Api
```

В Development миграции применяются при запуске. Схема меняется только новыми миграциями,
существующие не правятся.

## Конфигурация

| Ключ | Назначение |
| --- | --- |
| `ConnectionStrings:Default` | Строка подключения. Для разработки — в `appsettings.json`, на сервере — переменная окружения `ConnectionStrings__Default` |
| `Database:AutoMigrate` | Миграции и начальные данные при запуске (включено в Development) |
| `Auth:PublicUrl` | Публичный адрес хоста. По нему при запуске сверяются адреса возврата клиента OIDC |
| `Seed:AdminEmail`, `Seed:AdminPassword` | Первый администратор — только в user-secrets |
| `Jobs:Enabled` | Сервер фоновых задач Hangfire и панель `/hangfire` (выключено в окружении Testing) |
| `Jobs:QueuePollSeconds` | Как часто сервер задач опрашивает очередь (по умолчанию 15 с) |
| `Jobs:GenerationWorkers` | Сколько документов формируется одновременно (по умолчанию 2) |
| `Converter:Url`, `Converter:TimeoutSeconds` | Адрес конвертера DOCX → PDF (по умолчанию `http://localhost:3000`) и предел ожидания (120 с) |
| `Generation:StoragePath`, `Generation:RetentionDays` | Каталог сформированных файлов (по умолчанию `storage/generated` у хоста) и срок их хранения (30 дней) |
| `ValidationRules:LiteratureMaxAgeYears` | Основная литература старше этого числа лет — предупреждение при проверке (10) |

Фоновые задачи — Hangfire, хранилище в той же базе, схема `hangfire`: импорт исходных файлов (очередь `parsing`),
формирование DOCX и PDF и ежедневная очистка файлов с истёкшим сроком хранения (очередь `generation`).
Панель задач — https://localhost:5081/hangfire, только для администратора: вход — через страницу входа системы.
