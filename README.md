# RpdFos — АС создания РПД и ФОС (прототип)

Прототип к магистерской ВКР: автоматизированная система формирования рабочих программ дисциплин (РПД)
и фондов оценочных средств (ФОС).

Стек: .NET 10, ASP.NET Core (Carter, вертикальные срезы), EF Core + PostgreSQL 17,
ASP.NET Core Identity + OpenIddict (OpenID Connect, authorization code + PKCE), Blazor WebAssembly.

## Структура

```
src/RpdFos.Core                      прикладное ядро: сущности, AppDbContext, миграции, перехватчик версий
src/RpdFos.Api                       хост: модули Carter, сервер авторизации OpenIddict, страница входа,
                                     OpenAPI + Swagger UI; раздаёт веб-клиент
src/RpdFos.Web                       веб-клиент Blazor WebAssembly — отдельно не запускается
src/DisciplineDataExtractor          библиотека разбора исходных файлов: учебный план, список и матрица
                                     компетенций, должности сотрудников
tools/RpdFos.Corpus                  прогон по корпусу настоящих РПД и ФОС вуза (консольное приложение, корпус в
                                     репозиторий не входит; режим --fos разбирает настоящие ФОС)
tests/RpdFos.Api.Tests               тесты API и правил домена
tests/DisciplineDataExtractor.Tests  тесты разбора на реальных файлах (tests/fixtures)
tests/RpdFos.Corpus.Tests            тесты разбора настоящих ФОС и файла оформления ФОС
docs/                                проект, задания этапов, runbook-и, журнал разработки
```

## Запуск

Нужны .NET SDK 10 (версия — в `global.json`) и Docker.

```
dotnet dev-certs https --trust          # один раз: OpenIddict принимает только HTTPS
docker compose up -d db converter mail  # база, конвертер DOCX -> PDF и почтовая ловушка
dotnet user-secrets set "Seed:AdminEmail" "admin@rpdfos.local" --project src/RpdFos.Api
dotnet user-secrets set "Seed:AdminPassword" '<пароль>' --project src/RpdFos.Api
dotnet run --project src/RpdFos.Api
```

Порядок: сначала сервисы `docker compose` (база нужна для миграций при старте, конвертер — для PDF, ловушка — для почты), затем хост.
Без конвертера всё работает, кроме PDF: задача формирования PDF завершится с причиной «Конвертер PDF недоступен».
Без ловушки уведомления работают в интерфейсе, а письма о них ждут: отправка повторяется каждую минуту.

Сервисы `docker-compose.yml`:

| Сервис | Образ | Назначение |
| --- | --- | --- |
| `db` | `postgres:17-alpine` | База данных, порт 5432 |
| `converter` | `gotenberg/gotenberg:8.38.1` (MIT, ~2,5 ГБ) | DOCX → PDF: LibreOffice в режиме headless за HTTP API, порт 3000. Times New Roman в образе нет — подставляется метрически совместимый Liberation Serif |
| `mail` | `axllent/mailpit:v1.33.1` (MIT, ~14 МБ) | Почтовая ловушка для разработки: SMTP на порту 1025, письма видны на http://localhost:8025. Настоящий сервер — этап 8 |

- https://localhost:5081 — веб-клиент, https://localhost:5081/swagger — Swagger UI, `/health` — проверка.
- Профиль `https` из `Properties/launchSettings.json` включает окружение Development: при старте
  применяются миграции и создаются роли, клиент OIDC `rpdfos-web` и первый администратор.
- Импорт исходных данных — страница «Импорт данных» (методист и администратор): комплект из трёх файлов —
  учебный план (.xlsx), список и матрица компетенций (.docx); разбор идёт в фоне. Строки матрицы без дисциплины
  плана привязываются к дисциплинам на этой же странице.
- Справочник сотрудников — страница «Справочник сотрудников» (администратор): записи, места подписантов, смена
  человека на должности; там же загрузка файла должностей (.xlsx) — необязательная начальная загрузка, разбор в фоне.
  Председатель УМК задаётся по направлению подготовки, один действующий на направление: лист согласования
  РПД и ФОС печатает председателя направления плана дисциплины, в том числе по действующим шаблонам.
  Председателя направления нет — место печатается пустым, отчёт формирования предупреждает. Запись
  председателя без направления документов не подписывает и помечена в списке; загрузка файла должностей
  переопределяет категорию записей из файла и снимает с них направление.
- Пароль администратора хранится в user-secrets и в репозиторий не попадает. Требования: не короче
  8 символов, заглавная и строчная буквы, цифра и спецсимвол. Остальные учётные записи создаёт
  администратор на странице «Пользователи»; там же — новый временный пароль и отключение учётной записи.
  Ролей у учётной записи может быть несколько (заведующий кафедрой — преподаватель и утверждающий): они
  отмечаются флажками при создании и по кнопке «Изменить роли» и действуют со следующего входа.

## Проверка и согласование

| Роль | Страницы меню, кроме общих «Главной» и «Шаблонов» |
| --- | --- |
| Преподаватель | «Мои документы» |
| Методист | «Мои документы», «Проверка», «Закрепление дисциплин», «Импорт данных» |
| Утверждающий | «Согласование» |
| Администратор | «Мои документы», «Закрепление дисциплин», «Импорт данных», «Пользователи», «Справочник сотрудников» |

У учётной записи с несколькими ролями меню объединяет страницы её ролей.

- Автор отправляет РПД на проверку — документ попадает в очередь методиста на странице «Проверка». Методист
  возвращает его автору с замечаниями или принимает (с подтверждением).
- Приём запускает параллельное электронное согласование по электронным местам листа согласования шаблона;
  согласующих находят те же правила, что при печати. В шаблоне нет электронных мест — принятый документ
  сразу «Согласован».
- Согласующий для места не найден — документ остаётся «Принят». Методист или администратор назначает его
  вручную в панели «Согласование» на странице документа (поиск по справочнику), затем методист нажимает
  «Запустить согласование». Так же заменяют отсутствующего, пока его отметка ждёт. Назначение действует
  в пределах текущего круга; печатный лист согласования по-прежнему строится по правилам шаблона.
- Утверждающий на странице «Согласование» видит документы, которые ждут его отметки, и отмеченные им.
  На странице документа — «Согласовать» (с подтверждением) или «Вернуть на проверку» с обязательным
  комментарием. Заведующий кафедрой согласует и собственный РПД.
- Замечания к полям (в разделе «Замечания к полям» документа) оставляют методист — на проверке — и согласующий — пока
  его отметка ждёт; после отметки решение принято и замечание уже не оставить. Со своими неснятыми замечаниями
  «Согласовать» недоступно: их нужно снять или вернуть документ. В уведомлении о возврате с согласования методисту
  приходит число замечаний; методист снимает замечания согласующих (любое из них) или возвращает документ автору,
  а принять документ с неснятыми замечаниями нельзя.
- Все отметки поставлены — документ «Согласован»: правки закрыты, печать — автору, методисту и согласующим.
  Возврат заканчивает круг: документ снова у методиста, в очереди «Проверка» он помечен «с согласования»;
  следующий приём начинает новый круг.
- Уведомления — колокольчик в шапке: число непрочитанных, последние уведомления со ссылкой на документ,
  «Прочитано» и «Прочитать все». Автору — взят на проверку, возвращён на доработку (в том числе после
  исправления данных плана), принят, согласование начато вручную, согласован, возвращён на исправление,
  статус сменён принудительно, документ отправил в архив не он; методистам — отправлен на проверку, возвращён
  с согласования, согласован, возвращён на исправление, статус сменён принудительно; утверждающему — документ ждёт
  его отметки (при старте круга и при назначении); согласующим последнего круга — согласованный документ возвращён
  на исправление; прежнему согласующему — его место занял другой; запросившему формирование — печатная форма
  готова или не сформирована; прежнему автору — документ передан другому, новому — вам передан документ;
  сотруднику — дисциплина закреплена за ним или закрепление снято. Совершивший действие уведомления о нём не
  получает. Ссылку на документ получает тот, кому он открыт: уведомление о недоступном документе приходит без
  ссылки. Лента обновляется опросом сервера раз в минуту и при переходах между страницами.
- Почта — раздел `Mail` конфигурации (сервер, порт, отправитель, адрес системы для ссылок, час дайджеста). Письмо с темой,
  текстом и ссылкой на документ уходит на email учётной записи фоновой задачей в пределах минуты после события. По
  умолчанию — только если событие требует действия получателя: возвращён на доработку (в том числе после исправления
  данных плана), ждёт согласования, возвращён с согласования, срок доработки истекает или вышел, статус сменён
  принудительно, документ передан новому автору; по остальным событиям письма нет. Как слать, получатель
  решает в профиле (ниже). Прочитанное в интерфейсе и просроченное (больше `Mail:MaxAgeHours` часов после срока письма)
  не отправляется. Сбой отправки событие не отменяет — попытка повторяется каждую минуту. В разработке письма
  принимает ловушка `mail`, читать их — http://localhost:8025.
- Профиль и настройки — ссылка с именем пользователя в шапке (`/profile`, S-02). ФИО, должность, подразделение, email и
  роли — только для чтения. Таблица настроек уведомлений: по каждому событию «в интерфейсе» (выключенное событие не
  попадает в колокольчик и счётчик) и «почта» — сразу, раз в день или выключено. Пока настройки не менялись, действуют
  умолчания; в базе хранятся только отличия от них. «Раз в день» — одно письмо-дайджест со всеми неотправленными
  уведомлениями получателя в час `Mail:DigestHour` по времени сервера (8; часовой пояс — системный, на сервере его
  задаёт его настройка). Каналы независимы: письмо приходит и тогда, когда событие скрыто в интерфейсе. У пользователя
  без записи справочника сотрудников настроек нет.
- Напоминания о сроке доработки — раздел `Reminders` конфигурации (`ReworkDays` — 14, `WarnDaysBefore` — 3,
  `Enabled`). Задача `rework-reminders` идёт раз в сутки, в полночь по UTC (панель `/hangfire`, там же её можно
  запустить сразу). Срок отсчитывается от последнего перехода документа в «На доработке». За три дня до срока автору
  приходит «Срок доработки истекает», по истечении срока заведующему кафедрой дисциплины (то же правило, что в листе
  согласования) и методистам — «На доработке больше 14 дней». Каждое напоминание — один раз за одно пребывание на
  доработке: возврат документа начинает отсчёт заново. Если срок уже вышел, а предупреждения не было, автору оно не
  приходит. Ссылку на документ получает тот, кто его откроет: заведующий, не участвующий в документе (нет строки
  согласования), получает уведомление без ссылки. Заведующему без действующей учётной записи уведомление не
  создаётся — остаются методисты. События — в таблице настроек профиля, почта — «сразу».

## Жизненный цикл документа после согласования

- **Возврат на исправление.** Методист возвращает согласованный документ кнопкой «Вернуть на исправление»: причина
  обязательна, подтверждение без отмены. Документ снова «На проверке», согласие сбрасывается; методист принимает его
  (начинается новый круг согласования) или возвращает автору. Причина видна методисту и администратору в плашке
  «Возвращён на исправление», хранится в истории статусов и аудите. Уведомление — автору, согласующим последнего
  круга и остальным методистам, письма по умолчанию нет.
- **Принудительная смена статуса** (администратор, кнопка «Сменить статус», FR-ADM-04) — только назад: из любого
  статуса, кроме удалённого, в «Сохранённый черновик», «На доработке» или «На проверке». Комментарий обязателен,
  согласие сбрасывается, идущее согласование прерывается: отметить документ вне «На согласовании» нельзя, а строки
  круга сбросит следующий приём. Событие — в аудите, уведомление и письмо — автору и методистам.
- **Архив — только явно.** «В архив» (с подтверждением) нажимает автор, методист или администратор; переход — из
  «Согласован» в «Архивный». Ни по времени, ни при согласовании преемника документ в архив не уходит. Архивный документ
  открыт только для чтения, его печатают автор, методист и согласующий, дисциплину он не занимает. Из архива документ
  возвращает только администратор принудительной сменой статуса.
- **Один незавершённый документ** на дисциплину и линию редакций шаблона. Незавершённый — не «Согласован», не
  «Архивный» и не «Удалённый»: создание документа, возврат на исправление и смена статуса, которые это нарушили бы,
  отклоняются (409) со ссылкой на мешающий документ. Согласованный документ занимает дисциплину: новый по ней
  создаётся только на его основе (ниже).
- **Передача документа** (методист и администратор, кнопка «Передать документ»; FR-DOC-15): новый автор — преподаватель
  с действующей учётной записью, его находят поиском по фамилии; причина обязательна. Меняется только автор — статус
  и содержимое прежние; передача записана в аудит. Прежний автор документ больше не видит (если он не закреплён
  за дисциплиной, не методист, не администратор и не согласующий); новому автору приходит уведомление и письмо.

## Закрепление дисциплин и доступ к документам

- Страница «Закрепление дисциплин» (методист и администратор): выбирается учебный план; таблица — строки, по которым
  создаётся документ (без модулей, групп элективов, практик и ГИА), с кафедрой, закреплёнными сотрудниками и документами
  (автор, статус). Методист отмечает дисциплины (фильтр по кафедре и флажок «все» в шапке таблицы), ищет сотрудника
  по фамилии и нажимает «Закрепить»; «Снять» — у каждого закрепления, с подтверждением. Закрепить можно сотрудника
  с действующей учётной записью преподавателя. Закрепление — на дисциплину версии плана, одно для РПД и ФОС; на новую
  версию плана оно не переходит. Закрепление и снятие записываются в аудит, сотрудник получает уведомление (без письма).
- Закреплённый преподаватель видит документы своих дисциплин — раздел «Документы моих дисциплин» на странице «Мои
  документы» — вместе с замечаниями, но только для чтения: из действий у него «Создать на основе». Править документ
  может один автор (FR-DOC-14); другой человек продолжает его после передачи документа.
- У дисциплины с закреплениями документы создают только закреплённые преподаватели: остальным на экране создания
  вместо кнопки «Создают закреплённые преподаватели», а запрос получает отказ 403. Методист и администратор создают
  документы по любой дисциплине — за кафедру. Закрепления нет — создаёт любой преподаватель. Передача документа
  закрепляет нового автора, если у дисциплины есть закрепления.

## Создать на основе и признак «устарел»

- Кнопка «Создать на основе» — у согласованного и архивного документа (автор, методист, администратор, закреплённый
  преподаватель) и на экране «Создание документа», блок «Основа». Основа — документ любого статуса, кроме удалённого,
  доступный пользователю: свой, закреплённой дисциплины, а методисту и администратору — любой.
- Цель — та же дисциплина (шаблон её плана) или дисциплина другого плана; другая дисциплина того же плана не
  принимается. Новый документ собирается заново: поля из учебного плана, справочников и матрицы компетенций берутся
  у цели, поверх кладётся то, что вводил автор основы. Постоянные пункты вуза берутся из нового шаблона, если автор
  не менял их в основе. Не переносятся разделы, скрытые для цели, составители (в новом документе один — автор),
  протокол кафедры и индикаторы компетенций, которых нет в матрице цели. Список неперенесённого — в плашке «Создан
  на основе» при каждом открытии документа и в аудите.
- Преемник согласован — основа той же дисциплины получает значок «устарел» (версия и время изменения основы не
  меняются), а автор сам решает, отправить ли её «В архив». Основа другой дисциплины не устаревает. Значок
  «устарел» ставят две причины: новая редакция шаблона и согласованный преемник.

## ФОС: создание, редактор, сквозная проверка, печать, согласование

Фонд оценочных средств — второй тип документа рядом с РПД: свой шаблон (тип «ФОС», схема `fos.schema.json`, круг
подписей `fos.signatures.json`), те же статусы, права, замечания и согласование.

- **Шаблон ФОС** создаётся по плану так же, как шаблон РПД: загрузка файла оформления
  (`tests/fixtures/FOS_TemplateBookmarks_v2.docx` — 52 закладки; файл разработан по приложениям Положения о ФОС),
  проверка сопоставления закладок, публикация. Шаблон хранит снимок схемы и сопоставления на момент создания:
  после правок схемы или файла оформления шаблон загружают заново.
- **Создание по РПД.** «Создать документ» → тип «ФОС»: список дисциплин с РПД; из РПД ведёт кнопка «Создать ФОС».
  ФОС создаётся по РПД в любом статусе, кроме удалённой и архивной; создаёт автор РПД, у дисциплины с закреплениями —
  только закреплённые преподаватели, методист и администратор — за кафедру. Один незавершённый ФОС на дисциплину и
  линию шаблона. Автор ФОС, не являющийся автором РПД, читает её только для чтения.
- **Снимок РПД.** Наследуемое из РПД (компетенции с индикаторами, разделы тематического плана, виды занятий и
  аттестации по семестрам) хранится в ФОС снимком — раздел «Связь с РПД», только для чтения. РПД изменилась — в ФОС
  плашка «РПД изменилась»; «Обновить из РПД» (автор в работе, методист на проверке) заменяет снимок и называет
  добавленные и исчезнувшие индикаторы и разделы. Строки паспорта и оценочных средств с исчезнувшими индикаторами
  не удаляются, а подсвечиваются красным.
- **Редактор** — разделы: титул и лист согласования (как у РПД), «Паспорт ФОС» (таблица разделов и таблица
  индикаторов; ссылки на задания собираются выбором группы и номеров), «Текущий контроль», «Оценочные средства»
  (кнопка «Предложить» подбирает типовые средства по формам контроля, видам занятий и аттестации РПД; файл
  соответствий `fos.means-suggestions.json`), «Банк заданий» (группы вопросов, заданий и тестов; нумерация в группе,
  «Перенумеровать» переписывает ссылки паспорта), «Экзаменационные билеты», «Критерии формирования оценок».
  Обязательны титул, паспорт и лист согласования; банк, билеты, средства, текущий контроль и шкала — нет, пустой раздел печатается формулировкой-заглушкой
  или типовыми критериями. В форматированном тексте заданий и вопросов билетов — таблицы (вставка, строки,
  столбцы, объединение ячеек) и рисунки: PNG и JPEG до 2 МБ, до 100 на документ, метаданные снимаются при загрузке;
  формулы — линейной записью или рисунком. Рисунок читает тот, кто читает документ; при «Создать на основе» файл
  не копируется, а связывается.
- **Сквозная проверка РПД ↔ ФОС** сравнивает ФОС с РПД как она есть сейчас. Блокирует отправку одно правило —
  связанная РПД должна быть «На проверке» или дальше (до этого ФОС не отправить). Остальные — предупреждения, они
  не мешают ни отправке, ни приёму: у каждого индикатора РПД есть оценочное средство и задание; ссылки паспорта
  указывают на существующие задания; виды аттестации и шкала согласуются; формы текущего контроля представлены; число
  вопросов, тестов и билетов не меньше порогов Положения о ФОС, у средств заполнены критерии. Автору, методисту,
  администратору и закреплённому преподавателю над разделами показана сводка «расхождений N» с переходом к полю; в окне приёма — то же число;
  в РПД у каждого ФОС по ней — «расхождений: N». РПД от ФОС не зависит.
- **Печать.** DOCX по файлу оформления v2 и PDF тем же конвертером; имя — `ФОС_<дисциплина>_<ГГГГ-ГГГГ>`. Паспорт
  (две таблицы, числа заданий по банку), текущий контроль, средства, банк заданий частями по виду аттестации — каждая
  часть со своей шапкой и подписью составителя, шкала, билеты — по странице на билет с шапкой и подписью заведующего
  кафедрой.
- **Проверка и согласование** — тем же механизмом, что у РПД: очередь «Проверка» (колонка «Тип»), замечания к полям,
  возврат и приём, параллельное электронное согласование по местам листа (по Положению о ФОС — председатель УМК
  направления подготовки и начальник учебно-методического управления; заведующий кафедрой остаётся в печатном листе
  согласования и электронной отметки не ставит), замечания согласующих, уведомления и письма. Председатель УМК
  находится по направлению учебного плана дисциплины, как в РПД; не найден — документ «Принят» до назначения
  методистом. Круг задаёт лист согласования шаблона — его снимок: шаблоны ФОС, созданные до этого круга, работают по
  прежнему (заведующий кафедрой и начальник УМУ). Отправить ФОС можно, когда РПД на проверке или дальше.
- **«Создать на основе» и «устарел».** ФОС создаётся на основе прежнего для новой РПД дисциплины: банк, билеты,
  средства, текущий контроль, шкала и паспорт переносятся, снимок берётся из РПД цели; ссылки на индикаторы,
  которых в ней нет, и строки паспорта с ними не переносятся и названы в списке. Согласован преемник РПД — прежняя РПД и
  её согласованные ФОС получают «устарел». РПД с незавершённым ФОС в архив не переводится (409 с названием ФОС);
  иначе РПД и её согласованные ФОС уходят в архив вместе.

## Сборка и тесты

```
dotnet build                            # без ошибок и предупреждений
dotnet test                             # нужен запущенный Docker
```

Интеграционные тесты (`tests/RpdFos.Api.Tests/Integration`) поднимают чистую PostgreSQL 17 в контейнере
(Testcontainers) и применяют к ней миграции; база разработки не используется. Аутентификация в них —
тестовая схема (роль из заголовка `X-Test-Role`), политики доступа — рабочие.

Замер скорости печати (`tests/RpdFos.Api.Tests/Bench`, этап 8) в обычный прогон не входит. Нужен конвертер из
`docker-compose.yml` (`docker compose up -d converter`):

```
$env:RPDFOS_BENCH = "1"; $env:BENCH_ROUNDS = "3"; dotnet test tests/RpdFos.Api.Tests --filter "Category=Bench"
```

Переменные: `BENCH_POLL`, `BENCH_WORKERS` (настройки `Jobs:*` на время замера), `BENCH_CONVERTER` (адрес конвертера),
`BENCH_LABEL`, `BENCH_IDLE_SECONDS` (окно измерения нагрузки опроса). Таблицы — в `out/bench/`.

## Миграции

Миграции живут в ядре (`-p`), конфигурацию берут из хоста (`-s`):

```
dotnet tool install --global dotnet-ef
dotnet ef migrations add <Имя> -p src/RpdFos.Core -s src/RpdFos.Api
```

В Development миграции применяются при запуске. Схема меняется только новыми миграциями,
существующие не правятся.

## Конфигурация

| Ключ | Назначение |
| --- | --- |
| `ConnectionStrings:Default` | Строка подключения. Для разработки — в `appsettings.json`, на сервере — переменная окружения `ConnectionStrings__Default` |
| `Database:AutoMigrate` | Миграции и начальные данные при запуске (включено в Development) |
| `Auth:PublicUrl` | Публичный адрес хоста. По нему при запуске сверяются адреса возврата клиента OIDC |
| `Seed:AdminEmail`, `Seed:AdminPassword` | Первый администратор — только в user-secrets |
| `Jobs:Enabled` | Сервер фоновых задач Hangfire и панель `/hangfire` (выключено в окружении Testing) |
| `Jobs:QueuePollSeconds` | Как часто сервер задач сам заглядывает в очередь (по умолчанию 5 с, от 0,5 до 300). Печать от него не зависит: задачу ставит тот же процесс, исполнителя будят сразу; опрос — страховка для задач, вернувшихся в очередь без сигнала |
| `Jobs:GenerationWorkers` | Сколько документов формируется одновременно (по умолчанию 2, от 1 до 20). Конвертер обрабатывает файлы по очереди, больше двух исполнителей время не сокращают |
| `Converter:Url`, `Converter:TimeoutSeconds` | Адрес конвертера DOCX → PDF (по умолчанию `http://localhost:3000`) и предел ожидания (120 с) |
| `Generation:StoragePath`, `Generation:RetentionDays` | Каталог сформированных файлов (по умолчанию `storage/generated` у хоста) и срок их хранения (30 дней) |
| `Mail:Enabled` | Отправка писем о событиях и её расписание (включена). Уведомления в интерфейсе от этого не зависят |
| `Mail:Host`, `Mail:Port` | Почтовый сервер: по умолчанию ловушка `mail` из docker-compose, `localhost:1025`. Логина и пароля нет — настоящий сервер появится в этапе 8 |
| `Mail:From`, `Mail:PublicUrl` | Отправитель письма и адрес системы для ссылок в письмах (в разработке `https://localhost:5081`; пусто — письма без ссылок) |
| `Mail:MaxAgeHours`, `Mail:DigestHour` | Сколько часов после срока письма оно ещё отправляется (24) и час дайджеста по времени сервера (8) |
| `Reminders:Enabled` | Ежедневная задача напоминаний о сроке доработки (включена) |
| `Reminders:ReworkDays`, `Reminders:WarnDaysBefore` | Срок доработки в сутках (14; от 2) и за сколько суток предупредить автора (3; от 1 и раньше срока). Значения проверяются при старте |
| `ValidationRules:LiteratureMaxAgeYears` | Основная литература старше этого числа лет — предупреждение при проверке (10) |
| `ValidationRules:LiteratureMainMin` | В основной литературе записей меньше — предупреждение при проверке (3, Положение о рабочих программах, п. 4.1) |

Фоновые задачи — Hangfire, хранилище в той же базе, схема `hangfire`: импорт исходных файлов (очередь `parsing`),
формирование DOCX и PDF, ежедневная очистка файлов с истёкшим сроком хранения и ежедневные напоминания о сроке
доработки `rework-reminders` (очередь `generation`), отправка писем `notification-mail` раз в минуту (очередь `mail`).
Панель задач — https://localhost:5081/hangfire, только для администратора: вход — через страницу входа системы.
