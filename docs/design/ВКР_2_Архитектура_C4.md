# Раздел 2.x. Архитектура системы (модель C4)

*Черновик для главы 2 ВКР (задача Т-104). Архитектура описана по модели C4 на трёх уровнях: контекст, контейнеры, компоненты. Исходники диаграмм даны в нотации C4-PlantUML для рендеринга.*

## 2.x.1. Подход: модель C4

Архитектура описывается по модели **C4** (Context — Containers — Components — Code) Саймона Брауна. Модель даёт несколько уровней детализации, каждый для своей аудитории: контекст — для понимания места системы в окружении, контейнеры — для технического обзора, компоненты — для внутренней структуры. Четвёртый уровень (Code, диаграммы классов) в работе не приводится: на этом уровне структура определяется кодом и устаревает быстрее, чем документация.

Используются три уровня:
- **Уровень 1 (Контекст)** — система как единое целое, её пользователи и внешние системы.
- **Уровень 2 (Контейнеры)** — отдельно запускаемые единицы (приложения, сервисы, хранилища) и технологии.
- **Уровень 3 (Компоненты)** — внутреннее устройство ключевого контейнера (API).

> Исходники ниже используют библиотеку **C4-PlantUML**. Для рендеринга нужен доступ к её stdlib — либо через интернет (директива `!include` с URL), либо через локальную копию (тогда заменить URL на путь к файлу). Если C4-PlantUML недоступна, диаграммы можно перерисовать обычными средствами PlantUML или в draw.io.

## 2.x.2. Уровень 1 — Контекст

Система обслуживает четыре роли пользователей: **Преподаватель** (создаёт и редактирует РПД/ФОС), **Методист** (готовит шаблоны из исходных данных, проверяет документы), **Утверждающий** (согласует документы) и **Администратор** (управляет пользователями и структурой типов документов).

Единственная внешняя система, с которой система интегрирована на этапе MVP, — **почтовый сервер** для уведомлений (SMTP). Интеграции с информационными системами вуза (1С:Университет, Планы ММИС, кадровая система, системы Рособрнадзора) отнесены к перспективе: они требуют согласования со службами вуза и выходят за рамки прототипа, разворачиваемого на одной кафедре и в методическом отделе. На этапе MVP исходные данные поступают в систему через загрузку файлов, а не через прямую интеграцию.

```plantuml
@startuml C4_Context
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Context.puml
title Контекст: АС создания РПД и ФОС

Person(teacher, "Преподаватель", "Создаёт и редактирует РПД/ФОС")
Person(methodist, "Методист", "Готовит шаблоны, проверяет документы")
Person(approver, "Утверждающий", "Согласует документы")
Person(admin, "Администратор", "Управляет пользователями и структурой типов")

System(sys, "АС создания РПД и ФОС", "Создание, проверка, согласование и генерация РПД и ФОС")

System_Ext(mail, "Почтовый сервер", "Уведомления по SMTP")
System_Ext(univ, "Внешние системы вуза", "1С:Университет, Планы (ММИС), кадровая система, Рособрнадзор — перспектива")

Rel(teacher, sys, "Создаёт документы, отправляет на проверку")
Rel(methodist, sys, "Готовит шаблоны, проверяет, принимает")
Rel(approver, sys, "Согласует")
Rel(admin, sys, "Администрирует")
Rel(sys, mail, "Отправляет уведомления", "SMTP")
Rel(sys, univ, "Импорт/экспорт данных (перспектива)")
@enduml
```

## 2.x.3. Уровень 2 — Контейнеры

Система состоит из семи контейнеров:

| Контейнер | Технология | Назначение |
|---|---|---|
| Веб-приложение | Blazor WebAssembly | Интерфейс пользователя, исполняется в браузере |
| API | ASP.NET Core, Carter (vertical slices) | Бизнес-логика, REST API |
| Фоновый обработчик | Hangfire | Разбор исходных файлов, генерация документов, рассылка уведомлений, периодические задачи |
| Сервер аутентификации | Duende IdentityServer | Аутентификация по OIDC, хранение учётных данных |
| Конвертер документов | LibreOffice в режиме headless | Преобразование сформированного DOCX в PDF |
| База данных | PostgreSQL | Данные системы, очередь фоновых задач, исходные файлы и шаблоны оформления |
| Хранилище файлов | Том Docker | Сгенерированные документы с ограниченным сроком хранения |

Взаимодействие. Веб-приложение проходит аутентификацию на сервере аутентификации по протоколу OIDC и обращается к API с полученным токеном доступа. API и фоновый обработчик — два хоста одного прикладного ядра: общие библиотеки содержат доменную модель, доступ к данным, движки схем и валидации, конвейеры импорта и генерации. Поэтому фоновая задача исполняет тот же код бизнес-правил, что и API, не обращаясь к нему по сети. Долгие операции API не выполняет синхронно, а ставит задачу в очередь Hangfire, которая хранится в той же PostgreSQL; обработчик забирает задачу оттуда. В прототипе сервер фоновых задач запускается в процессе API (один контейнер); вынесение его в отдельный хост для масштабирования (NFR-SCA-03) не требует изменения кода.

PDF не верстается отдельно: обработчик формирует DOCX по шаблону оформления и передаёт его конвертеру. Так у каждого документа одна вёрстка, заданная шаблоном оформления, и PDF совпадает с DOCX по построению (FR-GEN-02, точный режим предпросмотра FR-DOC-10). Файлы, которые нельзя восстановить (исходные данные, шаблоны оформления), хранятся в базе данных и попадают в её резервные копии; на томе хранятся только сгенерированные документы, которые можно сформировать заново.

```plantuml
@startuml C4_Container
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Container.puml
title Контейнеры: АС создания РПД и ФОС

Person(user, "Пользователь", "Преподаватель / Методист / Утверждающий / Администратор")

System_Boundary(sys, "АС создания РПД и ФОС") {
  Container(web, "Веб-приложение", "Blazor WebAssembly", "Интерфейс пользователя в браузере")
  Container(api, "API", "ASP.NET Core, Carter", "Бизнес-логика, REST API")
  Container(worker, "Фоновый обработчик", "Hangfire", "Разбор файлов, генерация, уведомления; в прототипе — в процессе API")
  Container(idp, "Сервер аутентификации", "Duende IdentityServer", "OIDC, учётные данные")
  Container(conv, "Конвертер документов", "LibreOffice (headless)", "DOCX → PDF")
  ContainerDb(db, "База данных", "PostgreSQL", "Данные, очередь задач, исходные файлы и шаблоны оформления")
  Container(files, "Хранилище файлов", "Том Docker", "Сгенерированные документы")
}

System_Ext(mail, "Почтовый сервер", "SMTP")

Rel(user, web, "Работает с системой", "HTTPS")
Rel(web, idp, "Аутентификация", "OIDC")
Rel(web, api, "Запросы", "JSON/HTTPS, токен доступа")
Rel(api, idp, "Проверка токена")
Rel(api, db, "Чтение/запись, постановка задач", "EF Core, Hangfire")
Rel(worker, db, "Получение задач, чтение/запись", "Hangfire, EF Core")
Rel(worker, conv, "DOCX → PDF", "HTTP")
Rel(worker, files, "Запись сгенерированных документов")
Rel(api, files, "Выдача файлов для скачивания")
Rel(worker, mail, "Отправляет уведомления", "SMTP")
@enduml
```

## 2.x.4. Уровень 3 — Компоненты

API организован по принципу **вертикальных срезов** (Carter): каждый модуль отвечает за свою бизнес-область целиком — от эндпоинта до доступа к данным. Это снижает связанность между областями и упрощает добавление новых. Общая логика вынесена в прикладное ядро — набор библиотек, которые используют и API, и фоновый обработчик.

**Модули (вертикальные срезы):** Документы (жизненный цикл документа), Шаблоны (шаблоны, загрузка исходных данных, публикация), Проверка и согласование (проверка, приём, параллельное электронное согласование), Генерация (постановка задач и выдача файлов), Уведомления (лента уведомлений в интерфейсе, настройки каналов), Справочники, Отчёты, Пользователи и профиль, Администрирование.

**Прикладное ядро:**
- **Движок схем документов** интерпретирует JSON Schema и x-расширения: предзаполняет поля из источников (`x-source`), определяет состав разделов по данным учебного плана (`x-visible-if`), обязательность и доступность полей в зависимости от статуса (`x-required-for-status`, `x-readonly-after`). Это центральный компонент унифицированной модели методических документов.
- **Движок валидации** проверяет документ по JSON Schema и именованным правилам, в том числе кросс-документным (точка расширения: правила валидации).
- **Резолвер подписантов** формирует лист согласования по декларативным правилам шаблона (точка расширения: резолверы).
- **Конвейер импорта** вызывает парсер и переносит результат разбора в справочники.
- **Конвейер генерации** заполняет шаблон оформления DOCX по закладкам, строит таблицы, подставляет формулировки отключённых разделов и передаёт DOCX конвертеру для получения PDF (точка расширения: генераторы).
- **Форматированный текст**: санитизация по белому списку разрешённых элементов (NFR-SEC-10), преобразование разрешённой разметки в OpenXML при генерации, извлечение простого текста для полнотекстового поиска и сравнения версий.
- **Доступ к данным и файлы**: DbContext EF Core; файлы — за единым интерфейсом хранилища.

**Сквозные механизмы** работают для всех модулей без участия их кода: запись журнала аудита и увеличение номера версии при каждом сохранении (перехватчик сохранения EF Core), авторизация (ролевые политики и ограничение выборок по владельцу), единая обработка ошибок (стандартизованный ответ; конфликт версий — код 409), структурированное логирование.

**Внешние библиотеки:** парсер `DisciplineDataExtractor`, Open XML SDK.

На диаграмме связи модулей с компонентом доступа к данным опущены для читаемости: его используют все модули.


## 2.x.5. Развёртывание

Прототип разворачивается на одном сервере вуза средствами Docker Compose, без передачи данных во внешние облачные сервисы (NFR-SEC-09). Обратный прокси завершает HTTPS (NFR-SEC-01), раздаёт статические файлы веб-приложения и направляет запросы к API и серверу аутентификации. Данные базы и сгенерированные файлы хранятся в именованных томах. Ежедневное резервное копирование базы (NFR-REL-05) охватывает и исходные файлы с шаблонами оформления, поскольку они хранятся в базе.

```plantuml
@startuml C4_Deployment
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Deployment.puml
title Развёртывание прототипа

Deployment_Node(pc, "Рабочее место пользователя", "Браузер") {
  Container(web, "Веб-приложение", "Blazor WebAssembly", "")
}

Deployment_Node(srv, "Сервер вуза", "Linux, Docker Compose") {
  Deployment_Node(proxyNode, "Контейнер прокси", "nginx") {
    Container(rp, "Обратный прокси", "nginx", "TLS, маршрутизация, статические файлы веб-приложения")
  }
  Deployment_Node(apiNode, "Контейнер API", "ASP.NET Core") {
    Container(api, "API и сервер фоновых задач", "Carter, Hangfire", "")
  }
  Deployment_Node(idpNode, "Контейнер аутентификации", "ASP.NET Core") {
    Container(idp, "Сервер аутентификации", "Duende IdentityServer", "")
  }
  Deployment_Node(convNode, "Контейнер конвертера", "LibreOffice headless") {
    Container(conv, "Конвертер документов", "DOCX → PDF", "")
  }
  Deployment_Node(dbNode, "Контейнер БД", "PostgreSQL") {
    ContainerDb(db, "База данных", "PostgreSQL", "Том данных; ежедневный pg_dump")
  }
}

Rel(web, rp, "HTTPS")
Rel(rp, api, "/api", "HTTP")
Rel(rp, idp, "/identity", "HTTP")
Rel(api, db, "EF Core, Hangfire")
Rel(api, conv, "HTTP")
@enduml
```

## 2.x.6. Ключевые архитектурные решения

| Решение | Отвергнутая альтернатива | Обоснование |
|---|---|---|
| PDF получается конвертацией сформированного DOCX | Отдельная вёрстка PDF в коде | У документа одна вёрстка — шаблон оформления; PDF совпадает с DOCX; новый тип документа не требует кода вёрстки |
| Общее прикладное ядро для API и фонового обработчика | Обработчик обращается к API по сети или дублирует логику | Бизнес-правила существуют в одном экземпляре; обработчик выносится в отдельный хост без изменения кода |
| Учётные данные хранятся только на сервере аутентификации | Пароли в таблице пользователей системы | Один источник правды об учётных данных; справочные записи без права входа остаются в общем справочнике |
| Невосстановимые файлы — в базе данных, сгенерированные — на томе | Все файлы на файловой системе | Резервное копирование одной процедурой; файлы доступны всем процессам |
| Форматированный текст — санитизированное подмножество HTML | Собственный структурный формат | Готовые компоненты редактора выдают HTML; белый список ограничивает разметку тем, что переносится в DOCX |
| Уведомления в интерфейсе — периодический опрос сервера | Push-доставка (SignalR) | Достаточно для событий документооборота; push — перспектива |
| Задачи разбора — в отдельной очереди с одним исполнителем | Параллельный разбор | Библиотека-парсер хранит состояние в статических полях; до её доработки параллельный разбор небезопасен |

## 2.x.7. Точки расширения

Расширяемость системы (NFR-SUP-10, кандидат в научную новизну) обеспечивается четырьмя точками расширения, заложенными в архитектуру:

1. **Новый тип документа.** Центральная таблица `documents` хранит содержимое в `payload JSONB` и не зависит от типа, а конвейер генерации работает с любым шаблоном оформления. Добавление нового типа (например, программы практики) требует: значения в перечне типов, JSON Schema структуры (ведёт Администратор, FR-ADM-08), DOCX-шаблона оформления с закладками (FR-TPL-13) и при необходимости — правил валидации и источников предзаполнения. Изменения схемы БД, API и кода генерации не требуются. Это и есть унифицированная модель методических документов.

2. **Правила валидации.** Правила регистрируются по имени: в JSON Schema поле помечается `x-validation-rule`, движок валидации сопоставляет его с зарегистрированным классом-правилом. Новая проверка — это новый класс, движок не меняется.

3. **Резолверы подписантов.** Реализованы паттерном «цепочка ответственности». Каждый способ определить подписанта (`context.author`, `discipline.department.head`, `lookup.role:X` и др.) — отдельное звено цепи. Новый способ добавляется звеном, не затрагивая остальные. Один шаблон работает для всех кафедр, а смена заведующего — это строка в справочнике, а не правка шаблонов.

4. **Генераторы выходных форматов.** DOCX формируется обобщённым конвейером по шаблону оформления, PDF — конвертацией DOCX. Новый формат вывода (например, HTML для размещения на сайте вуза) подключается новым генератором за единым интерфейсом, не затрагивая вызывающий код.

В аналогах, рассмотренных в главе 1, подобные механизмы расширения не описаны: типы документов, правила и состав подписантов в них, как правило, жёстко зашиты.

## 2.x.8. Связь с другими разделами

- **Контейнеры и технологии** обоснованы в главе 3: Blazor, Carter, PostgreSQL + EF Core, Duende IdentityServer, Hangfire, Open XML SDK; для конвертации DOCX в PDF — LibreOffice.
- **Модули** соответствуют контекстам структуры данных (раздел 2.4) и группам ресурсов программного интерфейса: модуль «Документы» — контекст Documents — ресурс `/api/documents` и т. д.

- **Сквозные механизмы** реализуют принципы раздела 2.6: оптимистичную блокировку (номер версии увеличивается перехватчиком сохранения) и управление через смену статусов (переходы фиксируются в журнале аудита).
- **Точки расширения** — материал для обоснования научной новизны во введении и для выводов по главе 2.
