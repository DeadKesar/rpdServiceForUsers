# Раздел 2.x. Проектирование структуры данных

*Финальный черновик для главы 2 ВКР. Все ключевые решения по модели данных, обоснование и полная спецификация сущностей.*

## 2.x.1. Подход к проектированию: гибридная модель

### Проблема выбора

При проектировании структуры данных для системы, которая должна поддерживать разные типы документов (РПД, ФОС на этапе MVP; в перспективе — аннотации дисциплин, программы практик, аккредитационные документы), возникает фундаментальный выбор архитектуры хранения. Рассмотрены три подхода:

**Подход 1 — полностью нормализованный.** Для каждого типа документа создаётся отдельная таблица (`rpd_contents`, `fos_contents`) со всеми необходимыми полями. Преимущество: строгая схема, проверки целостности на уровне СУБД. Недостаток: добавление нового типа документа требует миграции БД и изменения кода во всех слоях системы, что противоречит требованию расширяемости (FR-TPL-10, NFR-SUP-10).

**Подход 2 — полностью денормализованный (JSONB).** Единая таблица `documents` со всем содержимым в поле `payload JSONB`. Преимущество: максимальная гибкость, добавление нового типа не требует миграций. Недостаток: невозможность выполнять SQL-запросы к структуре документа (например, «найти все РПД, у которых сумма часов в тематическом плане не совпадает с учебным планом»); вся валидация переносится в код приложения и не может быть защищена на уровне БД.

**Подход 3 — гибридный (выбранный).** Объединяет преимущества двух первых. Данные, которые: (а) используются для кросс-документной валидации, (б) требуются для поиска и фильтрации, (в) связаны внешними ключами с другими сущностями, — хранятся в нормализованных таблицах. Свободное содержимое документа (формулировки целей, описания разделов, темы лекций), специфичное для типа документа, — хранится в `payload JSONB` с валидацией по JSON Schema.

### Обоснование гибридного подхода

Выбор гибридной модели обусловлен следующими соображениями:

1. **Соответствие требованию расширяемости.** Добавление нового типа документа (например, программы практики) требует только: (а) добавления нового значения в перечень `document_type`, (б) написания JSON Schema для валидации, (в) реализации генератора и парсера для нового типа. Изменения структуры БД не требуются.

2. **Сквозная валидация РПД и ФОС.** Часы (`document_hours`) и привязки к компетенциям (`document_competence_links`) вынесены в отдельные таблицы с внешними ключами. Это позволяет формулировать требование FR-VAL-04 («каждая компетенция в РПД имеет оценочные средства в ФОС») как SQL-запрос, а не как императивный код на клиенте.

3. **Эффективный поиск.** Требование FR-SEA-01 (полнотекстовый поиск за ≤1 секунды при 10 000 документов) реализуется комбинацией: индекс по нормализованным полям (название дисциплины, автор) + GIN-индекс по `tsvector` над `payload` для полнотекстового поиска.

4. **Опора на возможности PostgreSQL.** JSONB в PostgreSQL — это не «сырой» JSON, а бинарный формат с поддержкой GIN-индексов, операторов `@>`, `?`, `#>>` и возможностью доступа к отдельным полям через `->`. Валидация структуры `payload` выполняется на уровне приложения через JSON Schema, привязанные к типам документов.

### Принципы именования и типов

- Все таблицы — в `snake_case` множественного числа (`documents`, `competence_indicators`).
- Первичные ключи — `UUID v4` (колонка `id`). UUID выбран вместо `bigserial` для безопасности API (непоследовательные идентификаторы не выдают размер БД) и возможности генерировать ID на клиенте до сохранения (полезно для автосохранения черновиков).
- Временные метки — `timestamptz` (с часовым поясом, всегда в UTC в БД).
- Удаление — мягкое (`deleted_at timestamptz NULL`) для документов и шаблонов; жёсткое — для строго подчинённых сущностей (комментарии, часы, история статусов).
- Все внешние ключи — `ON DELETE RESTRICT` по умолчанию; `ON DELETE CASCADE` только для строго подчинённых сущностей.

## 2.x.2. Предметные области (контексты) схемы

Схема логически разделена на четыре контекста, соответствующих модулям приложения (Carter Vertical Slices):

| Контекст | Таблицы | Ответственность |
|---|---|---|
| **Identity** | `users`, `roles`, `user_roles`, `login_history`, `notification_preferences` | Пользователи, роли, аутентификация, настройки |
| **Reference** | `institutes`, `departments`, `study_directions`, `study_profiles`, `fgos`, `competences`, `competence_indicators`, `curriculum_plans`, `disciplines`, `discipline_semester_details`, `competence_matrix` | Справочные данные: оргструктура, ФГОС, компетенции, учебные планы, дисциплины |
| **Documents** | `document_templates`, `documents`, `document_versions`, `document_comments`, `document_status_history`, `document_hours`, `document_competence_links`, `document_signatures`, `saved_filters` | Шаблоны, документы, их жизненный цикл и содержимое |
| **Infrastructure** | `uploaded_files`, `generation_tasks`, `generated_files`, `audit_log`, `parser_runs` | Файлы, фоновые задачи, аудит, импорт |

## 2.x.3. Спецификация сущностей

### Контекст Identity

#### `users` — пользователи системы и справочные записи

Таблица хранит как активных пользователей системы (с правом входа), так и справочные записи (для подстановки в листы согласования — ректор, директор института и др.):

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | `uuid` | PK | Идентификатор |
| `email` | `varchar(255)` | UNIQUE, NULL | Корпоративный email; NULL для справочных записей |
| `password_hash` | `varchar(255)` | NULL | Хеш пароля (Argon2id); NULL для справочных записей |
| `full_name` | `varchar(255)` | NOT NULL | ФИО полностью — «Иванов Александр Борисович» |
| `name_for_document` | `varchar(255)` | NOT NULL | Подпись в документах — «А. Б. Иванов» |
| `official_designation` | `varchar(255)` | UNIQUE, NULL | Канонический код для именованных лукапов |
| `position` | `varchar(255)` | NULL | Должность — «Заведующий кафедрой» |
| `academic_degree` | `varchar(100)` | NULL | Учёная степень |
| `signatory_role` | `varchar(50)` | NULL, CHECK | Категория подписанта (см. ниже) |
| `department_id` | `uuid` | FK → `departments.id`, NULL | Кафедра |
| `institute_id` | `uuid` | FK → `institutes.id`, NULL | Институт (для сотрудников без кафедры) |
| `can_login` | `boolean` | NOT NULL, DEFAULT true | true — пользователь системы; false — только справочная запись |
| `is_active` | `boolean` | NOT NULL, DEFAULT true | Активна ли учётная запись |
| `created_at` | `timestamptz` | NOT NULL | |
| `updated_at` | `timestamptz` | NOT NULL | |

**Допустимые значения `signatory_role`:** `department_head`, `department_head_acting`, `institute_director`, `vice_rector`, `rector`, `umu_head`, `library_director`, `it_dept_head`. Подробнее — в разделе 2.x.4.

**Ограничения целостности:**

```sql
-- Никто не может входить без email и пароля
CHECK ((can_login = false) OR (email IS NOT NULL AND password_hash IS NOT NULL))

-- Привязка подписанта согласована с его уровнем в оргструктуре
CHECK (
  (signatory_role IN ('department_head', 'department_head_acting') AND department_id IS NOT NULL)
  OR (signatory_role = 'institute_director' AND institute_id IS NOT NULL AND department_id IS NULL)
  OR (signatory_role IN ('rector', 'vice_rector', 'umu_head', 'library_director', 'it_dept_head')
      AND department_id IS NULL AND institute_id IS NULL)
  OR (signatory_role IS NULL)
)
```

**Индексы:**
- UNIQUE (`email`) WHERE `email IS NOT NULL`
- UNIQUE (`official_designation`) WHERE `official_designation IS NOT NULL`
- UNIQUE (`signatory_role`, `department_id`) WHERE `signatory_role IN ('department_head', 'department_head_acting') AND department_id IS NOT NULL`
- UNIQUE (`signatory_role`, `institute_id`) WHERE `signatory_role = 'institute_director'`
- INDEX (`department_id`), INDEX (`institute_id`), INDEX (`can_login`, `is_active`)

#### `discipline_semester_details` — детализация по семестрам

Соответствует структуре `DisciplineDetails` из парсера `DisciplineDataExtractor`. Хранит распределение часов и вид контроля по каждому семестру, в котором изучается дисциплина:

| Поле | Тип | Ограничения | Описание |

| `id` | `uuid` | PK | |
| `discipline_id` | `uuid` | FK → `disciplines.id` ON DELETE CASCADE | |
| `semester` | `int` | NOT NULL | 1–12 |
| `contact_hours` | `int` | NOT NULL DEFAULT 0 | Контактные часы |
| `lectures` | `int` | NOT NULL DEFAULT 0 | |
| `practice` | `int` | NOT NULL DEFAULT 0 | Практические занятия |
| `lab_hours` | `int` | NOT NULL DEFAULT 0 | Лабораторные занятия |
| `self_study` | `int` | NOT NULL DEFAULT 0 | Самостоятельная работа |

**Допустимые значения `control_type`:**

```sql

  'exam',                -- экзамен                       (Exam в парсере)
  'credit',              -- зачёт                         (Credit)
  'graded_credit',       -- зачёт с оценкой               (CreditWithRating)
```

## 2.x.4. Ключевые решения и их обоснование

### Иерархия Институт → Кафедра → Пользователь

Оргструктура МГТУ «СТАНКИН» (как и большинства вузов) трёхуровневая: университет → институт → кафедра. Дисциплина закрепляется за кафедрой, кафедра входит в институт. Подписанты документа могут принадлежать любому из этих уровней:

- **Уровень кафедры** — заведующий кафедрой, разработчик документа (преподаватель).
- **Уровень института** — директор института.
- **Уровень университета** — ректор, проректор, начальник УМУ.

В таблице `users` для этого предусмотрены два внешних ключа: `department_id` и `institute_id`, оба NULL. Преподаватель кафедры имеет заполненный `department_id` (институт выводится через `departments.institute_id`); директор института — заполненный `institute_id` при пустом `department_id`; сотрудник университетского уровня — оба поля NULL.

### Декларативная модель листа согласования через резолверы

Подписанты документа — это не данные, извлекаемые из учебного плана, а **справочная таблица + правила резолва, описанные в шаблоне**. Шаблон не указывает конкретного человека («подписывает Иванов А. Б.»), а указывает **роль и правило поиска**: «подписывает заведующий кафедрой данной дисциплины». При создании или генерации документа система разрешает каждое правило на конкретного человека из таблицы `users`.

Это решение даёт три преимущества:

1. **Один шаблон работает для всех кафедр.** Не нужно создавать отдельный шаблон РПД для кафедры ИТиВС, отдельный — для кафедры ПриМ, и так далее.
2. **Подписи не «прибиты» к шаблону.** При смене заведующего кафедрой меняется одна строка в справочнике, а не каждый шаблон.
3. **Реорганизация оргструктуры не ломает шаблоны.** Если кафедры объединяются или передаются между институтами — это административное действие, шаблоны продолжают работать.

Реализация. Поле `users.signatory_role` фиксирует категорию подписанта (`department_head`, `institute_director`, `rector` и др.). В шаблоне поле `signatures_config` декларативно описывает порядок и категории подписей. При обработке документа сервис `SignatureResolver` (см. главу 4) разрешает каждое правило в конкретного пользователя по таблице `users` с учётом контекста дисциплины. Полный каталог резолверов и формат описания подписей задаются в JSON Schema шаблона (см. раздел «Шаблоны документов»).

Этот механизм — отдельный аргумент в копилку расширяемости системы. В существующих аналогах из главы 1 такого механизма не описано: обычно лист согласования жёстко зашит в коде или хранится как набор разрозненных шаблонов.

### Параллельное электронное согласование

В бумажном процессе подписи ставятся по очереди, потому что документ физически носят между кабинетами и ищут нужных людей. В электронной версии этой причины нет: согласующему достаточно войти в систему и отметить согласие, и порядок значения не имеет. Поэтому согласование в системе сделано **параллельным**, а не последовательным — это упрощает процесс и снимает «хождение по кабинетам».

Существенные следствия, влияющие на модель:

1. **Электронных согласующих может быть меньше, чем подписантов в итоговом бумажном документе.** Требования к бумажной версии не отменяются: итоговый документ всё равно подписывается физически по прежнему процессу. Поэтому полный лист согласования формируется при генерации документа из `signatures_config` (со всеми подписантами), а в электронном контуре отслеживается только подмножество — те, кто отмечает согласие в системе.
2. **В шаблоне (`signatures_config`) каждый подписант помечается флагом**, участвует ли он в электронном согласовании. Электронные → попадают в `document_signatures` и отслеживаются по статусу; бумажные → только рендерятся в листе согласования для физической подписи.
3. **Документ переходит в `approved`, когда все электронные согласующие отметили согласие** (в любом порядке). Любой из них может вернуть документ на доработку с обязательным комментарием — это ветка «есть замечания» на диаграмме состояний.

Граница прототипа. На первом этапе система разворачивается на одной кафедре и в методическом отделе; остальные подразделения вуза в электронный контур не входят — это требует согласования со службами вуза и выходит за рамки настоящей работы. Поэтому набор электронных согласующих в прототипе намеренно узкий, тогда как полный лист согласования для бумажной версии формируется в полном составе. При расширении системы на весь вуз (перспектива) электронными можно сделать всех подписантов без изменения модели — достаточно проставить флаг в `signatures_config`.

Среднее время согласования (FR-REP-01) считается по разнице `created_at` и `approved_at` в `document_signatures`.

### Двухстадийная привязка к компетенциям и индикаторам

ФГОС 3++ требует привязки результатов обучения к индикаторам достижения компетенций (`УК-1.1`, `УК-1.2`), а не к компетенциям целиком (`УК-1`). Однако исходные данные не всегда дают индикаторы: парсер `DisciplineDataExtractor` на текущей версии извлекает только коды компетенций.

Для совместимости с обеими стадиями таблица `document_competence_links` имеет два внешних ключа: `competence_id` и `indicator_id`, оба nullable, с ограничением «должна быть указана хотя бы одна привязка». На MVP-стадии заполняется только `competence_id`; при доработке парсера и заполнении справочника индикаторов записи дополняются `indicator_id`. Это позволяет не блокировать первоначальный запуск и не делать болезненную миграцию в будущем.

### Версионирование шаблонов и документов

**Шаблоны** версионируются «по месту»: при изменении опубликованного шаблона создаётся новая запись в `document_templates` с тем же `type` и `name`, но новым `version` и статусом `draft`. Предыдущая запись остаётся в статусе `published` до момента публикации новой. Документ запоминает использованную версию шаблона через `template_version`.

**Документы** версионируются через отдельную таблицу `document_versions`, хранящую снимки. Это избыточнее по данным, но позволяет реализовать FR-DOC-13 (diff версий) и FR-DOC-17 (откат).

### Устаревание документа — флаг, а не статус

Когда публикуется новая версия шаблона, документы, созданные по старой версии, должны быть помечены как устаревшие (FR-DOC-12). На раннем этапе проектирования для этого предполагался отдельный статус `obsolete`. От него отказались в пользу булева флага `documents.is_outdated`.

Причина: устаревание **ортогонально** жизненному циклу документа. Документ может быть `approved` (утверждён и используется) и одновременно устаревшим (вышла новая версия шаблона). Если бы «устарел» был статусом, пришлось бы дублировать всю воронку статусов в двух вариантах (устаревший/актуальный) либо терять информацию о реальном положении документа в процессе согласования. Флаг же позволяет независимо фильтровать: «показать все утверждённые, но устаревшие РПД». Это согласуется и с диаграммой состояний документа, где отдельного состояния «устарел» нет, а есть лишь переход в архив по решению пользователя.

### Поле `search_vector` — отдельная колонка

Альтернатива — индекс по выражению (`CREATE INDEX ... USING GIN (to_tsvector('russian', title || ...))`) — работает, но требует повторения выражения в запросах. Выбран вариант с GENERATED-колонкой ради читаемости кода запросов и стабильной производительности.

### Роли — справочник, а не enum

Enum в PostgreSQL требует миграции для изменения. Если в будущем появится новая роль (например, «Внешний эксперт» или «Декан»), с enum это обходится дороже, чем INSERT. Кроме того, роли в БД-справочнике легко связывать с таблицей разрешений, если в перспективе появится гранулярная модель прав.

### JSONB, а не JSON

JSONB хранит данные в бинарном формате после парсинга, что даёт: поддержку GIN-индексов, быстрый доступ к полям через `->` и `->>`, операторы `@>`, `?`, `?|`. Единственный недостаток — потеря исходного форматирования (порядок ключей, пробелы), что для нашего случая несущественно.

### Discipline отделён от Document

Дисциплина существует независимо от любого конкретного документа: она появляется в БД при импорте учебного плана и существует, даже если к ней пока не создано ни одного документа. Это позволяет методисту создавать шаблоны, применимые к множеству дисциплин; автоматически предзаполнять поля нового документа данными из `disciplines`; строить отчёты по прогрессу («сколько дисциплин в УП имеют актуальные РПД»).

## 2.x.5. Миграции и версионирование схемы

Миграции выполняются через EF Core (`dotnet ef migrations add`). Политика:

- Миграции **не удаляют данные** — только добавляют и расширяют.
- Переименование колонок и типов идёт через двухшаговую миграцию: (1) добавить новое → скопировать данные → (2) удалить старое в отдельном релизе.
- Seed-данные (роли, шаблон ФГОС, стандартные типы контроля) — через идемпотентные SQL-скрипты, запускаемые при старте приложения.

## 2.x.6. Оценка объёма данных

Расчёт для типичного университета (МГТУ «СТАНКИН») на горизонте 5 лет:

| Сущность | Оценка записей | Размер |
|---|---|---|
| `users` | ~1 500 (с учётом справочных записей) | < 2 МБ |
| `institutes`, `departments` | ~50 | < 0,1 МБ |
| `disciplines` | ~5 000 (100 УП × 50 дисциплин) | ~2 МБ |
| `discipline_semester_details` | ~10 000 | ~3 МБ |
| `documents` (РПД + ФОС) | ~10 000 | ~500 МБ (с `payload`) |
| `document_signatures` | ~30 000 (электронные согласующие, ≈3 на документ) | ~6 МБ |
| `document_versions` | ~50 000 | ~2,5 ГБ |
| `audit_log` | ~500 000 / год | ~300 МБ / год |

Итого 5–10 ГБ на горизонте 5 лет — штатная нагрузка для PostgreSQL на сервере, заявленном в ограничениях.

## Правки по ревизии архитектуры (июнь 2026)

**`users` — учётные данные выносятся на сервер аутентификации.** Поле `password_hash` и ограничение `CHECK ((can_login = false) OR (email IS NOT NULL AND password_hash IS NOT NULL))` удаляются: пароли хранит сервер аутентификации (Duende IdentityServer на базе ASP.NET Identity). Добавляется поле `identity_subject varchar(200) NULL UNIQUE` — идентификатор пользователя на сервере аутентификации (утверждение `sub` токена). Новое ограничение: `CHECK ((can_login = false) OR (email IS NOT NULL AND identity_subject IS NOT NULL))`. Создание учётной записи Администратором создаёт пользователя на сервере аутентификации и сохраняет его идентификатор.

**`notifications` — новая таблица (контекст Infrastructure), FR-REV-08.**

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | `uuid` | PK | |
| `recipient_id` | `uuid` | FK → users, NOT NULL | Получатель |
| `event_type` | `varchar(50)` | NOT NULL | Тип события: смена статуса, комментарий, возврат и т. д. |
| `document_id` | `uuid` | FK → documents, NULL | Связанный документ |
| `payload` | `jsonb` | NOT NULL | Текст и параметры уведомления |
| `created_at` | `timestamptz` | NOT NULL | |
| `read_at` | `timestamptz` | NULL | Время прочтения; NULL — не прочитано |
| `emailed_at` | `timestamptz` | NULL | Время отправки по почте (немедленно или в дайджесте) |

Частичный индекс `(recipient_id, created_at) WHERE read_at IS NULL` обслуживает счётчик непрочитанных.

**`document_templates.print_template_file_id`** `uuid NULL FK → uploaded_files` — DOCX-шаблон оформления с закладками (FR-TPL-13). Соответствие «закладка — поле схемы» хранится в поле `print_mapping jsonb`.

**`uploaded_files` — содержимое в базе данных.** Добавляется поле `content bytea NULL`. Невосстановимые файлы (исходные данные, шаблоны оформления) хранятся в `content` и попадают в резервные копии базы; `storage_path` становится необязательным. Сгенерированные файлы (`generated_files`) остаются на томе файлового хранилища: их можно сформировать заново.

**Номер версии.** `documents.version` и `document_templates.version` увеличиваются перехватчиком сохранения EF Core при каждом изменении — не вручную в обработчиках.
