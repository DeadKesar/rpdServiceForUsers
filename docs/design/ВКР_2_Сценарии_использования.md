# Раздел 2.x. Сценарии использования (Use Cases)

*Черновик для главы 2 ВКР. Текстовые сценарии к диаграмме вариантов использования. Дополняет диаграмму: диаграмма показывает «что» и «кто», сценарии раскрывают «как» — основной поток, альтернативы, предусловия.*

## Условные обозначения

Каждый сценарий описывается по единому шаблону: идентификатор и название, основной актор, цель, предусловия, основной поток, альтернативные потоки и исключения, постусловия, трассировка к функциональным требованиям. Акторы: **П** — Преподаватель, **М** — Методист (сотрудник методического отдела), **У** — Утверждающий, **А** — Администратор.

## UC-01. Импорт исходных данных и создание шаблона

**Актор:** Методист.
**Цель:** загрузить учебный план, список и матрицу компетенций, справочник должностей и создать на их основе шаблон документа.
**Предусловия:** методист авторизован; структура типа документа (JSON Schema) для РПД/ФОС задана администратором.

**Основной поток:**
1. Методист открывает раздел «Шаблоны» и выбирает «Создать шаблон».
2. Указывает тип (РПД или ФОС), направление подготовки и учебный год.
3. Загружает исходные файлы: учебный план (`.xlsx`), список компетенций (`.docx`), матрицу компетенций (`.docx`), при необходимости — файл должностей.
4. Система проверяет файлы на корректность формата и структуры (FR-VAL-05) и запускает фоновую задачу разбора (парсер `DisciplineDataExtractor`).
5. По завершении система создаёт записи в справочниках (`curriculum_plans`, `disciplines`, `discipline_semester_details`, `competences`, `competence_matrix`) и фиксирует результат в `parser_runs`.
6. Система отображает сводку: сколько дисциплин, компетенций, сотрудников извлечено, какие проблемы обнаружены.
7. Шаблон переходит в статус «пустой» → методист настраивает поля и правила проверки → статус «заполненный».

**Альтернативы и исключения:**
- 4а. Файл повреждён или не соответствует структуре → система прерывает разбор, указывает позицию ошибки (файл, лист, строка) и предлагает повторить загрузку.
- 5а. Часть строк не распозналась (например, ФИО «????» в справочнике должностей) → записи помечаются в `errors_log`, методист устраняет их вручную.

**Постусловия:** справочники наполнены; создан шаблон в статусе «заполненный».
**Трассировка:** FR-TPL-01, FR-TPL-02 – FR-TPL-07, FR-VAL-05.

## UC-02. Публикация шаблона

**Актор:** Методист.
**Цель:** сделать шаблон доступным преподавателям для создания документов.
**Предусловия:** шаблон в статусе «заполненный»; методист авторизован.

**Основной поток:**
1. Методист открывает заполненный шаблон и выбирает «Опубликовать».
2. Система выполняет финальную проверку целостности шаблона (полнота обязательных полей, связность с исходными данными, корректность сумм часов) — FR-TPL-11.
3. Проверка пройдена → шаблон переходит в статус «опубликованный», открывается доступ для создания документов.

**Альтернативы и исключения:**
- 2а. Проверка не пройдена → система перечисляет ошибки, шаблон остаётся в статусе «заполненный» для исправления.
- 3а. Публикуется новая версия ранее опубликованного шаблона → предыдущая версия помечается устаревшей, документы на её основе получают флаг `is_outdated` (FR-DOC-12).

**Постусловия:** шаблон опубликован и доступен преподавателям.
**Трассировка:** FR-TPL-08, FR-TPL-09, FR-TPL-11, FR-DOC-12.

## UC-03. Создание РПД по шаблону

**Актор:** Преподаватель.
**Цель:** создать черновик документа на основе опубликованного шаблона с автозаполнением из учебного плана.
**Предусловия:** существует опубликованный шаблон нужного типа; преподаватель авторизован.

**Основной поток:**
1. Преподаватель выбирает «Создать документ», указывает тип, направление и дисциплину.
2. Система создаёт документ, копирует схему из шаблона и автозаполняет поля с пометкой `x-source` (название дисциплины, часы, компетенции из матрицы) — FR-DOC-02.
3. Документ открывается в редакторе в статусе «черновик».

**Альтернативы и исключения:**
- 1а. Преподаватель выбирает «переиспользовать данные из ранее созданного РПД/ФОС» → система предлагает совместимые документы автора и переносит их содержимое в новый документ (FR-DOC-07).
- 2а. Для дисциплины не разрешается подписант (нет заведующего кафедрой) → документ создаётся, но при отправке на согласование потребуется ручное назначение.

**Постусловия:** создан документ в статусе «черновик» с предзаполненными полями.
**Трассировка:** FR-DOC-01, FR-DOC-02, FR-DOC-07.

## UC-04. Редактирование документа с автосохранением

**Актор:** Преподаватель.
**Цель:** заполнить методическое содержание документа.
**Предусловия:** документ в статусе «черновик» или «на доработке»; преподаватель — автор документа.

**Основной поток:**
1. Преподаватель открывает документ; слева — дерево разделов с индикаторами заполненности (FR-DOC-03).
2. Заполняет поля текущего раздела; обязательные поля выделены (FR-DOC-04).
3. Система автоматически сохраняет черновик каждые 3–5 минут с индикатором состояния (FR-DOC-05).
4. Преподаватель при необходимости выбирает «Сохранить, не отправлять» → документ переходит в «сохранённый черновик».

**Альтернативы и исключения:**
- 3а. Документ открыт параллельно в другой сессии → система применяет оптимистическую блокировку и предупреждает о конфликте (NFR-REL-04).
- 4а. Преподаватель просматривает комментарии методиста (если документ возвращён на доработку) и устраняет замечания.

**Постусловия:** изменения сохранены; документ в статусе «черновик» или «сохранённый черновик».
**Трассировка:** FR-DOC-03 – FR-DOC-06, NFR-REL-02, NFR-REL-04.

## UC-05. Отправка документа на проверку

**Актор:** Преподаватель.
**Цель:** передать заполненный документ методисту на проверку.
**Предусловия:** документ в статусе «черновик»/«сохранённый черновик»; преподаватель — автор.

**Основной поток:**
1. Преподаватель выбирает «Отправить на проверку».
2. Система выполняет полную валидацию: JSON Schema + правила (`hours_match_curriculum`, `all_indicators_covered` и др.) — FR-VAL-01 – FR-VAL-07.
3. Валидация пройдена → документ переходит в «на проверке», редактирование блокируется, методист уведомляется (FR-REV-08).

**Альтернативы и исключения:**
- 2а. Найдены ошибки (несоответствие суммы часов, незаполненные обязательные поля) → отправка блокируется, система перечисляет проблемы.
- 1а. Пакетная отправка: преподаватель выбирает несколько черновиков и отправляет их одним действием (FR-GEN-08).

**Постусловия:** документ в статусе «на проверке».
**Трассировка:** FR-DOC-06, FR-VAL-01 – FR-VAL-07, FR-REV-08, FR-GEN-08.

## UC-06. Проверка документа и возврат на доработку

**Актор:** Методист.
**Цель:** проверить документ и при наличии замечаний вернуть автору.
**Предусловия:** документ в статусе «на проверке»; методист авторизован.

**Основной поток:**
1. Методист открывает список документов на проверке с фильтрами по автору, дисциплине, дате (FR-REV-01).
2. Открывает документ в режиме просмотра, оставляет структурированные комментарии к конкретным полям (FR-REV-02).
3. При наличии замечаний выбирает «Вернуть на доработку».
4. Система проверяет наличие хотя бы одного комментария (FR-REV-03) → документ переходит в «на доработке», редактирование разблокируется, автор уведомляется.

**Альтернативы и исключения:**
- 2а. Методист вносит мелкую правку напрямую без смены статуса (событие «правка методистом») — отражено на диаграмме состояний.
- 3а. Замечаний нет → методист переходит к приёму документа (UC-07).

**Постусловия:** документ в статусе «на доработке» с комментариями; либо переходит к приёму.
**Трассировка:** FR-REV-01 – FR-REV-03, FR-REV-08.

## UC-07. Приём документа

**Актор:** Методист.
**Цель:** принять проверенный документ и передать его на согласование.
**Предусловия:** документ в статусе «на проверке», замечаний нет; методист авторизован.

**Основной поток:**
1. Методист выбирает «Принять документ».
2. Документ переходит в статус «принят»; преподаватель уведомляется; формируется печатная версия (предварительный PDF).
3. Система разрешает подписантов из `signatures_config` шаблона, создаёт записи `document_signatures` для электронных согласующих и переводит документ в статус «на согласовании».

**Альтернативы и исключения:**
- 3а. Какой-либо электронный согласующий не разрешился (нет в справочнике) → методист или администратор назначает подписанта вручную перед стартом согласования.

**Постусловия:** документ в статусе «на согласовании»; созданы записи согласования.
**Трассировка:** FR-REV-04.

## UC-08. Параллельное электронное согласование

**Актор:** Утверждающий (несколько, параллельно).
**Цель:** отметить согласие с документом.
**Предусловия:** документ в статусе «на согласовании»; для согласующего создана запись `document_signatures` со статусом `pending`.

**Основной поток:**
1. Утверждающий видит в своём списке документы, ожидающие его согласования (порядок не задан) — FR-REV-05.
2. Открывает документ, при необходимости просматривает комментарии и историю.
3. Отмечает согласие → его запись в `document_signatures` получает статус `approved` и время.
4. Когда согласие отметили все электронные согласующие, документ автоматически переходит в статус «согласован» (FR-REV-06).

**Альтернативы и исключения:**
- 3а. Согласующих несколько и они действуют независимо — порядок отметок не важен (параллельная модель).
- 4а. Часть подписантов участвует только в бумажном документообороте → они не отслеживаются в системе; их подписи проставляются на распечатанной версии (см. UC-10).

**Постусловия:** при наличии всех согласий документ в статусе «согласован».
**Трассировка:** FR-REV-05, FR-REV-06.

## UC-09. Возврат документа с согласования

**Актор:** Утверждающий.
**Цель:** вернуть документ на доработку при обнаружении проблем.
**Предусловия:** документ в статусе «на согласовании»; согласующий имеет запись `document_signatures`.

**Основной поток:**
1. Утверждающий открывает документ и обнаруживает замечание.
2. Выбирает «Вернуть с согласования», указывает обязательный комментарий.
3. Его запись получает статус `rejected`; документ переходит обратно в «на проверке» (ветка «есть замечания»), методист уведомляется.

**Альтернативы и исключения:**
- 3а. Документ возвращается методисту, а не сразу автору, — методист решает, что делать с замечанием (учесть самому или вернуть преподавателю на доработку).

**Постусловия:** документ в статусе «на проверке»; цепочка согласования сброшена.
**Трассировка:** FR-REV-06.

## UC-10. Генерация документа в DOCX/PDF

**Актор:** Преподаватель (а также Методист — для согласованных документов).
**Цель:** получить итоговый документ в формате для печати и физической подписи.
**Предусловия:** документ существует; для финальной версии — статус «согласован».

**Основной поток:**
1. Преподаватель выбирает «Сформировать в DOCX» или «Сформировать в PDF».
2. Система ставит фоновую задачу генерации (Hangfire), создаёт запись `generation_tasks` со статусом `queued` (FR-GEN-04).
3. Воркер формирует документ по шаблону оформления МГТУ «СТАНКИН», вставляет полный лист согласования (все подписанты из `signatures_config`, включая бумажных) с разрешёнными ФИО и должностями.
4. По завершении создаётся `generated_files`, преподаватель уведомляется и скачивает файл.

**Альтернативы и исключения:**
- 1а. Пакетная генерация: формирование нескольких документов одной задачей (FR-GEN-05).
- 3а. Имя файла формируется автоматически по шаблону `<Тип>_<Дисциплина>_<Год>` (FR-GEN-03).
- 4а. Файл доступен для скачивания ограниченное время, затем удаляется (FR-GEN-06).

**Постусловия:** сформирован файл DOCX/PDF, доступный для скачивания и печати.
**Трассировка:** FR-GEN-01 – FR-GEN-06.

## Связь сценариев с диаграммой состояний документа

Сценарии последовательно проводят документ по статусам жизненного цикла:

| Сценарий | Переход статуса документа |
|---|---|
| UC-03 | — → черновик |
| UC-04 | черновик ↔ сохранённый черновик |
| UC-05 | черновик → на проверке |
| UC-06 | на проверке → на доработке (→ черновик при доработке) |
| UC-07 | на проверке → принят → на согласовании |
| UC-08 | на согласовании → согласован |
| UC-09 | на согласовании → на проверке |
| UC-10 | (статус не меняется; формируется файл) |

Сценарии работы со справочниками и шаблонами (UC-01, UC-02) предшествуют работе с документами и подготавливают данные, на которых строится весь дальнейший процесс.
