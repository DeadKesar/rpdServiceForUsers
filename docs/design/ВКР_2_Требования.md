# Раздел 2.x. Требования к автоматизированной системе

*Черновик для главы 2 ВКР. Адаптирован из примера для десктопного приложения под многопользовательскую веб-архитектуру (Blazor WASM + .NET 10 API + PostgreSQL + Docker).*

## 2.x.1. Общие положения

Требования к системе сформулированы на основе результатов анализа предметной области (глава 1) и проектных решений, принятых в разделах «Роли» и «Основные экраны интерфейса» настоящей главы. Требования классифицированы по модели FURPS+: функциональные (Functionality) и нефункциональные (Usability, Reliability, Performance, Supportability + ограничения).

Каждое требование отнесено к одному из двух **контуров реализации**:

- **MVP** — обязательно к реализации в рамках настоящей ВКР. Охватывает автоматизацию создания РПД и ФОС.
- **Перспектива** — требование не реализуется в прототипе, но **учитывается в архитектуре**, чтобы обеспечить расширение системы на другие методические документы образовательной программы (программы практик, программа государственной итоговой аттестации, аннотации рабочих программ и т.п.) без переработки ядра.

Используемые сокращения в идентификаторах: `FR` — функциональное требование (Functional Requirement), `NFR` — нефункциональное (Non-Functional Requirement), далее — код модуля и порядковый номер.

## 2.x.2. Функциональные требования

### 2.x.2.1. Аутентификация и управление пользователями (FR-AUTH)

Система должна обеспечить надёжную идентификацию пользователей и разграничение доступа в соответствии с ролями, определёнными в разделе «Роли» (Преподаватель, Методист, Утверждающий, Администратор).

| № | Требование | Контур |
|---|---|---|
| FR-AUTH-01 | Аутентификация пользователей по протоколам OpenID Connect / OAuth 2.0 с выдачей JWT-токенов | MVP |
| FR-AUTH-02 | Регистрация новых пользователей возможна только по запросу через Администратора (самостоятельная регистрация запрещена) | MVP |
| FR-AUTH-03 | Система должна поддерживать восстановление пароля по корпоративной электронной почте | MVP |
| FR-AUTH-04 | Разграничение прав доступа на основе ролевой модели (RBAC), поддержка совмещения ролей на одной учётной записи (например, Методист + Утверждающий) | MVP |
| FR-AUTH-05 | Принудительное завершение сессии по таймауту бездействия (значение настраивается Администратором, по умолчанию 60 мин.) | MVP |
| FR-AUTH-06 | Журналирование всех событий входа, выхода и неуспешных попыток аутентификации с сохранением IP-адреса и времени | MVP |
| FR-AUTH-07 | Интеграция с корпоративной службой каталогов вуза (LDAP / Active Directory) | Перспектива |
| FR-AUTH-08 | Двухфакторная аутентификация (2FA) для ролей Методист, Утверждающий, Администратор | Перспектива |

### 2.x.2.2. Управление шаблонами документов (FR-TPL)

Методист отвечает за создание и публикацию шаблонов, на основе которых преподаватели создают конкретные документы. Шаблон представляет собой структурированное описание разделов и полей будущего документа с привязкой к исходным данным (учебный план, справочник компетенций, матрица компетенций).

| № | Требование | Контур |
|---|---|---|
| FR-TPL-01 | Методист должен иметь возможность создавать, редактировать и удалять черновики шаблонов через веб-интерфейс | MVP |
| FR-TPL-02 | Система должна поддерживать загрузку исходных файлов: учебного плана (`.xlsx`), списка компетенций (`.docx`), матрицы компетенций (`.docx`) и справочника должностей сотрудников (`.xlsx`). Разбор выполняется в фоновом режиме с отображением хода выполнения, сводки извлечённых данных и журнала ошибок с привязкой к файлу, листу и строке | MVP |
| FR-TPL-03 | Система должна автоматически извлекать из учебного плана: название дисциплины, уровень образования, направление и профиль подготовки, форму обучения, общий объём часов, распределение часов по видам занятий (лекции, практики, лабораторные, СРС, контроль), распределение по семестрам, зачётные единицы, вид контроля по семестрам, структуру плана (блоки и части, модули, элективные дисциплины) и закреплённую кафедру | MVP |
| FR-TPL-04 | Система должна извлекать из справочника компетенций перечень компетенций с кодами (УК, ОПК, ПК) и формулировками | MVP |
| FR-TPL-05 | Система должна извлекать из матрицы компетенций связи дисциплин с кодами компетенций | MVP |
| FR-TPL-06 | Автоматическое сопоставление кодов компетенций из матрицы с полными формулировками из справочника | MVP |
| FR-TPL-07 | Ручная корректировка распознанных данных до публикации шаблона | MVP |
| FR-TPL-08 | Шаблон проходит жизненный цикл из шести состояний (см. диаграмму состояний шаблона): Пустой, Черновик, Сохранённый черновик, Опубликован, Архивный, Удалённый. Только опубликованные шаблоны доступны преподавателям для создания документов | MVP |
| FR-TPL-09 | Версионирование шаблонов: при изменении опубликованного шаблона создаётся новая версия; предыдущие версии помечаются как устаревшие, но остаются доступны для просмотра | MVP |
| FR-TPL-10 | Система должна поддерживать типы документов `РПД` и `ФОС` как базовые и обеспечивать архитектурную возможность добавления новых типов (аннотация дисциплины, программа практики, программа государственной итоговой аттестации) без изменения ядра | MVP (архитектура) / Перспектива (реализация) |
| FR-TPL-11 | Валидация шаблона перед публикацией: проверка полноты обязательных полей, целостности связей с исходными данными, корректности сумм часов | MVP |
| FR-TPL-12 | Импорт справочника должностей сотрудников: ФИО, должность, формулировка для документа, подразделение. Записи без права входа в систему используются для подстановки в лист согласования; категорию подписанта назначает Администратор | MVP |
| FR-TPL-13 | К шаблону документа прикрепляется шаблон оформления в формате DOCX с именованными закладками для автозаполняемых полей. Соответствие «закладка — поле схемы» хранится как данные шаблона; при публикации проверяется, что каждая закладка сопоставлена полю | MVP |
| FR-TPL-14 | Состав разделов документа определяется данными учебного плана: разделы лабораторных и практических занятий, курсовой работы (проекта) включаются только при наличии у дисциплины соответствующих часов или вида аттестации. Отключённый раздел в печатной форме заменяется стандартной формулировкой «…не предусмотрено» | MVP |

### 2.x.2.3. Создание и редактирование документов (FR-DOC)

Преподаватель работает с документом в структурированном веб-редакторе, в котором разделы и поля заданы выбранным шаблоном. Редактор должен минимизировать оформительскую работу и сосредоточить преподавателя на методическом содержании.

| № | Требование | Контур |
|---|---|---|
| FR-DOC-01 | Преподаватель должен иметь возможность создать новый документ на основе любого опубликованного шаблона, выбрав тип, уровень и направление подготовки | MVP |
| FR-DOC-02 | При создании документа система автоматически предзаполняет поля данными из учебного плана и справочника компетенций в соответствии со схемой шаблона | MVP |
| FR-DOC-03 | Редактор документа должен отображать слева дерево разделов с индикаторами заполненности (заполнено / частично / не заполнено) | MVP |
| FR-DOC-04 | Центральная область редактора должна показывать поля текущего раздела с обязательными полями, выделенными визуально | MVP |
| FR-DOC-05 | Автосохранение черновика с интервалом 3–5 минут и индикатором состояния («Сохранено в HH:MM») | MVP |
| FR-DOC-06 | Ручное сохранение, сохранение и выход, отправка на проверку (с модальным подтверждением и проверкой полноты обязательных полей) | MVP |
| FR-DOC-07 | Возможность импорта содержимого из собственных документов преподавателя, созданных ранее на основе совместимых шаблонов | MVP |
| FR-DOC-08 | Преподаватель видит и может редактировать только собственные документы | MVP |
| FR-DOC-09 | Хранение истории изменений документа (кто, когда, какие поля) с возможностью просмотра версий Методистом и Администратором | MVP |
| FR-DOC-10 | Предпросмотр документа (для шаблона — с тестовыми данными) в двух режимах: черновой — быстрое приближение структуры и содержимого; точный — PDF, сформированный тем же генератором, что и итоговый файл. Финальная доводка оформления допускается в скачанной копии DOCX | MVP |
| FR-DOC-11 | Документ может находиться в одном из 9 состояний (см. диаграмму состояний): Черновик, Сохранённый черновик, На проверке, На доработке, Принят, На согласовании, Согласован, Архивный, Удалённый | MVP |
| FR-DOC-12 | Автоматическая пометка документа как устаревшего (флаг «Устарел») при публикации новой версии шаблона-предка. Признак не меняет статус документа в процессе согласования и позволяет отдельно отбирать утверждённые, но устаревшие документы | MVP |
| FR-DOC-13 | Визуальное сравнение двух версий документа (diff): построчная подсветка изменений в текстовых полях (зелёный/красный), выделение добавленных и удалённых строк в таблицах часов и компетенций. Кнопка «Сравнить с предыдущей версией» — в истории изменений | MVP |
| FR-DOC-14 | Исполнители (составители) документа: документ имеет упорядоченный список исполнителей для титула и листа согласования; владелец-автор остаётся единственным редактором | MVP |
| FR-DOC-15 | Передача владения документом другому пользователю (администратором или методистом) — например, при смене ответственного преподавателя | MVP |
| FR-DOC-16 | Совместное одновременное редактирование документа несколькими пользователями | Перспектива |
| FR-DOC-17 | Возможность отката к любой предыдущей версии документа с автоматическим созданием новой записи в истории и уведомлением всех участников процесса | Перспектива |
| FR-DOC-18 | Документы создаются для каждой дисциплины учебного плана, в том числе элективной и факультативной; практики и государственная итоговая аттестация в MVP не обрабатываются (направление расширения, см. FR-TPL-10) | MVP |
| FR-DOC-19 | ФОС создаётся со ссылкой на конкретный РПД той же дисциплины и наследует из него индикаторы компетенций, разделы и формы контроля | MVP |
| FR-DOC-20 | Текстовые поля поддерживают ограниченное форматирование, переносимое в DOCX без потерь: полужирный и курсивный текст, маркированные и нумерованные списки, таблицы. Математические выражения записываются линейно (текст, символы Unicode) | MVP |
| FR-DOC-21 | Редактор математических формул и вставка изображений в текстовые поля с переносом в DOCX и PDF | Перспектива |
| FR-DOC-22 | Банк заданий ФОС организуется именованными группами (по разделам, видам аттестации и семестрам либо по уровням сложности) со сквозной нумерацией внутри группы; паспорт ФОС ссылается на задания парой «группа — номер». Комплект экзаменационных билетов — необязательный подключаемый раздел | MVP |
| FR-DOC-23 | Автоматическая компоновка экзаменационных билетов из вопросов банка заданий | Перспектива |

### 2.x.2.4. Проверка и согласование документов (FR-REV)

Методист и Утверждающий взаимодействуют с документами преподавателей через цикл проверки, доработки и согласования.

| № | Требование | Контур |
|---|---|---|
| FR-REV-01 | Методист должен иметь доступ к списку всех документов, находящихся в статусах «На проверке», «На доработке», «На согласовании» с фильтрами по автору, дисциплине, дате отправки | MVP |
| FR-REV-02 | Методист может открыть документ в режиме просмотра, оставить структурированные комментарии к конкретным полям и разделам | MVP |
| FR-REV-03 | Возврат документа на доработку возможен только при наличии хотя бы одного комментария (контроль на уровне интерфейса и API) | MVP |
| FR-REV-04 | После успешной проверки методист принимает документ (статус «Принят»): преподаватель уведомляется, формируется печатная версия, после чего документ передаётся на согласование (статус «На согласовании») | MVP |
| FR-REV-05 | Электронный согласующий видит список документов, ожидающих его согласования (порядок согласования не задан) | MVP |
| FR-REV-06 | Согласование параллельное: документ переходит в «Согласован», когда все электронные согласующие отметили согласие (в любом порядке). Любой из них может вернуть документ на доработку методисту с обязательным комментарием | MVP |
| FR-REV-07 | Все действия по смене статуса фиксируются в журнале аудита с указанием пользователя, времени и комментария | MVP |
| FR-REV-08 | Уведомления пользователям о событиях, связанных с их документами: смена статуса, новый комментарий, приближение дедлайна, возврат на доработку. Каналы: в интерфейсе (иконка-колокольчик), по электронной почте. Пользователь может настраивать каналы и частоту (немедленно / ежедневный дайджест / отключить) по каждому типу события; настройки хранятся в профиле | MVP |
| FR-REV-09 | Автоматическая эскалация: если документ находится в статусе «На доработке» более 14 календарных дней — автоматическое уведомление заведующему кафедрой и Методисту со ссылкой на документ | Перспектива |
| FR-REV-10 | Параллельный коллективный просмотр и совместное комментирование документа несколькими Методистами | Перспектива |
| FR-REV-11 | Методист может вносить правки в документ, находящийся на проверке, без смены статуса; правки фиксируются в истории версий с указанием автора | MVP |
| FR-REV-12 | Лист согласования формируется декларативно по правилам шаблона: для каждой позиции задаются роль подписанта и правило его определения (например, «заведующий кафедрой дисциплины», «заведующий выпускающей кафедрой направления»), признак участия в электронном согласовании и место в печатной форме (гриф «УТВЕРЖДАЮ» на титуле или лист согласования). Реквизиты протокола заседания кафедры (номер, дата) вводятся в документ | MVP |
| FR-REV-13 | Методист или Администратор может вручную назначить или заменить подписанта, если правило не нашло его в справочнике или согласующий временно отсутствует | MVP |
| FR-REV-14 | Электронное согласование — внутренняя отметка согласующего лица, не являющаяся электронной подписью; юридически значимые подписи проставляются на печатном экземпляре | MVP |
| FR-REV-15 | Подписание документов усиленной квалифицированной электронной подписью | Перспектива |

### 2.x.2.5. Генерация и экспорт документов (FR-GEN)

Для финального представления документа и предоставления его в учебно-методическое управление система должна формировать документы в стандартных форматах.

| № | Требование | Контур |
|---|---|---|
| FR-GEN-01 | Генерация документа в формате `.docx` с сохранением форматирования (таблицы, шрифты, отступы, оформление, принятое в МГТУ «СТАНКИН») | MVP |
| FR-GEN-02 | Генерация документа в формате `.pdf` конвертацией сформированного DOCX: разметка PDF совпадает с разметкой DOCX | MVP |
| FR-GEN-03 | Автоматическое формирование имени файла по шаблону `<Тип>_<Дисциплина>_<Год>.docx` (например, `РПД_Программирование_2025.docx`) | MVP |
| FR-GEN-04 | Генерация выполняется асинхронно (фоновая задача) с индикацией прогресса и уведомлением по завершении | MVP |
| FR-GEN-05 | Пакетная генерация — возможность одновременного формирования нескольких документов (например, всех РПД, прикреплённых к одному учебному плану) | MVP |
| FR-GEN-06 | Готовые файлы доступны для скачивания в течение настраиваемого периода (по умолчанию 30 дней), после чего автоматически удаляются | MVP |
| FR-GEN-07 | Визуальный редактор шаблонов оформления без ручной разметки закладок в Word (в MVP шаблон оформления загружается как DOCX с закладками, см. FR-TPL-13) | Перспектива |
| FR-GEN-08 | Массовая отправка документов: Преподаватель может выбрать несколько черновиков и пакетно отправить их на проверку (единое модальное подтверждение с проверкой обязательных полей по всем выбранным документам) | MVP |
| FR-GEN-09 | Массовое архивирование документов Администратором или Методистом, устаревших более 5 лет (с предварительным отчётом и подтверждением) | Перспектива |

### 2.x.2.6. Валидация и контроль целостности (FR-VAL)

Ключевое требование, отличающее предлагаемую систему от существующих аналогов, — автоматическая валидация на всех этапах жизненного цикла документа.

| № | Требование | Контур |

## 2.x.4. Ограничения

### Технологические

- Реализация — на платформе .NET 10 и языке C# (обоснование — глава 3).
- СУБД — PostgreSQL; ORM — Entity Framework Core 10.
- Фронтенд — Blazor WebAssembly; собственный JavaScript сводится к минимуму, JS-interop допускается для готовых компонентов (редактор форматированного текста, просмотр PDF).
- Поставка — в виде набора Docker-образов с оркестрацией через Docker Compose.

### Ресурсные

- Серверная часть должна работать на типовом сервере уровня 4 vCPU / 8 ГБ ОЗУ / 100 ГБ SSD.
- Клиентская часть должна работать на типовом офисном ПК: процессор уровня Intel Core i3 или выше, 4 ГБ ОЗУ, современный браузер.

### Экономические

- Использование только открытых или бесплатных для университетского использования библиотек и инструментов; исключение платных лицензий (MS Office, 1С, коммерческие ORM и т.п.).
- Время обучения одного сотрудника работе с системой — не более 30 минут (см. NFR-USA-08).

### Нормативные

- Соответствие ФГОС ВО в части структуры и содержания РПД и ФОС.
- Соответствие внутренним нормативным актам МГТУ «СТАНКИН» (положения о ВКР, об ОП, о текущем контроле).
- Соблюдение ГОСТ 34.602 при оформлении технического задания.
- Соблюдение 152-ФЗ при работе с персональными данными.

### Интеграционные

- На этапе MVP система работает автономно (без прямой интеграции с 1С:Университет и другими информационными системами вуза); обмен данными — через импорт/экспорт файлов.
- В перспективе — интеграция через REST API и/или промежуточную шину данных.

## Примечания к адаптации примера

Ниже — коротко, что изменено по сравнению с десктопной версией требований, чтобы было проще согласовать с научруком:

- **Загрузка файлов:** в десктопе пользователь указывал путь на диске; в вебе — загрузка через браузер, с ограничением по размеру и MIME-проверкой.
- **Авторизация:** вместо Windows-учётной записи — OIDC + JWT, четыре роли, изоляция данных.
- **Производительность:** задаётся не «на ПК с 4 ГБ ОЗУ», а в терминах времени отклика API и числа одновременных пользователей.
- **Рабочий процесс:** добавлены требования на жизненный цикл документа и маршрут согласования, которых в десктопной версии не было.
- **Безопасность:** расширена до полноценного набора для многопользовательской веб-системы (OWASP, персональные данные, аудит).
- **Расширяемость:** вынесена в явные требования (FR-TPL-10, NFR-SUP-10, NFR-SCA-04) — это задел на поддержку других методических документов.
- **Ресурсы:** разделены на серверные и клиентские.
- **Локализация:** добавлены оговорки про английский интерфейс и другие вузы как перспективу.

## Связь требований с научной новизной

Три группы требований составляют основу научной новизны работы и раскрываются в последующих разделах главы:

1. **Унифицированная расширяемая модель методических документов** (FR-TPL-10, FR-TPL-13, FR-TPL-14, NFR-SUP-10, NFR-SCA-04). Единое описание РПД, ФОС и в перспективе других методических документов, в котором состав разделов определяется данными учебного плана, а печатная форма — шаблоном оформления; новый тип документа добавляется без изменения ядра системы.
2. **Сквозная кросс-документная валидация РПД и ФОС** (FR-VAL-01 – FR-VAL-10). Согласованность часов, компетенций, индикаторов, оценочных средств и форм контроля внутри документа и между документами; в рассмотренных аналогах (глава 1) такой валидации нет или она частична.
3. **Декларативное формирование листа согласования** (FR-REV-12, FR-REV-13). Подписанты задаются правилами относительно организационной структуры вуза, а не конкретными лицами: один шаблон работает для всех кафедр, кадровые изменения не требуют правки шаблонов.

Требования FR-VAL-08 (подбор типовых оценочных средств) и FR-REP-02 (реестр документов для аккредитации) определяют практическую значимость системы.
