# Раздел 2.x. Шаблоны документов и схемы данных

*Черновик для главы 2 ВКР. Связывает три уровня: выход парсера `DisciplineDataExtractor`, схему БД, JSON Schema шаблонов.*

## 2.x.1. Подход: шаблоны как JSON Schema

В разделе «Структура данных» обоснован выбор гибридной модели: критичные для валидации поля документа хранятся в нормализованных таблицах, а свободное содержимое — в `documents.payload jsonb`. Структура `payload` определяется **шаблоном документа**, который задаётся методистом и хранится в `document_templates.schema jsonb`.

**Технология описания структуры — JSON Schema (Draft 2020-12).** Этот формат выбран по следующим причинам:

1. **Стандарт.** JSON Schema — общепринятый способ описания структуры JSON-данных, поддерживаемый множеством библиотек на всех платформах. На .NET — `NJsonSchema`, `JsonSchema.Net`.
2. **Декларативность.** Схема описывается данными, а не кодом. Методист может в перспективе редактировать шаблоны через UI без программирования.
3. **Валидация.** Любой `payload` документа можно автоматически проверить на соответствие схеме при сохранении и при отправке на проверку (FR-VAL-05).
4. **Автогенерация форм.** По JSON Schema можно автоматически построить форму редактирования в Blazor (через библиотеки типа JSONForms или собственный рендерер). Это резко снижает объём UI-кода для каждого нового типа документа.
5. **Совместимость с OpenAPI.** API контракты Carter уже описываются в OpenAPI, который основан на JSON Schema — единый формат описания на всех уровнях.

### Расширения базового JSON Schema

Стандарт JSON Schema не покрывает все потребности предметной области, поэтому используются собственные `x-`-расширения (это разрешённая практика):

| Расширение | Назначение |
|---|---|
| `x-source` | Откуда автоматически предзаполнить поле: `parser.section_info.way_code`, `parser.discipline.name`, `db.user.full_name` и т.п. |
| `x-readonly-after` | Поле становится недоступным для редактирования после указанного статуса (`approved`, `under_review`). |
| `x-validation-rule` | Ссылка на пользовательское правило валидации (например, `hours_match_curriculum`). |
| `x-ui-widget` | Подсказка фронтенду, как рендерить поле: `textarea`, `richtext`, `hours_table`, `competence_picker`, `topic_plan_table`. |
| `x-required-for-status` | Поле обязательно только при переходе в указанный статус. Пример: подпись утверждающего обязательна только при переходе в `approved`. |

## 2.x.2. Маппинг: парсер → БД → шаблон

В системе три источника данных для документа:

1. **Парсер `DisciplineDataExtractor`** — автоматически извлекает структурированные данные из исходных файлов УП и компетенций.
2. **Справочные таблицы БД** — содержат загруженные парсером данные плюс справочники (пользователи, ФГОС, кафедры).
3. **Ручной ввод преподавателя** — методическое содержимое (цели, задачи, темы, литература).

Карта соответствия выхода парсера и сущностей БД:

| `SectionInfo.WayName` | `study_directions` | `name` |
| `SectionInfo.WaySection` | `study_profiles` | `name` |

## 2.x.5. Правила валидации (`x-validation-rule`)

Список именованных правил, реализованных в коде. Каждое правило получает на вход документ (и возможно — связанные сущности) и возвращает список ошибок.

| Правило | Проверка | Где применяется |
|---|---|---|
| `hours_match_curriculum` | Сумма часов по семестрам в документе совпадает с данными из `discipline_semester_details`. | `rpd.hours_distribution` |
| `topic_hours_match_total` | Сумма часов по разделам тематического плана совпадает с общим объёмом контактной работы. | `rpd.thematic_plan` |
| `all_indicators_covered` | Каждый индикатор из матрицы компетенций встречается хотя бы в одном разделе тематического плана. | `rpd.thematic_plan` |
| `linked_rpd_must_be_approved_or_under_review` | ФОС нельзя отправить на проверку, если связанный РПД — черновик или удалён. | `fos.linked_rpd` |
| `all_indicators_have_means` | Каждый индикатор из связанного РПД имеет хотя бы одно оценочное средство в ФОС. | `fos.evaluation_means` |
| `scale_matches_control_type` | Если в РПД `control_type = credit`, в ФОС шкала должна быть `pass_fail`. | `fos.evaluation_scale` |
| `unique_competence_codes` | Один и тот же код компетенции не встречается дважды на уровне документа. | Любой |
| `literature_main_count` | В основной литературе минимум N источников (N = настройка вуза). | `rpd.literature.main` |

Эти правила — это и есть кросс-документная валидация, которая отличает разрабатываемую систему от существующих аналогов (см. главу 1 и научную новизну в требованиях).

## 2.x.6. Жизненный цикл шаблона и документа на основе схемы

1. **Методист** загружает учебный план + список компетенций + матрицу через UI.
2. Парсер извлекает данные → `parser_runs` фиксирует результат → справочники БД заполняются (`curriculum_plans`, `disciplines`, `discipline_semester_details`, `competences`, `competence_matrix`).
3. **Методист** создаёт шаблон (`document_templates`), указывая тип (`rpd`/`fos`), привязку к УП, и редактирует JSON Schema (или выбирает базовую). Шаблон публикуется.
4. **Преподаватель** создаёт документ (`documents`) на основе шаблона. При создании система:
   - копирует `schema` из шаблона,
   - выполняет автозаполнение всех полей с `x-source`,
   - сохраняет результат в `documents.payload`.
5. Преподаватель редактирует поля, помеченные как редактируемые. Каждое сохранение валидируется по JSON Schema.
6. При отправке на проверку выполняется полная валидация — JSON Schema + все `x-validation-rule`. Если есть ошибки — переход блокируется.
7. Методист просматривает, оставляет комментарии (`document_comments` с `field_path` — JSON-pointer на поле в `payload`), возвращает или передаёт на согласование.
8. Утверждающий согласовывает → документ переходит в `approved`, поля становятся `readonly` (по `x-readonly-after`).
9. При генерации DOCX (FR-GEN-01) шаблонизатор обходит `payload` и подставляет значения в DOCX-шаблон, оформленный по стандартам МГТУ «СТАНКИН».

## 2.x.7. Преимущества подхода

1. **Расширяемость по типам документов** — добавление, скажем, программы практики сводится к: (а) написанию JSON Schema, (б) реализации специфичных правил валидации, (в) подготовке DOCX-шаблона. Изменения кода БД и API не требуются.
2. **Отделение методики от программирования** — JSON Schema может в перспективе редактировать методист. Это разгружает разработчика и снимает зависимость от него при изменении нормативной базы.
3. **Сквозная валидация на едином формате** — одни и те же правила работают на клиенте (Blazor), на сервере (API) и при импорте/экспорте.
4. **Прозрачное предзаполнение** — поле `x-source` явно фиксирует, откуда берётся значение, что упрощает отладку и аудит.

## Правки по сверке с реальными РПД и ФОС (июнь 2026)

Сверка с действующими документами МГТУ «СТАНКИН» (РПД и ФОС «Дискретная математика», 09.03.01, 2022) выявила уточнения к схемам. Полные JSON Schema подлежат доработке по этому списку; структурные изменения уже отражены в главе 2 (разделы 2.5.3–2.5.5).

**Новое расширение схемы:**
- `x-visible-if` — условие применимости раздела/поля по данным дисциплины. Примеры: раздел «Лабораторные работы» включается при наличии лабораторных часов в `discipline_semester_details`; раздел «Курсовая работа/проект» — при соответствующем виде промежуточной аттестации. Реализует вариативность состава разделов между дисциплинами без отдельных шаблонов.

**Структура РПД — добавить/уточнить:**
- Гриф «УТВЕРЖДАЮ» на титульном листе: у записи в `signatures_config` появляется признак размещения `placement: title | approval_sheet`.
- Раздел «Место дисциплины в структуре ОП»: пререквизиты (входные требования, текст) и постреквизиты (перечень дисциплин, использующих результаты; текст или мультивыбор из справочника `disciplines`).
- Блок «Знать / Уметь / Владеть» по дисциплине (ручной текст) — дополняет выбор индикаторов.
- Тематический план: у каждого раздела — формы текущего контроля (связь с мероприятиями ФОС).
- Условные разделы детализации занятий: практические, лабораторные, курсовая (через `x-visible-if`).
- «Учебно-методическое обеспечение» разворачивается в подразделы: литература, периодические издания, интернет-ресурсы (поле «дата обращения»), методические указания, ПО/базы данных/ИСС.
- Поля реквизитов протокола заседания кафедры (номер, дата) в листе согласования.
- Оглавление в схему не входит — строится генератором DOCX автоматически.

**Структура ФОС — добавить/уточнить:**
- «Паспорт ФОС»: две таблицы соответствия (разделы × компетенции × номера заданий; компетенция × индикатор × раздел РПД × номера заданий).
- Банк заданий: уровни сложности (A / B, C), сквозная нумерация; каждое задание имеет идентификатор, на который ссылается паспорт.
- Текущий контроль: формы аттестации, перечень мероприятий по модулям, программы и типовые варианты; модульно-рейтинговые атрибуты (баллы, недели) — текстом в MVP.

**Новые правила валидации (дополняют каталог из 8):**
- `fos_passport_consistent` — каждый номер задания в паспорте существует в банке; каждый индикатор привязан хотя бы к одному заданию.
- `control_forms_match` — формы текущего контроля из тематического плана РПД представлены мероприятиями в ФОС.

**Каталог `signatory_role` — дополнить:**
- `vice_rector_edu` — проректор по образовательной деятельности (титульный гриф РПД, согласование ФОС);
- `library_director` — директор научно-технической библиотеки;
- `it_directorate_director` — директор УИТП;
- `umk_chair` — председатель УМК по направлению (резолвер через направление подготовки документа);
- `graduate_department_head` — заведующий выпускающей кафедрой (резолвер: `study_directions.responsible_department_id` → `departments.head`); отличается от `department_head` кафедры-разработчика дисциплины.

**Содержимое полей (требования к редактору и генераторам):**
- В банке заданий и типовых вариантах встречаются таблицы и математическая нотация (матрицы весов, таблицы истинности, формулы). MVP: поддержка таблиц в rich-text-полях; формулы — линейной записью (текст/Unicode) либо вставкой изображения. Полноценный редактор формул (OMML/LaTeX) с генерацией в DOCX/PDF — перспектива.
- Опционально: справочник форм контроля (контрольная работа, опрос, тест, собеседование, …) для строгой кросс-валидации `control_forms_match`; в MVP допускается свободный текст с нестрогим сопоставлением.

## Правки по сверке № 2: РПД/ФОС «Программирование на ЯВУ» и шаблоны с закладками (июнь 2026)

Вторая сверка — с документами дисциплины полного состава (лабораторные + практические + курсовой проект, три семестра, зачёт и два экзамена) и с пустыми DOCX-шаблонами оформления, размеченными закладками.

**Банк заданий ФОС — именованные группы, а не фиксированные уровни.** В разных ФОС банк группируется по-разному: по уровням сложности (A / B, C — «Дискретная математика») либо по разделам дисциплины и видам аттестации с указанием семестра («вопросы к разделу 2», «вопросы к экзамену, 3 семестр» — «ПнаЯВУ»). Схема банка: произвольные именованные группы + сквозная нумерация внутри группы; ссылка паспорта — пара «группа, номер». Правило `fos_passport_consistent` проверяет существование пары. Многосеместровые дисциплины с несколькими видами контроля поддерживаются группами per-семестр.

**Экзаменационные билеты — опциональный раздел ФОС.** Нумерованные билеты (2–3 вопроса) с шапкой (дисциплина, курс, направление) и подписью заведующего кафедрой на каждом. В схеме — повторяющийся блок; генератор печатает билеты с шапкой и подписью. Перспектива: полуавтоматическая компоновка билетов из вопросов банка.

**Шкала оценивания / рейтинг — вариативный раздел.** В одних ФОС есть модульно-рейтинговая схема (баллы, недели), в других отсутствует. Раздел опционален.

**Заглушки «не предусмотрено».** Практика института: отключённый раздел в печатной форме не удаляется, а получает стандартную формулировку («В учебном плане курсовое проектирование для данной дисциплины не предусмотрено»). Следствие: `x-visible-if` управляет видимостью в редакторе; для генерации у раздела появляется атрибут текста-заглушки (например, `x-stub-text`), вставляемого при отключённом разделе.

**Методические указания — условные подразделы.** Дробятся по видам занятий (к лабораторным, к практическим, к курсовому проектированию) и включаются вместе с соответствующими видами занятий.

**Несколько составителей документа.** У реальных РПД/ФОС два и более исполнителей. Дополнение к структуре данных: связь «документ — исполнители» (`document_executors`: document_id, user_id, порядок) или JSONB-поле; `author` остаётся владельцем записи и единственным редактором в MVP. Требуется отразить в ER-диаграмме и разделе 2.4.

**DOCX-шаблон оформления — артефакт шаблона документа.** Ссылка `document_templates.print_template_file_id` → `uploaded_files`. При публикации шаблона валидируется согласованность: каждая закладка `Autofill*` DOCX-шаблона сопоставлена полю схемы; несопоставленные закладки — ошибка публикации (расширение финальной проверки FR-TPL-11). Маппинг «закладка → поле» хранится как данные шаблона, а не выводится из имени жёстко (в действующих шаблонах есть несогласованности: `Kurs`/`Curs`, `EducationLevel`/`EducationLvl`, разрывы нумерации).

**Каталог закладок** действующих шаблонов (52 для РПД, 46 для ФОС) с маппингом «закладка → поле схемы → источник» — в файле `ВКР_2_Карта_закладок_DOCX.md` (материал приложения и прямой вход для генератора, задача Т-301). Конвенция: `Autofill<Поле><N>`, одно значение подставляется во все одноимённые закладки (fan-out).

**Уточнение каталога `signatory_role`:** должность «начальник УИТП» (не «директор») — код `it_directorate_head`; начальник УМУ — `umu_head`.
