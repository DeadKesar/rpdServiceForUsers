## Этап 0. Ходячий скелет — веха `v0.1` (18.10.2026)

Коммиты: `8bf225f` (каркас), `6541135` (решение, пакеты, первая миграция). Runbook — [Этап0_ходячий_скелет.md](runbooks/Этап0_ходячий_скелет.md).

**Что сделано**
- Два проекта: прикладное ядро `RpdFos.Core` (сущности, `AppDbContext`, миграции, сквозные механизмы) и хост `RpdFos.Api` (модули Carter).
- PostgreSQL 17 поднимается одной командой (`docker-compose.yml`); EF Core с соглашением snake_case.
- Первая миграция `Initial` — таблица `document_templates`.
- Сквозные механизмы: `VersioningInterceptor` (номер версии и время изменения) и `ConcurrencyExceptionHandler` (конфликт версий → 409 в формате ProblemDetails).
- Описание API — встроенный `Microsoft.AspNetCore.OpenApi`, страница — Swagger UI; проверка `/health`.
- Два вертикальных среза: создание шаблона и его публикация (образец «смена статуса + проверка версии»).
- Тесты: дымовой тест `/health` и шесть случаев правила публикации — 7 зелёных.

**Ключевые решения**
- **Ходячий скелет:** сначала тончайший сквозной путь запрос → API → БД → ответ, функциональность — потом. Стыковые риски (фреймворки, миграции, конфигурация) проявляются в первые дни, когда исправление дёшево.
- **Порядок по риску:** следующим этапом — самое рискованное, связка Blazor и сервера аутентификации.
- **Отдельное прикладное ядро:** на этапе 2 его подключит фоновый обработчик, и миграции не придётся переносить.
- **Версия ведётся перехватчиком сохранения**, а не кодом эндпоинтов; ошибки обрабатываются в одном месте, без `try/catch` в эндпоинтах.
- **Swagger UI вместо Scalar**; схема БД — только миграциями; тесты и мелкие коммиты — с первого дня, тег на каждую веху.

**Проблемы и решения**
- Версии пакетов в скелете были ориентировочными → подняты до последних стабильных (Carter 10.0.0, пакеты ASP.NET Core и EF Core 10.0.13, Npgsql 10.0.3, EFCore.NamingConventions 10.0.1), добавлена явная ссылка на `Microsoft.EntityFrameworkCore.Relational` 10.0.13.
- SDK .NET 10 создаёт решение в новом формате → в репозитории `RpdFos.slnx` вместо `.sln` из runbook.

## Этап 1. Аутентификация — веха `v0.2` (18.10.2026)

Коммит: `9502b0d`; доработки после вехи — `chore: stage 1 cleanup`. Runbook — [Этап1_аутентификация.md](runbooks/Этап1_аутентификация.md).

**Что сделано**
- Учётные записи — ASP.NET Core Identity в той же базе (`AppUser` с ФИО), четыре роли: `teacher`, `methodist`, `approver`, `admin`. Миграция `AddIdentity` — таблицы Identity и OpenIddict.
- Сервер авторизации OpenIddict внутри хоста API: конечные точки authorize, token, logout; страница входа на русском (Razor Pages); токены проверяет тот же хост.
- Политики доступа: чтение шаблонов — любой вошедший, изменение — методист и администратор; `POST /api/admin/users` — только администратор, самостоятельной регистрации нет.
- Начальные данные (`AuthSeed`): роли, клиент OIDC `rpdfos-web`, первый администратор из user-secrets.
- Веб-клиент Blazor WebAssembly (`RpdFos.Web`) раздаётся тем же хостом; страницы «Шаблоны» (с проверкой ролей) и «Пользователи».
- Тесты: API закрыт без токена (401), сервер публикует документ discovery — всего 9 зелёных.

**Ключевые решения**
- **OpenIddict (Apache 2.0) внутри хоста API вместо Duende IdentityServer в отдельном контейнере** (как в проекте, глава 2). Причина — лицензия: риск 9 снят, OpenID Connect сохранён, отдельного контейнера нет. Тексты глав 2 и 3 нужно поправить под это решение.
- **Поток authorization code + PKCE**, публичный клиент без экрана согласия: клиент свой. Основа — официальный пример OpenIddict «Balosar».
- **Один адрес для API и клиента** — CORS больше не нужен, его настройка удалена.
- **Токены хранятся в браузере (sessionStorage)** — осознанное упрощение прототипа. Защита — санитизация форматированного текста (этап 4) и короткоживущие токены; BFF (пример OpenIddict «Dantooine») — перспектива.
- **У пользователя одна роль** — ограничение прототипа: клиентская библиотека Blazor без доработки не разбирает массив ролей.
- **Таблицы Identity и OpenIddict сохраняют имена библиотек** (`AspNetUsers`, `OpenIddict*`) — их задают сами библиотеки, соглашение snake_case меняет только колонки.

**Проблемы и решения**
- *OpenIddict принимает только HTTPS.* Для разработки — доверенный сертификат (`dotnet dev-certs https --trust`) и профиль `https://localhost:5081`; тест discovery обращается к хосту по https.
- *NuGetAudit: уязвимые транзитивные зависимости.* `OpenIddict.AspNetCore` 7.7.2 тянет в тестовый проект `System.Security.Cryptography.Xml` и `.Pkcs` 10.0.11 с известными уязвимостями (NU1902/NU1903) → явные ссылки на исправленные 10.0.13.
- *Остатки шаблона `blazorwasm -au Individual`:* демонстрационные страницы Counter и Weather, `sample-data`, `wwwroot/appsettings*.json` с заглушкой Microsoft Entra ID, отдельный профиль запуска клиента, английский интерфейс; пакеты клиента 10.0.12 при 10.0.13 в остальных проектах → удалено, интерфейс переведён на русский, версии выровнены (cleanup).
- *Вместе с профилем клиента по ошибке удалён профиль API* — без него хост стартует не в Development и не по HTTPS → профиль API восстановлен; в CLAUDE.md записан запрет на его удаление (cleanup).
- *Клиент OIDC создаётся один раз:* после смены адреса хоста вход падал с ошибкой `redirect_uri`, а runbook предлагал удалять клиента из базы вручную → `AuthSeed` при каждом запуске сверяет адреса возврата с `Auth:PublicUrl` и обновляет их (cleanup).
- *Учётная запись могла остаться без роли*, если назначение роли не удалось → результат проверяется, созданная запись удаляется, ответ — `ValidationProblem` (cleanup).

## Этап 2. Парсер и справочники — веха `v0.3` (18.10.2026)

Задание — [etap-2.md](tasks/etap-2.md). Коммиты: `87ac463`, `28fb925` (часть A — закрытие этапа 1), `e29fc14` (B1), `2d7b6b1` (B2), `6aeeeac` (B3), `3afd99a` (B4), `514fd8f` (B4.1), `39f69a5` (B5), `a0fc028` (B6), `6c5139b` (B7), `a0985e0` (исправление тестов фоновых задач).

**Итог вехи.** Методист загружает четыре исходных файла на странице «Импорт данных»; разбор и импорт идут в фоне (Hangfire, очередь `parsing`), справочники заполняются; ошибки разбора видны с файлом, листом (таблицей) и строкой; повторная загрузка тех же файлов общие справочники не дублирует и создаёт новую версию плана. Тесты: 23 — парсер на реальных файлах, 31 — API и ядро с базой в контейнере (импорт, механика версий, 409, роли, учётные записи, фоновые задачи, API импорта); сборка и тесты — без предупреждений. Страница импорта в браузере вручную не проверялась — сквозной путь проверен тестом API от загрузки файлов до завершения фоновой задачи.

**Что сделано**
- **B1.** Интеграционные тесты с базой: PostgreSQL 17 в контейнере (Testcontainers) + `WebApplicationFactory`, миграции при старте. Проверено: публикация увеличивает версию, устаревшая версия → 409, преподаватель → 403, методист → 201, без входа → 401. Аутентификация в тестах — тестовая схема, которой схема OpenIddict передаёт проверку (`ForwardDefault`); рабочие политики не менялись. Фикстура проверяет, что тесты подключены к контейнеру, а не к базе разработки.
- **B2.** Библиотека `DisciplineDataExtractor` (без зависимостей от `RpdFos.*`): учебный план (.xlsx), список и матрица компетенций (.docx), должности (.xlsx) → типизированный результат. ClosedXML и DocumentFormat.OpenXml, без NPOI. Статического состояния нет: читатели и журнал замечаний создаются на каждый разбор. Ошибки — списком `{файл, лист или таблица, строка, сообщение}`, частичный результат допустим. 23 теста на реальных файлах.
- Разбор реальных файлов 09.04.04 (2023): 46 строк плана (из них 1 модуль, 3 группы элективов и 12 элективов), 52 записи по семестрам, 17 компетенций, 57 индикаторов, 97 связей матрицы, 37 сотрудников; 1 ошибка, 7 предупреждений.
- **B3.** Модель справочников и миграция `AddReference` по `docs/design` (с отступлениями ниже): оргструктура, направления и профили, ФГОС, компетенции и индикаторы, учебные планы, дисциплины, детали по семестрам, матрица; справочник сотрудников `users`; `uploaded_files`, `parser_runs`. Ограничения целостности `users` (вход, категория подписанта) — как в проекте.
- **B4.** Конвейер импорта `ReferenceImporter` в ядре: результат разбора → справочники в одной транзакции. После импорта реальных файлов: институтов 4, кафедр 30, направлений 1, профилей 1, ФГОС 1, компетенций 17, индикаторов 57, сотрудников 37, планов 1, дисциплин 46, деталей по семестрам 52, связей матрицы 97. Повторная загрузка тех же файлов общие справочники не меняет и создаёт план версии 2.
- **B4.1.** Уточнения модели (ниже): смена человека на должности, ПК на профиль, связь учётной записи со справочником сотрудников.
- **B5.** Hangfire в хосте API: хранилище — та же PostgreSQL, схема `hangfire`; очередь `parsing` с одним исполнителем; задача `ImportJob` (ядро): файлы из `uploaded_files` → разбор → конвейер импорта; панель `/hangfire` — только администратору.
- **B6.** Модуль API `Imports`: `POST /api/imports` (multipart, методист и администратор; расширение, размер, один файл в двух полях; 202 и id запуска), `GET /api/imports/{id}` (статус, счётчики, замечания), `GET /api/imports` (последние запуски).
- **B7.** Страница клиента «Импорт данных»: выбор файлов, отправка, опрос статуса, сводка и таблица замечаний, последние запуски.

**Ключевые решения**
- **Колонки плана — по заголовкам**, а не по буквам: заголовок колонки, группа над ним («Семестр N», «Форма контроля», «Закрепленная кафедра») и границы групп по объединённым ячейкам. В разных выгрузках plx колонки сдвигаются.
- **Индекс дисциплины — по сегментам** (`Б1.О.01`, `Б1.В.ДВ.01.02`, `Б2.О.03(П)`, `ФТД.В.01`): отсюда блок, часть, родитель (ближайший индекс-префикс) и вид элемента.
- **Матрица сопоставляется с планом по названиям** — индексов в матрице нет. Ключ названия без регистра, «ё», пунктуации, дефисов и скобок; затем — совпадение набора слов с предупреждением; при нескольких кандидатах — уточнение по семестрам. Остальное — замечание: строка с потерянными связями — ошибка, без отметок — предупреждение. Ручную привязку не делаем (перспектива — в [ideas.md](tasks/ideas.md)).
- **Импорт: план — новой версией, справочники — по естественным ключам.** Институт и кафедра — по названию (оно согласовано между планом и файлом должностей), направление — по коду, профиль — по направлению и названию, ФГОС — по направлению, номеру и дате приказа, компетенция — по ФГОС и коду, индикатор — по компетенции и коду, сотрудник — по «Офиц. названию» строки файла должностей среди активных записей (место подписанта; смена человека — см. уточнения B4.1). Итог в `parser_runs`: `succeeded` — без ошибок, `partial` — план загружен, но есть ошибки, `failed` — план не создан, справочники не тронуты (откат транзакции).
- **Кафедры — только из справочника кафедр плана:** у кафедр из файла должностей нет номера, на который ссылаются дисциплины. Сотрудник такой кафедры загружается без кафедры и без категории подписанта — с предупреждением.
- **Категория подписанта — по должности:** кодов категорий в файле нет, поэтому — по ключевым словам с границами слов («заведующий» → `department_head`, «И.О. заведующего» → `department_head_acting`, «директор» строки института → `institute_director`, «ректор», «проректор», «УМУ», библиотека, УИТП). Категория назначается, только если согласуется с оргструктурой (ограничение `ck_users_signatory_scope`).
- **Подпись в документах** (`name_for_document`, по проекту «И. О. Фамилия») получается перестановкой из `short_name` («Фамилия И. О.»).
- **Фоновые задачи — без повторов:** автоматический повтор Hangfire отключён — импорт сам пишет итог в `parser_runs`, включая `failed`; повторная задача для завершённого запуска ничего не делает. Ядро от Hangfire не зависит: очередь и запуск задаёт хост.
- **Панель задач — по cookie страницы входа:** панель открывают переходом по адресу, без токена доступа, поэтому политика `jobs-dashboard` проверяет роль администратора по cookie входа (`IdentityConstants.ApplicationScheme`).
- **Загрузка файлов:** загрузивший — запись справочника текущего пользователя (по `sub`), без неё — 403. Файл с тем же `checksum` и типом, загруженный раньше, переиспользуется (содержимое не дублируется), но новый запуск создаётся: повторная загрузка — это новая версия плана. Один и тот же файл в двух полях формы — 422. Файл должностей — необязательный, как в проекте (`employees_file_id NULL`).
- **Фикстуры обезличены:** колонка «ФИО» в должностях и ФИО подписантов на листе «Титул» плана (правило CLAUDE.md о персональных данных — строже формулировки задания). Разбор копий совпадает с разбором оригиналов.

**Отступления от модели данных (согласованы для B3)**
- `discipline_semester_details.control_type` → `control_types text[] NOT NULL DEFAULT '{}'` с кодами `exam`, `credit`, `graded_credit`, `course_project`, `course_work`: в семестре бывает несколько видов аттестации (экзамен и курсовой проект).
- `fgos.version` — необязательное, заполняется вручную: в содержимом исходных файлов версии стандарта нет. Естественный ключ ФГОС — направление, номер и дата приказа.
- `users`: `short_name` («Фамилия И. О.», из файла должностей) — обязательное; `full_name` — необязательное (в файле только фамилия с инициалами), заполняется вручную или из учётной записи.

**Уточнения модели (шаг B4.1, миграция `RefineReference`)**
- **Смена человека на должности.** Ключ сотрудника — официальное название среди *активных* записей. Тот же человек (`short_name` совпадает) — строка обновляется; другой — прежняя строка получает `is_active = false`, создаётся новая. Причина: `document_signatures.resolved_user_id` ссылается на `users.id`, перезапись строки переписала бы историю согласований. Частичные уникальные индексы `users` (`official_designation`; `signatory_role` + `department_id`; `signatory_role` + `institute_id`) — только для активных записей. Прежняя строка деактивируется отдельным сохранением до вставки новой: EF не знает об условии индекса и мог бы вставить новую строку раньше.
- **ПК привязаны к профилю.** `competences.profile_id`: NULL для УК и ОПК (их задаёт ФГОС), профиль — для ПК (их задаёт образовательная программа). Уникальность — `(fgos_id, code) WHERE profile_id IS NULL` и `(profile_id, code) WHERE profile_id IS NOT NULL`. Без этого импорт второго профиля того же направления перезаписал бы ПК первого. *Ограничение прототипа:* ПК — на профиль, а не на год набора: если ПК профиля меняются от набора к набору, последняя загрузка перепишет формулировки.
- **Учётная запись ↔ справочник.** При создании учётной записи (`UsersModule` и засев первого администратора) создаётся запись `users` с `can_login = true` и `identity_subject` = id учётной записи; `short_name` и `name_for_document` вычисляются из ФИО («Петров Пётр Петрович» → «Петров П. П.», «П. П. Петров»). Необязательный `directoryUserId` привязывает учётную запись к существующей записи справочника (например, из файла должностей) вместо создания новой; ФИО полностью тогда берётся из учётной записи. Учётная запись, роль и запись справочника создаются в одной транзакции — это заменило удаление учётной записи при ошибке назначения роли (шаг A3). Засев связывает и администратора, созданного на этапе 1. В ядре — `DirectoryAccounts.FindIdAsync`: id записи справочника текущего пользователя по утверждению `sub` (для `uploaded_by`, `started_by` и дальше).

**Проблемы и решения**
- *Ошибка генератора-предшественника — сдвиг колонок часов.* В `Models/Helpers.cs` (`GetDisciplines`) часы дисциплины с листа «План» читались со сдвигом на одну колонку: лекции — из колонки «Лаб», лабораторные — из «Пр», практические — из «СР» (первое вхождение заголовка на листе, то есть колонки первого семестра). Часы по семестрам предшественник брал с листов «Курс», где сдвига нет. В новой библиотеке колонки ищутся по заголовку внутри группы семестра, тесты сверяют часы конкретных дисциплин с файлом.
- *Заголовок «ФТД.Факультативы» начинается как индекс* и принимался за дисциплину → индекс проверяется по сегментам.

ProblemDetails — контракт API: русский текст получает любой клиент, а сервер знает, *что* не найдено или почему отказано. `ProblemTitles` (`CustomizeProblemDetails`) заменяет стандартные английские заголовки («Not Found», «Bad Request», «Forbidden», ошибка сервера и др.) русскими с пояснением — в том числе в ответах без тела (`UseStatusCodePages`) и при необработанных исключениях; заголовки, заданные эндпоинтом, не трогаются. **B2. Модель документов (миграция `AddDocuments`)**

Отступления: **`template_revision`** вместо `template_version` (по аналогии с `revision` шаблона, задание этапа); оптимистичная блокировка — `version` через `IVersioned` вместо `current_version`. `search_vector` (поиск, FR-SEA-01) — не на этом этапе.
- `document_versions` (снимки `payload`, часов и компетенций; `trigger_event`: `auto_save`, `manual_save`, `status_change`, `approved`), `document_hours` (часы по семестрам, неотрицательные), `document_competence_links` (компетенция и/или индикатор; уникальность с `NULLS NOT DISTINCT` — иначе пара «компетенция без индикатора» могла бы повториться), `document_status_history`.
- **Синхронизация нормализованных таблиц** — `DocumentProjections` (ядро) пересобирает часы и привязки по `payload` в том же `SaveChanges`, то есть в той же транзакции. Часы обновляются на месте по семестру, привязки — разницей множеств: удаление и вставка одной строки в одном сохранении столкнулись бы на уникальном индексе. Коды компетенций и индикаторов переводятся в id по матрице компетенций дисциплины; выбранный индикатор даёт строку «компетенция + индикатор», компетенция без выбранных индикаторов — «компетенция»; кода нет в матрице — привязки нет (расхождение проверит правило этапа 5).

**B3. Создание документа и предзаполнение**
- `POST /api/documents` (`templateId`, `disciplineId`) — преподаватель, методист, администратор (политика `document-authors`); автор — запись справочника текущего пользователя, без неё — 403. Проверки — в ядре (`DocumentCreation`): шаблон опубликован и это РПД (ФОС — этап 6), дисциплина из плана шаблона, это настоящая дисциплина (FR-DOC-18), документа по этой дисциплине и линии редакций шаблона ещё нет — иначе 409 со ссылкой на существующий (`documentId`, `location`). Остальные отказы — 422 с причиной.
- **Настоящая дисциплина** — вид строки «дисциплина» или «факультатив», но не группа дисциплин по выбору: в разобранном плане у группы элективов (`Б1.В.ДВ.01`) тот же вид строки, что у дисциплины, — отличает часть плана `elective_group`. Модули, практики (Б2) и ГИА (Б3) — 422.
- **Предзаполнение** (`DocumentPrefill`) — по `x-source` снимка схемы шаблона. Значения кодов плана — по-русски в именительном падеже: «Блок 1 «Дисциплины (модули)»», «Обязательная часть», «Магистратура», «очная» (`PlanTitles`; другие падежи — словарём этапа 5). Компетенции матрицы — с пустым выбором индикаторов, кандидаты с индикаторами — в метаданных. Первый составитель — автор.
- **Дополнения схемы РПД** (по составу предзаполнения из задания): в «Место в структуре» — индекс, блок и часть (источник `parser.discipline.block` добавлен в каталог); в трудоёмкости — общее число часов; `x-source` трудоёмкости перенесён с объекта на список семестров; учебный год начала изучения — из года набора и первого семестра (`reference.curriculum_plan.academic_year`, редактируемый). Поля из плана — названия, коды, часы, ЗЕТ, виды аттестации — помечены стандартным `readOnly: true` (целиком раздел трудоёмкости).
- **Метаданные** (`DocumentMetadata`) вместе с документом: разделы — видимость по данным дисциплины (`x-visible-if`, FR-TPL-14: лабораторные и практические — по часам, курсовой — по видам аттестации), заглушка скрытого раздела, заполненность по обязательным полям режима отправки (`complete`, `incomplete`, `not_applicable`) и чего не хватает; поля только для чтения при текущем статусе (`readOnly` — всегда, `x-readonly-after` — после указанного статуса); кандидаты в компетенции.
- Документы создаются по снимку схемы шаблона: шаблоны, опубликованные до этих изменений, хранят прежнюю схему (с подписями в листе согласования), и новая редакция её копирует. Для документов по новой схеме нужен новый шаблон.

*Согласовано по сводке B3:* видимые условные разделы (лабораторные, практические, курсовой проект) обязательны при отправке — хотя бы одна запись (у раздела-объекта — заполненное поле); скрытые не проверяются. Проверка к отправке — `DocumentSubmission` (схема в режиме отправки + условные разделы по данным дисциплины), по ней же считается заполненность разделов. Шаблоны базы разработки со старой схемой не переносятся — автор создаёт новый шаблон РПД.

**B4. Редактирование и сохранение — API**
- `GET /api/documents?status=&planId=` — преподаватель видит свои документы (FR-DOC-08), методист и администратор — все; `GET /api/documents/{id}` — содержимое, схема из шаблона и метаданные; чужой документ преподавателю — 403. `GET /api/documents/disciplines?templateId=` — для экрана создания: только дисциплины, для которых создаётся документ, и уже созданные по линии шаблона (ссылка — если документ доступен пользователю).
- `PATCH /api/documents/{id}/sections/{section}` (значение раздела и версия клиента) — `DocumentEditing` в ядре: раздел есть в схеме (иначе 404) и предусмотрен планом (иначе 422); форматированный текст (`x-ui-widget: richtext`) — через санитайзер; поля «только для чтения» (`readOnly` и закрытые `x-readonly-after`) должны совпасть с тем, что уже в документе, — иначе 422 с полями; весь `payload` проверяется в режиме черновика — иначе 422 с ошибками `{path, message}`. Нормализованные таблицы, рабочий снимок и запись истории — в том же сохранении. Ответ — новая версия, статус и заполненность раздела; устаревшая версия — 409.
- Правка сохранённого черновика возвращает `draft` с записью в истории. Рабочий снимок (`auto_save`) перезаписывается автосохранениями; `POST …/save` — `saved_draft` и новый снимок `manual_save` с часами и привязками к компетенциям. `DELETE …?version=` — автор, только `draft` и `saved_draft`, мягко. Изменяет и удаляет документ только автор; правила статусов — `DocumentTransitions`, переходы — методами сущности.

**B5. Признак «устарел» (FR-DOC-12)** — `TemplateLifecycle.PublishAsync`: после публикации новой редакции неудалённые документы всех прежних редакций линии получают `is_outdated = true` одним `UPDATE` в той же транзакции, что архивирование прежней редакции и публикация. Версию документа признак не меняет: он ортогонален содержимому, и автосохранение в открытом редакторе не должно упасть с конфликтом версий из-за публикации шаблона.
- *Проблема:* первый вариант исключал из подзапроса удалённые шаблоны через `IgnoreQueryFilters()` — и удалённые документы тоже стали устаревшими: EF снимает глобальные фильтры со всего запроса, а не с подзапроса. Поймал тест; фильтр удалённых документов теперь и явный.

**B6. Клиент**

*Архитектурное решение: форма по схеме с реестром виджетов.* Редактор не знает разделов РПД — форму раздела он строит по снимку схемы шаблона, который приходит вместе с документом.
- Универсальный обработчик (`Forms/SchemaField`, `ScalarInput`) рисует по типу и подсказкам схемы строки, многострочные тексты, числа, даты, перечисления (с русскими названиями из `x-enum-titles`), флажки, объекты — вложенные поля в порядке `properties` — и списки.
- Особые поля получают виджет из реестра (`Forms/WidgetRegistry`) по `x-ui-widget`: `richtext` — форматированный текст, `list` — список строк, `hours_table` — трудоёмкость, `topic_plan_table` — тематический план с итогами против плана, `competence_picker` — компетенции и индикаторы, `class_table` и `literature_list` — таблицы записей. Список без подсказки — список строк или таблица записей, по типу элементов.
- Обработчик и виджеты наследуют `FieldBase` с одними параметрами: контекст документа, подсхема, контейнер и ключ значения, путь. Новый виджет — компонент и строка в реестре; обработчик не меняется.
- Подписи полей — `title` схемы, локальные `$ref` разрешает контекст формы, поля «только для чтения» и скрытые — по метаданным сервера.

Так подтверждается тезис главы 2: новый тип документа, которому хватает существующих виджетов, не требует нового кода интерфейса — достаточно схемы шаблона.

- **«Мои документы» (S-10):** дисциплина, тип, статус по-русски, дата изменения, автор, метка «устарел»; фильтры по статусу и учебному плану.
- **Создание (S-11):** опубликованный шаблон РПД, затем дисциплина его плана; дисциплины, по которым документ уже создан, — со ссылкой на него.
- **Редактор (S-12):**
  - слева — разделы с отметкой заполненности (заполнен; не хватает обязательного — с перечнем; не предусмотрен планом — с заглушкой вместо формы);
  - поля из учебного плана — только для чтения, с пометкой «из учебного плана»;
  - автосохранение раз в 4 минуты и при уходе из раздела, «Сохранено в ЧЧ:ММ»; «Сохранить» и «Сохранить и выйти»; уход со страницы с несохранённым требует подтверждения (`NavigationLock`);
  - чужой документ или документ не в работе открывается только для просмотра.
- **Конфликт версий (409):** сообщение «Документ изменён в другой сессии». Введённое остаётся на экране, автосохранение и сохранение остановлены до решения пользователя: «Перезагрузить документ» или «Скопировать мой текст» (текст полей открытого раздела — в буфер обмена и в поле под кнопкой).
- **Форматированный текст** — `RadzenHtmlEditor` из Radzen.Blazor 12.0.8 (MIT): только полужирный, курсив и списки. Подключена тема без базовых стилей страницы (`default-base.css`) — оформление приложения остаётся на Bootstrap. Разметку всё равно чистит сервер.

**B7. Тесты** — по списку задания:
- ядро: предзаполнение реальной дисциплины из фикстур (часы, ЗЕТ, виды аттестации), видимость условных разделов, валидатор в двух режимах, санитайзер — в том числе разметка редактора из браузера;
- API: создание (допустимая дисциплина; модуль, практика, ГИА — 422; дубль — 409), доступ к чужим документам, сохранение раздела и рост версии, устаревшая версия — 409, поле «только для чтения» — 422, очистка вредной разметки, ручное сохранение и снимок, `is_outdated` при новой редакции шаблона, порядок разделов и полей в снимке схемы.

**Исправление: порядок разделов и полей (jsonb → json).**
- *Проблема.* При проверке в браузере разделы редактора и столбцы таблиц шли не в порядке схемы. Снимок схемы шаблона хранился в `jsonb`, а `jsonb` хранит ключи объекта в своём порядке (короче — раньше, затем по байтам). Порядок `properties` терялся, а по нему редактор строит разделы и поля.
- *Решение* — тип `json` (текст как есть) для снимка схемы, миграция `TemplateSchemaJson`.
  - `signatures_config` — массив мест согласования: порядок элементов массива `jsonb` сохраняет, порядок ключей внутри места не важен. Остаётся `jsonb`, как и `print_mapping`.
  - `payload` остаётся `jsonb`: порядок ключей содержимого не значим, а по нему нужны индекс GIN и поиск.
- *Тест:* снимок после записи и чтения новым контекстом сохраняет порядок разделов, полей титула и столбцов `class_item` как в `rpd.schema.json`; разделы в метаданных документа идут в порядке схемы. Шаблон и документ проверки в базе разработки созданы заново.

**Проверка в браузере** (преподаватель, база разработки, РПД по дисциплине Б1.О.10):
- разделы — в порядке схемы; титул и трудоёмкость — только для чтения с пометкой «из учебного плана»; учебный год редактируется;
- форматированный текст с полужирным, курсивом и списком сохранён очищенным (`strong`, `em`, `ul`/`li`); цели — списком;
- уход из раздела — автосохранение, сохранённый черновик вернулся в черновик с записью в истории;
- выбраны компетенции и индикаторы — привязки появились в `document_competence_links`;
- тематический план: часы, индикаторы из выбранных, итоги против плана пересчитываются при вводе;
- конфликт из второй вкладки: сообщение, введённое на месте, автосохранение и сохранение отключены, копия текста, перезагрузка;
- «Сохранить и выйти» → «Мои документы», статус «Сохранённый черновик»; в базе — снимки `auto_save` и `manual_save` и история переходов.

**Проблемы и решения** (найдены при проверке в браузере)
- *Порядок разделов и полей* — см. выше.
- *Форматирование из редактора пропадало.* Radzen оформляет полужирный и курсив не тегами, а `span` со стилями `font-weight` и `font-style` (иногда в обёртке `div`). Санитайзер снимал стили вместе с форматированием — молча. Теперь перед очисткой стили полужирного и курсива переводятся в `strong` и `em` (AngleSharp), остальное очищается как раньше. Тесты — на разметке, пришедшей из браузера.
- *Итоги тематического плана показывали 0.* Введённое в форме целое клиент хранил как `long`, а итоги читали `int` — значение не читалось. Целые поля хранят `int`, виджеты читают числа через текст — одинаково для пришедших с сервера и введённых.
- *Пометка «из учебного плана» стояла у редактируемого учебного года* — теперь она только у полей «только для чтения».

**Итог.** Преподаватель создаёт РПД по опубликованному шаблону для дисциплины плана. Титул, место в структуре, трудоёмкость и компетенции заполнены из плана и матрицы, поля плана не редактируются; разделы лабораторных, практических и курсового проекта видны только по плану. Форма строится по схеме шаблона: универсальный обработчик и шесть виджетов из реестра. Документ сохраняется автоматически и вручную; снимки версий, часы и привязки к компетенциям пишутся в той же транзакции. Конфликт версий ловится без потери введённого; документы прежних редакций шаблона помечаются «устарел». Тестов — 191 (25 + 166), сборка без предупреждений.

## Этап 5. Проверка и печать — веха `v0.6` (в работе)

Задание — [etap-5.md](tasks/etap-5.md).

**После вехи `v0.5`: потеря ввода при уходе со страницы** (нашёл автор при проверке). Признак несохранённых правок ставился по событию `change`, то есть при уходе из поля. Текст, набранный в поле без ухода из него, пропадал без предупреждения при закрытии вкладки или переходе на другой сайт: `NavigationLock` спрашивает подтверждение, только когда признак уже стоит.
- Поля и виджеты обрабатывают `oninput`, форматированный текст — событие `Input` редактора Radzen. Значение сразу пишется в содержимое, признак ставится тут же. Пробелы по краям обрезаются при уходе из поля, как раньше. Недонабранное число («-», «1.») в содержимое не пишется — только отмечается правка, иначе перерисовка стёрла бы набранное.
- Страница перерисовывается при первой правке, а не на каждую клавишу. Автосохранение во время набора сохраняет то, что на экране. Правки, сделанные за время запроса сохранения, признак не снимают: введён счётчик правок.
- *Проверка:* встроенный браузер среды разработки сам разрешает уход со страницы и закрывает вкладки без событий выгрузки, поэтому проверялся обработчик `beforeunload` во время настоящего перехода на другой сайт: при фокусе в поле с набранным текстом он запросил подтверждение. Закрытие вкладки проверил автор в своём браузере — появляется предупреждение о возможной потере данных. Отдельно: автосохранение по таймеру при фокусе в редакторе форматированного текста сохранило набранное.
