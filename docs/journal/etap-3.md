## Этап 3. Шаблоны — веха `v0.4`

Задание — [etap-3.md](../tasks/etap-3.md).

**Часть A. Доработки этапа 2**
- **A1. Место подписанта отдельно от человека** (уточнение модели B4.1). Раньше при смене человека на должности прежняя запись справочника деактивировалась целиком; если за ней стояла учётная запись, человек терял доступ — бывший заведующий, оставшийся преподавателем, получал 403. Теперь смена человека снимает с прежней записи только место — `official_designation` и `signatory_role`; запись без учётной записи (`identity_subject IS NULL`) дополнительно получает `is_active = false`, запись с учётной записью остаётся активной. История согласований не страдает: роль хранится в `document_signatures.role`, ссылка ведёт на того же человека.
- **A2. Привязка к справочнику в интерфейсе.** `GET /api/admin/users` — учётные записи с ролью и связанной записью справочника; `GET /api/admin/directory?surname=` — поиск по началу фамилии (без учёта регистра) среди активных записей без учётной записи. Страница «Пользователи»: список учётных записей и необязательный выбор записи справочника при создании → `directoryUserId`. Так заведующие и директора из файла должностей войдут «самими собой» на этапе 6 (согласование), а не новыми записями справочника.

**Часть B. Типы документов и сопоставление закладок (B1–B3)**
- **Структуры типов — файлами в ядре** (`DocumentTypes/*.json`, встроенные ресурсы): JSON Schema 2020-12 РПД и ФОС с x-расширениями, сопоставление закладок по умолчанию, лист согласования по умолчанию; `DocumentTypeRegistry` — один экземпляр на приложение. Титул и лист согласования ФОС — `$ref` на схему РПД. Порядок шагов — B1 → B3 → B2: тесту сопоставления нужен читатель закладок.
- **Чтение закладок** — Open XML SDK (`DocumentFormat.OpenXml` 3.5.1, MIT): все `BookmarkStart` с префиксом `Autofill` в теле, колонтитулах и сносках, числовой суффикс любой длины отбрасывается. Реальные шаблоны: 52 вхождения / 35 базовых имён в РПД, 46 / 24 в ФОС — совпадает с каталогом. Тест сопоставления проверяет совпадение в обе стороны: каждая закладка сопоставлена, лишних ключей нет.
- **Валидатор JSON Schema в тестах** — JsonSchema.Net 8.0.5, последняя версия под MIT: с 9.x пакет распространяется по OSMF EULA. Выбор валидатора для рабочего кода (этап 4) — в [ideas.md](../tasks/ideas.md).

**Отступления от проекта (согласованы по сводке B3)**
- **Имена источников** — в стиле каталога закладок: вместо `parser.section_info.*` черновика схемы — `reference.direction.*`, `reference.profile.name`, `reference.curriculum_plan.education_form`, `reference.department.name`. Каталог источников — `DocumentSources` (21 путь).
- **Схемы:** код индикатора допускает три уровня (`ПК-1.1.1`); `control_types` — массив (решение этапа 2); в ФОС `passport` обязателен, `evaluation_scale` — нет (правки по сверке); банк заданий — `task_bank` с именованными группами вместо `test_bank`.
- **Шестой построитель таблиц** `fos_passport`: в ФОС `AutofillCompetenciesTable` — паспорт ФОС (разделы, компетенции, индикаторы, задания), а не таблица компетенций РПД.
- **Формы слова — переопределением вхождения.** Одна закладка бывает в разных формах: «Обязательная часть» на титуле РПД и «относится к обязательной части» в разделе 2. В сопоставлении — необязательные `occurrences`: полное имя закладки с номером → форма (`nom`, `gen`, `dat`, `acc`, `ins`, `prep`) или своя цель. Без переопределения — именительный. Склонение — на этапе 5, словарём форм для закрытых наборов значений (части плана, формы обучения, уровни, квалификации), без библиотек морфологии. Переопределены: РПД `AutofillPartType2` (dat); ФОС `AutofillEducationForm1`, `AutofillEducationLvl1`, `AutofillMonitoring2–3` (gen), `AutofillMonitoringU1` (dat).
- **Ошибки каталога закладок** исправлены в `docs/design/ВКР_2_Карта_закладок_DOCX.md` с пометкой «исправлено по шаблонам, этап 3»: `AutofillKurs` — фраза раздела 3.5 о курсовом проекте (без курсового проекта по плану — стандартная заглушка, FR-TPL-14), а не курс; `AutofillPositionKafForDoc` — сокращение кафедры заведующего (`departments.short_name`); `AutofillEducationLevel` в ФОС — квалификация: явная из плана, иначе производная от уровня (бакалавриат → бакалавр, магистратура → магистр, специалитет → специалист).
- **Прочие цели:** `AutofillPassDestination` — «фонда оценочных средств по дисциплине «…»» (подтверждено реальным ФОС); `AutofillMonitoringU` и `AutofillMonitoring` — формы текущего контроля через запятую; `AutofillExaming` оставлен помеченным — сверка на этапе 5.
- **Единый набор кодов категорий подписантов:** `department_head`, `department_head_acting`, `institute_director`, `rector`, `vice_rector_edu`, `umu_head`, `library_director`, `it_directorate_head`, `umk_chair` — и в листах согласования шаблонов, и в `users.signatory_role`. Переименование значений в базе — миграцией шага B4. `umk_chair` пока без привязки к подразделению; связь с направлением — на этапе 6.

**B4. Модель шаблона (миграция `TemplatesModel`)**
- **Редакция — `revision`, связь редакций — `lineage_id`** (отступление от проекта по заданию). В проекте `document_templates.version` — редакция шаблона, но в коде `Version` занята оптимистичной блокировкой. Редакции связываются общим `lineage_id`, а не совпадением типа и названия: переименование не рвёт связь. Уникальны `(lineage_id, revision)` и опубликованная редакция в линии — частичный индекс `lineage_id WHERE status = 'published'`.
- **Снимок структуры типа:** `schema` и `signatures_config` (jsonb) копируются из реестра типов при создании; `print_template_file_id` → `uploaded_files`, `print_mapping` (jsonb); `curriculum_plan_id` → `curriculum_plans`, `created_by` → `users`, `published_at`, `deleted_at`. Длины `type`, `name`, `status` — как в проекте (50, 255, 20). `default_payload` из проекта не добавлен — вне задания этапа.
- **Год шаблона этапа 0** (`year`) удалён: шаблон привязан к версии учебного плана, у неё есть год набора.
- **Тестовые шаблоны этапов 0–1** («Создать тестовый шаблон») миграция удаляет мягко: без учебного плана и снимка структуры их не опубликовать. Записи остаются в таблице.
- **Коды подписантов в базе:** `vice_rector` → `vice_rector_edu`, `it_dept_head` → `it_directorate_head`, в наборе появился `umk_chair`; ограничения `ck_users_signatory_role` и `ck_users_signatory_scope` обновлены (`umk_chair` — без кафедры и института). Импорт должностей: `vice_rector_edu` — только проректор по образовательной деятельности (ОДиМП), другие проректоры — не подписанты.

**B5. Жизненный цикл шаблона в ядре**
- Правила переходов — `TemplateTransitions`, изменения состояния — методы сущности (`AttachPrintTemplate`, `Save`, `Publish`, `Archive`, `Delete`, `CreateRevision`): запрещённый переход — исключение, эндпоинты проверяют правило заранее и отвечают 409 с русским названием статуса. Загрузка оформления → «Черновик» (и из «Сохранённого черновика»: изменённый шаблон снова не сохранён); «Сохранить» — только из «Черновика». Публикация из «Пустого» запрещена — правило и тест этапа 0 обновлены.
- **Проверка перед публикацией** (`TemplateCheck`, без базы): учебный план, файл оформления, закладки `Autofill` в нём, каждая закладка сопоставлена, каждая цель существует — поле по *снимку* схемы шаблона, а не по текущему реестру; в листе согласования — известные категории, правила и размещения. Ошибки — списком, ответ 422 с `errors`.
- **Публикация новой редакции** (`TemplateLifecycle`) архивирует прежнюю опубликованную в одной транзакции, двумя сохранениями: частичный уникальный индекс не допускает двух опубликованных в линии, а порядок команд одного `SaveChanges` EF не гарантирует. Номер новой редакции — следующий в линии с учётом удалённых (их номера заняты уникальным индексом); вторая неопубликованная редакция параллельно не создаётся — 409.

**B6. API шаблонов**
- `GET /api/templates?type=&status=&planId=`, `GET /api/templates/{id}` — с закладками оформления (вхождения, цель или её отсутствие), листом согласования (с названием правила определения) и ошибками проверки; `POST /api/templates` — тип, название, план (создатель — запись справочника текущего пользователя, без неё — 403); `POST …/print-template` — multipart `file` + `version`; `POST …/save`, `…/publish`, `…/archive`, `…/revisions`; `DELETE …?version=`. Контракт создания этапа 0 (с годом) заменён.
- **Шаблон оформления** хранится в `uploaded_files` с типом `other` (отдельного типа в проекте нет); тот же файл по `checksum` переиспользуется, как при импорте. Файл, который не открывается как DOCX, — 422. Сопоставление по умолчанию — цели реестра только для закладок загруженного файла.
- **Новая редакция и версия клиента.** Опубликованная редакция при создании новой не меняется, поэтому оптимистичная блокировка сама не сработает — версия клиента сравнивается явно, ответ тот же, что у `ConcurrencyExceptionHandler`.
- **Срез «Учебные планы»** — `GET /api/curriculum-plans` (только чтение): форме создания шаблона нужен выбор импортированного плана, а списка планов в API не было.

**B7. Клиент**
- «Шаблоны» — список с типом, планом, редакцией и статусом по-русски, фильтры по типу, статусу и плану; кнопка «Создать тестовый шаблон» этапа 1 убрана. Страница шаблона: создание (тип, название, импортированный план), загрузка DOCX-шаблона оформления, проверка перед публикацией, таблица закладок (вхождения, сопоставлена или нет, вид и цель, переопределения вхождений, пояснения), лист согласования, кнопки по статусу. Преподавателю и проверяющему — только просмотр.
- Проверено в браузере на базе разработки (методист): создание шаблона РПД для плана версии 4, загрузка DWP-шаблона через поле файла (35 закладок, 52 вхождения, все сопоставлены), сохранение, публикация, новая редакция и её публикация — первая редакция ушла в архив; шаблон РПД с оформлением ФОС не опубликован, показаны 8 несопоставленных закладок; удаление черновика. Миграция `TemplatesModel` на базе разработки: четыре тестовых шаблона этапа 1 удалены мягко, коды `vice_rector` и `it_dept_head` переименованы.

**На подтверждение автора**
- *Второе вхождение `AutofillEducationLevel` в РПД — квалификация.* Найдено при разметке форм вхождений: в разделе 1 шаблона — «…по направлению подготовки … с квалификацией «AutofillEducationLevel»», на титуле — «Уровень высшего образования». Сделано по образцу решения для ФОС: переопределение `AutofillEducationLevel2` → `reference.direction.qualification`. В каталоге закладок не исправлено — решение за автором. → *Подтверждено автором, каталог исправлен на этапе 4 (A4).*

**Проблемы и решения**
- *EF угадал переименование.* При удалении `year` и добавлении `revision` (оба `int`) генератор миграции предложил `RenameColumn` — год стал бы редакцией. Миграция исправлена вручную: удаление и добавление столбца; значения по умолчанию для существующих строк сняты после заполнения. Миграция проверена на копии старой схемы с тестовыми шаблонами и кодами подписантов и на базе разработки.
- *Фильтр по проекции с конструктором.* `Where` и `OrderBy` по полям записи `PlanItem`, созданной позиционным конструктором, EF не переводит в SQL — все запросы списка шаблонов отвечали 500. Проекция переписана на инициализацию свойств; ошибку поймали интеграционные тесты.
- *`@code` в разметке Razor* — та же ловушка, что на этапе 3 A2: переменная `code` в `@foreach` читается как директива. Переименована.
- *Docker Desktop не был запущен* — интеграционные тесты (Testcontainers) без него не идут; запущен перед прогоном.

**Итог.** Методист создаёт шаблон РПД или ФОС для импортированной версии плана, загружает DOCX-шаблон оформления, видит все закладки сопоставленными и публикует; проверка не даёт опубликовать шаблон без оформления или с несопоставленной закладкой и называет причины; новая редакция создаётся из опубликованной и при публикации архивирует прежнюю. Тестов — 120 (25 + 95), сборка без предупреждений.
