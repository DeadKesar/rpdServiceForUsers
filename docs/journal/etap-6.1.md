**Сделано**

- Оболочка клиента отдаётся без кэша (ниже).

**Проблема.** На остановке после B3 страница клиента открылась пустой. Оболочка клиента (`index.html`) собирается вместе с клиентом: в неё записываются имена файлов с хешем содержимого (`dotnet.<хеш>.js`, `blazor.webassembly.<хеш>.js`, карта модулей `importmap`). Статические файлы ASP.NET Core отдаются с `ETag` и `Last-Modified`, но без `Cache-Control`; при таких заголовках браузер вправе какое-то время использовать копию, не спрашивая сервер. После пересборки клиента хеши меняются, и старая копия оболочки ссылается на файлы, которых уже нет, — клиент не запускается. Помогало только обновление страницы без кэша.

**Решение.** Класс `ClientShell` (`Infrastructure`): обработчик ответа статических файлов (`OnPrepareResponse`) добавляет `Cache-Control: no-cache`, если отдаётся `index.html`. Параметры подключены в двух местах: `UseStaticFiles` (адрес `/index.html`) и `MapFallbackToFile` (корень `/` и адреса страниц клиента, например `/documents`). Второе обязательно: запасной маршрут строит собственный конвейер статических файлов, параметры обычного на него не действуют; проверено тестом — без параметров на запасном маршруте `/` и `/documents` остаются без заголовка. `no-cache` не запрещает хранение: браузер держит копию, но перед каждым использованием спрашивает сервер по `ETag`, и пока оболочка не менялась, получает ответ 304 без тела. Остальные файлы шаг не затрагивает: у файла с хешем новое содержимое — новое имя.

**Проверка**

- Тест `ClientShellTests`: `/`, `/documents` и `/index.html` отвечают `Cache-Control: no-cache`; обычный файл (`css/app.css`) — без этого заголовка. Тестовый хост работает в окружении Testing, где статические файлы проекта-клиента не подключаются (это происходит только в Development), поэтому тест подкладывает свой веб-корень во временном каталоге с `index.html` и `css/app.css`.
- Запущенный сервер (Development, `https://localhost:5081`, запросы через curl): `/`, `/documents`, `/index.html` — 200 и `Cache-Control: no-cache`, один и тот же `ETag`; повторный запрос `/` и `/documents` с `If-None-Match` — 304 с тем же заголовком; `css/app.css` — без `Cache-Control`. Файлы `_framework` с хешем (`dotnet.<хеш>.js`, `blazor.webassembly.<хеш>.js`) тоже отвечают `no-cache`: эти адреса обслуживает `UseBlazorFrameworkFiles` раньше `UseStaticFiles`, шаг их ответы не меняет. Клиент открывается, ошибок в консоли браузера и в журнале сервера нет.
- Сборка — без предупреждений; тесты — все пройдены (322 в `RpdFos.Api.Tests` и 42 в `DisciplineDataExtractor.Tests`).

**Отступления от `docs/design`.** Нет: требования в проекте нет.

**Замечено, шагом не охвачено.** Файлы без хеша в имени (проверено на `css/app.css`) по-прежнему отдаются без `Cache-Control`; после правки стилей браузер может показывать прежние, пока страница не обновлена без кэша (Ctrl+F5).

## Правка по замечанию C2: подпись строк прерванного круга (15.11.2026)

Решение автора по замечанию из записи C2 о строках возвращённого круга: «да, подписывать явно».

**Причина.** После возврата строки круга остаются в таблице до нового приёма (решение B1). Строка согласующего, не успевшего отметиться, оставалась `pending`, и панель показывала её «ожидает» — как живую, хотя круг окончен.

**Решение.** В панели такая строка получает статус для показа `interrupted` и подпись «круг прерван»; признак — в круге есть возвращённая строка (`DocumentApproval.StateAsync`). В таблице строка не меняется: новый приём сбрасывает её в `pending`, и подпись снова «ожидает». Статус `interrupted` не хранится и не входит в `SignatureStatuses.All` — по нему строится ограничение таблицы. Вместе с подписью из панели ушло предупреждение «нет учётной записи с ролью «Утверждающий»» для таких строк: оно написано для строк, которые ждут отметки. Отступления от `docs/design` нет: подписей строк прерванного круга в проекте нет.

**Проверка.** Тест `Return_from_approval_labels_the_rows_that_did_not_mark_as_interrupted`: до исправления падал (приходило `pending` / «ожидает»), после — проходит; после нового приёма обе строки снова «ожидает».

## C3. Уведомления: события и API (15.11.2026)

**Сделано**

- **Служба `DocumentNotifications`** (ядро, `Documents/DocumentNotifications.cs`): по методу на событие; получатели, фраза и параметры — внутри. Её вызывают те же классы, что меняют статус, — `DocumentReview` (отправка, взятие на проверку, возврат, приём), `DocumentApproval` (старт круга, назначение, отметка, возврат с согласования) и `DocumentEditing` (возврат после исправления данных плана). Уведомления только добавляются в контекст, сохраняет вызывающий: событие и уведомление о нём — одна транзакция, при конфликте версий (409) не появляется ни то ни другое.
- **События и получатели**

| Событие (`event_type`) | Кому | Где создаётся |
|---|---|---|
| `document.submitted` | методистам (повторная отправка с доработки — «повторно») | отправка автором |
| `document.taken_for_review` | автору (в тексте — причина) | «Взять на проверку» |
| `document.returned_for_rework` | автору (число замечаний, общий комментарий, если есть) | возврат методистом |
| `document.returned_after_plan_correction` | автору (число замечаний — по разделам) | исправление данных плана, после которого документ неполон |
| `document.accepted` | автору: согласование начато / ждёт назначения (какие места) / не нужно | приём |
| `approval.awaiting_mark` | согласующему; одно уведомление на человека со всеми его местами | старт круга; назначение на идущем круге |
| `document.returned_from_approval` | методистам (кто и комментарий) | возврат согласующим |
| `document.approved` | автору и методистам | последняя отметка; приём при шаблоне без электронных мест |

- **Срез `Features/Notifications`:** `GET /api/notifications?limit=` (по умолчанию 20, не больше 100; от новых к старым), `GET /api/notifications/unread-count`, `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all`. Доступ — любой вошедший; в ответе — id, тип, документ, готовая фраза, время создания и прочтения. Чужое уведомление и несуществующее неразличимы — 404.
- **`DirectoryAccounts.ActiveHoldersOfAsync(роль)`** — получатели «всем методистам»: запись справочника активна, вход разрешён, учётная запись с этой ролью не отключена администратором (бессрочная блокировка, этап 5.2).
- **`DocumentHistory.StatusChanged`** теперь возвращает время записи в историю статусов.

**Решения**

1. **Получатель — запись справочника; совершившему действие уведомления нет.** Список получателей события очищается от автора действия и от повторов: человек, который одновременно автор документа и методист, получит «согласован» один раз, а не дважды. Заведующий кафедрой — автор и согласующий — не получает уведомлений о своих действиях: отправил, последним отметил (решение автора 3).
2. **Время уведомления — время события.** Для смены статуса это время записи в историю (`StatusChanged` его возвращает). Иначе два уведомления одного получателя из одного сохранения — «принят» и «ждёт вашего согласования» у автора-согласующего, «принят» и «согласован» при шаблоне без электронных мест — встали бы в ленте в порядке вызовов, а не событий: «принят» создаётся после старта круга, потому что в нём сказано, чем приём кончился.
3. **«При ручном назначении» понято как «когда назначение делает документ ожидающим отметки».** На идущем круге (статус «На согласовании») назначенный получает «ждёт вашего согласования» сразу. В статусе «Принят» круга ещё нет: назначенного уведомит старт круга, как и остальных. Иначе председатель, назначенный до запуска, получил бы два уведомления об одном и том же. Повторное назначение того же человека не уведомляет. Уточнение к формулировке задания; если нужно буквально — это одна строка в `AssignAsync`.
4. **Приём при шаблоне без электронных мест** даёт автору два уведомления — «принят» (согласующих нет) и «согласован»: в истории статусов тоже два перехода. Методисты, кроме принявшего, получают «согласован».
5. **Готовая фраза — в `payload.text`**, параметры рядом: `title`, `discipline_code`, `discipline`, `by`, `comment`, `remarks`, `seats`, `approval`. Фразы без родовых форм («Принят», «Взят на проверку методистом …», «Согласующий: …»): пол автора и методиста системе неизвестен. Точка в конце предложения ставится, только если её нет: «Фамилия И. О.» уже кончается точкой (та же «двойная точка» уже встречалась в сообщении о назначении согласующего, этап 6). Параметр без значения (нет общего комментария) в payload не пишется.
6. **Пользователь без записи справочника** (учётная запись не связана) получателем быть не может: лента пуста, число — 0, «прочитать все» — 204, «прочитано» для любого id — 404. Остальные действия API на такой учётной записи отвечают 403, но колокольчик есть у всех, и ошибка на каждом опросе была бы лишней.
7. **«Прочитано» повторно** время прочтения не меняет; «прочитать все» — один запрос на обновление только своих непрочитанных, прочитанное не перезаписывается.
8. **Схема базы не менялась:** таблица и частичный индекс с шага B1 подходят, миграции нет.

**Отступления от `docs/design`** (FR-REV-08): из всего требования сделан только канал «в интерфейсе»; настройки каналов и частоты не делаются — `notification_preferences` не создаётся, экран S-02 не затронут; события «приближение дедлайна» и «новый комментарий» не реализованы (смены статуса и возвраты — реализованы); `emailed_at` остаётся пустым.

**Проверка**

Во всех потоках проверено, что в фразах нет «..» и двойных пробелов.

## C4. Очереди: «Отмеченные мной» и возвращённые с согласования (15.11.2026)

**Сделано**

- **Список «Отмеченные мной»** — `GET /api/approvals/marked` (срез `Features/Approvals`, политика «Утверждающий»): документы, где в строках текущего круга (`document_signatures`) за пользователем стоит согласие или возврат. В ответе: документ, тип, дисциплина, автор, статус документа сейчас, отметка (`approved` / `rejected`) с подписью («согласовано» / «возвращено») и время. Время согласия — `approved_at`; время возврата в строке не хранится — оно из истории статусов (последний переход «На согласовании → На проверке»). Сверху — последние отметки.
- **Пометка «с согласования»** — поле `fromApproval` (кто и когда) в ответе `GET /api/documents` у документов на проверке, чей последний переход в этот статус пришёл с согласования. Приходит методисту и администратору; автору не приходит — как ему не приходят строки круга и плашка возврата в документе.
- **Страницы клиента.** «Согласование»: под очередью — второй список «Отмеченные мной», колонки — дисциплина, автор, тип, статус документа, отметка, время (значок отметки того же цвета, что в панели документа). «Проверка»: под названием дисциплины — значок «с согласования» и строка «возврат: ФИО, дата». В браузере страницы не показывались — они в показе C5.
- Обе идеи перенесены из `ideas.md` в `ideas-done.md`; одна новая записана в `ideas.md` (список растёт без границы).

**Решения**

1. **«Текущий круг» — это строки таблицы.** Возврат оставляет строки до нового приёма (решение B1), приём сбрасывает их. Отсюда поведение списка: после возврата в нём остаются и возврат, и согласия того же круга (документ уже на проверке); после нового приёма отметки сброшены — документ снова в очереди и из списка ушёл. Отдельного признака круга в базе нет, и вводить его не пришлось.
2. **Документ в списке один раз.** Отметки одного человека в документе ставятся вместе, но второе место ему можно назначить и после первой отметки; тогда в списке берётся последняя из них, а документ стоит ещё и в очереди — второе место ждёт отметки.
3. **Колонка «Отправлен» в «Проверке» не менялась** (замечание из записи C2). У вернувшегося с согласования она по-прежнему показывает дату отправки автором, порядок списка тоже прежний — по ней. Кто и когда вернул — в пометке рядом с названием. Если нужна дата поступления на проверку вместо даты отправки или порядок по возврату — это решение автора (`/fix`).
4. **Пометка — без родовых форм:** «возврат: ФИО, дата», а не «вернул» — как и в уведомлениях C3: пол согласующего системе неизвестен. Комментарий возврата в список не вынесен: он в документе, в плашке для методиста.
5. **Пометка — по последнему переходу, не по любому.** Документ, возвращённый с согласования, а потом возвращённый методистом автору и отправленный им снова, пометки не несёт: его последний переход в «На проверке» — с доработки. Второй возврат с согласования показывает того, кто вернул последним.
6. **Схема базы не менялась:** история статусов и строки круга всё нужное хранят, миграции нет.

**Отступления от `docs/design`.** Дополнения к экранам: в S-31 (в проекте — одна таблица очереди) добавлен второй список «Отмеченные мной», в S-30 — пометка «с согласования». Обе по решению автора от 15.11.2026 (пункт 4) — это идеи этапа 6; противоречия с проектом нет.

**Проверка**

## C5. Колокольчик: точка проверки в браузере (16.11.2026)

**Сделано**

- **Колокольчик в шапке** (`Layout/NotificationBell.razor`, подключён в `LoginDisplay` внутри `Authorized`): значок с числом непрочитанных (больше 99 — «99+»); по клику — список последних 20 уведомлений: готовая фраза сервера, время (`дд.мм.гггг чч:мм`, местное, как на остальных страницах), ссылка «Открыть документ», у непрочитанных «Прочитано», в шапке списка «Прочитать все». Непрочитанные — светлый фон и синяя полоса слева, прочитанные приглушены. Список закрывается кликом вне его, клавишей Esc и переходом на другую страницу; клик вне списка только закрывает его и до элемента под ним не доходит (прозрачная подложка вместо скрипта). Переход по ссылке отмечает уведомление прочитанным.
- **Клиентская служба `NotificationFeed`** (`RpdFos.Web/Notifications`, одна на вкладку): держит ленту и число, ведёт опрос. Обновление — раз в минуту (`PeriodicTimer`, первое сразу) и при каждом переходе между страницами (`LocationChanged`), кроме служебных `authentication/*`; открытие списка тоже обновляет, не дожидаясь минуты. Одно обновление — два запроса: последние 20 (`GET /api/notifications?limit=20`) и число (`GET /api/notifications/unread-count`): непрочитанных может быть больше, чем в списке.
- **Модели клиента** `Models/Notifications.cs` (`NotificationItem`, `UnreadCount`) — зеркало ответов среза C3.
- **Стили:** `NotificationBell.razor.css`; в `MainLayout.razor.css` шапке на узком экране добавлено `position: relative` — к ней привязан список.
- **Тесты ленты** — 18 (`tests/RpdFos.Api.Tests/Client/NotificationFeedTests.cs`), см. «Проверка».

**Решения**

1. **Лента — отдельный класс, а не код компонента.** Опрос, сбои и остановка — поведение, которого удачный путь в браузере не покажет; в классе их проверяют тесты с подставным HTTP-обработчиком, без браузера. Компонент только рисует и подписан на событие `Changed`.
2. **Фоновое обновление молчит при любом сбое.** `RefreshAsync` не бросает исключений: нет токена (`AccessTokenNotAvailableException`), нет связи (`HttpRequestException`), ответ 401 или 5xx, тело не разобралось — лента остаётся прежней, на вход не перенаправляет, на экране ничего; следующий опрос повторит. Идея из `ideas.md` («потеря связи с сервером на странице документа») для колокольчика учтена сразу; для `PrintPanel` она остаётся. Действие пользователя («Прочитано», «Прочитать все») ведёт себя как на остальных страницах: нет токена — перенаправление на вход; нет связи или ответ с ошибкой — строка «Не удалось выполнить действие…» в списке; 404 (такого уведомления нет) считается выполненным.
3. **Без правки списка на месте.** После «Прочитано» лента запрашивается заново: число непрочитанных считает сервер, и «одно прочитано» не всегда «на единицу меньше».
4. **«Побеждает последнее».** Ответ обновления, начатого раньше другого обновления или действия, отбрасывается (по номеру запроса): иначе устаревший ответ мог бы на мгновение вернуть прочитанное уведомление непрочитанным. После остановки опроса ответы ушедших запросов тоже отбрасываются.
5. **Остановка опроса.** Опрос живёт, пока компонент стоит в `AuthorizeView`: выход убирает компонент, и его `Dispose` останавливает опрос. Страховка: перед каждым обновлением проверяется состояние входа, и если пользователя уже нет, опрос прекращается, а лента забывается. Если опрос остановлен, а компонент ещё на экране, колокольчика нет вовсе: значок с пустой лентой вводит в заблуждение. Это решение принято после опыта в браузере (см. «Найдено»).
6. **Узкий экран.** Колокольчик стоит у левого края шапки, и список, выровненный по его правому краю, уходил за экран. На экранах уже 641 px список привязан к шапке и занимает её ширину (найдено при проверке в панели браузера, исправлено).
7. **Фраза — как пришла.** Клиент ничего не собирает из параметров события: показывается `payload.text`; ссылка всегда на страницу документа.
