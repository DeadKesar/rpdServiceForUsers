# Руководство системного программиста

<a id="purpose"></a>
## Назначение и состав

Руководство — для того, кто устанавливает, настраивает и сопровождает автоматизированную систему создания рабочих программ дисциплин (РПД) и фондов оценочных средств (ФОС): стенд апробации на компьютере кафедры, а позже — сервер ИТ-службы. Последний раздел, [«Администратору»](#admin), — для пользователя с ролью «Администратор»: учётные записи, справочник сотрудников, кафедры, журнал аудита.

Пошаговые команды установки, обновления, сертификатов, почты и резервных копий собраны в инструкции стенда [`docs/runbooks/Этап8_стенд.md`](../runbooks/Этап8_стенд.md); руководство ссылается на её разделы и не повторяет команды без нужды. Если команда здесь и в инструкции расходится, верна инструкция: она проверялась установкой с нуля.

Работа пользователей описана отдельно: [руководство преподавателя и согласующего](teacher.md) и [руководство методиста](methodist.md).

<a id="components"></a>
### Состав системы

Система — набор контейнеров Docker, который поднимает Docker Compose из папки `deploy` репозитория (имя проекта compose — `rpdfos-stand`).

| Служба | Образ | Что делает |
| --- | --- | --- |
| `proxy` | `nginx:1.30.8` | Принимает HTTPS (TLS 1.2 и 1.3) на портах 443 и 80, с 80 и с «чужого» имени перенаправляет на `https://<имя стенда>`, передаёт запросы хосту |
| `api` | `rpdfos-api:stand`, собирается из `Dockerfile` репозитория | Хост: API, веб-клиент Blazor WebAssembly, сервер авторизации OpenID Connect, страница входа, фоновые задачи |
| `db` | `postgres:17-alpine` | База данных: все данные системы, исходные файлы, шаблоны оформления, очередь фоновых задач |
| `converter` | `gotenberg/gotenberg:8.38.1` | Конвертер DOCX → PDF (LibreOffice без интерфейса за HTTP) |
| `mail` | `boky/postfix:5.2.1-alpine` | Свой почтовый сервер стенда, только на отправку |
| `backup` | `postgres:17-alpine` | Ежедневная резервная копия базы в папку компьютера |
| `certs` | `nginx:1.30.8` | Выпуск сертификатов; не работает постоянно, запускается вручную |

Хост API — один процесс .NET 10 (ASP.NET Core). В нём:

- **API** — модули Carter по областям: документы, шаблоны, импорт, учебные планы, закрепление дисциплин, согласование, печать, рисунки, уведомления, профиль, справочник сотрудников, кафедры, пользователи, журнал аудита, история документа. Адреса начинаются с `/api/`.
- **Веб-клиент** — файлы Blazor WebAssembly раздаёт сам хост: клиент и API живут по одному адресу, CORS не нужен.
- **Сервер авторизации** — ASP.NET Core Identity и OpenIddict: вход по OpenID Connect (поток authorization code с PKCE), конечные точки `/connect/authorize`, `/connect/token`, `/connect/logout`, `/connect/userinfo`, страница входа `/Account/Login`. Учётные записи и хеши паролей — в той же базе.
- **Фоновые задачи** — Hangfire; хранилище — схема `hangfire` той же базы (подробнее — [«Фоновые задачи»](#jobs)).

Связи между службами:

- Браузер → `proxy` (443) → `api` (8080 во внутренней сети). Порт хоста наружу не публикуется: заголовкам прокси (`X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`) хост верит без списка доверенных адресов.
- `api` → `db` (5432) и `api` → `converter` (3000) — сеть `back`, внутренняя, без выхода в интернет и без портов наружу.
- `api` → `mail` (587, без входа и шифрования) — сеть `mailnet` из двух служб; почтовому серверу нужен выход наружу на порт 25 серверов получателей.
- `backup` → `db` — сеть `back`.

Данные — в именованных томах Docker:

| Том | Что хранит |
| --- | --- |
| `rpdfos-stand_dbdata` | Файлы базы PostgreSQL |
| `rpdfos-stand_appdata` | Ключи Data Protection (`/var/lib/rpdfos/keys`) и сформированные файлы DOCX и PDF (`/var/lib/rpdfos/generated`) |
| `rpdfos-stand_mailqueue` | Очередь неотправленных писем |
| `rpdfos-stand_maildkim` | Ключ подписи DKIM |

Вне томов, в папке `deploy` компьютера: `.env` (настройки с паролями), `certs/` (сертификаты), папка копий (`BACKUP_DIR`, по умолчанию `deploy/backups`). В git они не попадают.

<a id="network"></a>
### Порты, сети, порядок запуска

| Служба | Порт | Сети | Наружу | Проверка здоровья |
| --- | --- | --- | --- | --- |
| `proxy` | 80, 443 | `front` | Да — единственная | Ответ nginx на `http://127.0.0.1/` раз в 15 с |
| `api` | 8080 | `front`, `back`, `mailnet` | Нет | Запрос `/health` раз в 15 с, первые 40 с — время запуска |
| `db` | 5432 | `back` | Нет | `pg_isready` раз в 5 с |
| `converter` | 3000 | `back` | Нет | `/health` раз в 30 с |
| `mail` | 587 | `mailnet` | Нет (исходящий 25 к получателям) | Нет |
| `backup` | — | `back` | Нет | Была ли копия за сутки, раз в час |

Порядок запуска задаёт compose: `db` → `api` (ждёт здоровую базу и запущенный конвертер) → `proxy`; `backup` ждёт здоровую базу. `docker compose up -d --wait` возвращает управление, когда службы с проверками стали `healthy`. Все службы, кроме `certs`, перезапускаются сами (`restart: unless-stopped`) — после сбоя и после перезагрузки компьютера, если их не останавливали командой `stop`.

**Прокси.** Настройки nginx — шаблон `deploy/nginx/templates/default.conf.template`; при запуске контейнера в него подставляется `STAND_HOST`. Что в нём задано:

- запросы по другому имени или адресу и по HTTP — перенаправление 301 на `https://<STAND_HOST>`: вход работает только по этому имени;
- TLS 1.2 и 1.3, сертификат `certs/stand`, без номера версии nginx в ответах;
- размер запроса до 64 МБ — три файла импорта одним запросом;
- увеличенные буферы заголовков — коды и токены OIDC;
- ожидание ответа хоста до 180 с — печать ждёт конвертер до 120 с;
- адрес хоста уточняется через DNS Docker каждые 10 с — после обновления у контейнера хоста другой адрес, прокси перезапускать не нужно;
- журнал без строки запроса.

Правка шаблона — `docker compose restart proxy`; при обновлении из git свои правки шаблона придётся перенести заново, поэтому их лучше не делать без нужды.

<a id="architecture"></a>
### Устройство хоста

Исходный код — решение `RpdFos.slnx`:

| Проект | Что в нём |
| --- | --- |
| `src/RpdFos.Core` | Прикладное ядро: сущности, контекст базы `AppDbContext`, миграции, правила домена (переходы статусов, проверка содержимого по JSON Schema и каталогу правил), импорт, печать DOCX, почта, напоминания, перехватчик версий. Общее для API и фоновых задач |
| `src/RpdFos.Api` | Хост: модули Carter по областям (`Features/<Область>`), сервер авторизации и страница входа (Razor Pages), регистрация фоновых задач, обработка ошибок |
| `src/RpdFos.Web` | Веб-клиент Blazor WebAssembly — клиент OIDC `rpdfos-web`; отдельно не запускается, его файлы входят в образ хоста |
| `src/DisciplineDataExtractor` | Разбор файлов учебного плана (`.xlsx`), списка и матрицы компетенций (`.docx`) |
| `tools/RpdFos.Manuals` | Проверка и сборка руководств в PDF |
| `tools/RpdFos.Corpus` | Разбор корпуса прежних документов кафедры (исследование, в работе системы не участвует) |
| `tests/` | Тесты: модульные и интеграционные (хост в памяти, PostgreSQL в Testcontainers) |

**Как проходит вход.** Пользователь открывает `https://<имя стенда>`; хост отдаёт клиент. «Войти» — клиент отправляет браузер на `/connect/authorize` с кодом PKCE; хост показывает страницу входа `/Account/Login`, проверяет пароль (ASP.NET Core Identity) и ставит куку входа; браузер возвращается на `/authentication/login-callback` с кодом; клиент обменивает код на токены (`/connect/token`): токен доступа и токен обновления, подписанные и зашифрованные сертификатами входа. Дальше каждый запрос к `/api/…` идёт с токеном доступа; хост проверяет его сам, без внешнего сервера. Роли — в токене: новые роли пользователь получает при следующем входе.

**Как проходит запрос, меняющий документ.** Клиент отправляет содержимое раздела и версию, которую видел. Ядро проверяет право (роль, автор, закрепление), допустимость действия в текущем статусе и данные по схеме шаблона; перехватчик сохранения увеличивает версию. Если документ тем временем сохранил другой пользователь, версия не совпадёт — ответ 409, клиент предлагает обновить страницу. Переход статуса пишется в историю статусов, значимые действия — в журнал аудита, события — в уведомления адресатам.

**Как проходит печать.** Запрос ставит задачу в очередь `generation`; исполнитель собирает DOCX из файла оформления шаблона и содержимого документа (Open XML SDK) и, если нужен PDF, отдаёт DOCX конвертеру. Файл ложится на том (`Generation:StoragePath`), запись о нём — в `generated_files`; клиент опрашивает задачу и скачивает файл. Через `Generation:RetentionDays` файл удаляется.

**Как проходит импорт.** Методист загружает три файла; они сохраняются в базе (`uploaded_files`, содержимое — в самой записи), задача в очереди `parsing` разбирает их и обновляет справочники, учебный план и матрицу компетенций; итог и замечания — в `parser_runs`.

**Хранение.** Невосстановимое — исходные файлы, файлы оформления шаблонов, рисунки — лежит в базе и попадает в её копию. На томе — только сформированные файлы, их можно сформировать заново. Содержимое документа — JSON в колонке `payload`, критичные поля (статус, дисциплина, автор, версия) — обычные колонки.

<a id="security"></a>
### Безопасность

| Мера | Как устроено |
| --- | --- |
| Шифрование канала | Только HTTPS, TLS 1.2 и 1.3 (NFR-SEC-01); HTTP перенаправляется на HTTPS. Сертификат — от своего корневого, ограниченного именем стенда |
| Изоляция | Наружу открыты только 80 и 443; база и конвертер — во внутренней сети без выхода в интернет, без внешних облаков (NFR-SEC-09) |
| Пароли | Только хеши ASP.NET Core Identity в `AspNetUsers`; пароль задаёт сам человек, администратор — только временный |
| Токены | Подписаны и зашифрованы сертификатами входа; клиент — публичный, с PKCE; у учётной записи с временным паролем токены не выдаются |
| Куки и ссылки | Защищены ключами Data Protection на томе; ссылки из писем одноразовые, с ограниченным сроком |
| Доступ | Каждый адрес `/api/…` требует токен; права — по ролям и по связи с документом (автор, закрепление, назначенный согласующий) |
| Перебор паролей | Блокировка на 5 минут после 5 неудачных попыток |
| Файлы | Проверка расширения и размера при загрузке; файлы до 10 МБ (импорт, оформление), рисунки до 2 МБ |
| Журналы | Журнал nginx — без строки запроса (в ней бывают коды входа и токены); журнал аудита — действия с документами и справочниками |
| Секреты | Пароли базы, сертификатов, почты — в `deploy/.env` вне git; ключ корневого — на отдельном носителе |

Персональные данные в системе — ФИО, должности, степени и адреса сотрудников. Копии базы и `.env` содержат их и секреты: хранить копии там, куда нет доступа посторонним.

<a id="design-deviations"></a>
### Отличия от проекта

Проект системы — глава 2 пояснительной записки, файлы `docs/design`: контейнеры — раздел «Уровень 2 — Контейнеры», развёртывание — «Развёртывание» в `ВКР_2_Архитектура_C4.md`. Реализация отличается от него в следующем:

| В проекте | В реализации | Почему |
| --- | --- | --- |
| Отдельный контейнер сервера аутентификации (Duende IdentityServer) | OpenIddict внутри хоста API | Лицензия Duende платная для организаций; OpenIddict — Apache 2.0 |
| nginx раздаёт статические файлы клиента и маршрутизирует `/api` и `/identity` | nginx только завершает HTTPS и передаёт все запросы хосту; клиент раздаёт хост | Один адрес для клиента, API и входа; адреса файлов клиента с хешами строит сборка хоста |
| Фоновый обработчик — отдельный хост | Сервер Hangfire работает в процессе API | Для апробации одного процесса достаточно; вынести сервер задач в отдельный контейнер можно без изменения кода (NFR-SCA-03) |
| SMTP — внешний почтовый сервер | Свой почтовый сервер стенда (`mail`); корпоративный подключается только настройками | Решение автора: на период апробации — своя почта |
| Ежедневный `pg_dump` | Служба `backup` в compose | Одинаково на Windows и Linux, без планировщика ОС |
| Один сервер вуза под Linux | Компьютер кафедры под Windows или Linux | Стенд апробации; сервер ИТ-службы — позже (раздел [«Перенос на сервер ИТ-службы»](#transfer)) |

<a id="jobs"></a>
### Фоновые задачи

Сервер Hangfire работает внутри хоста и слушает три очереди:

| Очередь | Исполнителей | Что выполняет |
| --- | --- | --- |
| `parsing` | 1 | Разбор загруженных файлов: учебный план, список и матрица компетенций. Импорты идут по одному |
| `generation` | `Jobs:GenerationWorkers` (2) | Формирование DOCX и PDF; ежедневная очистка сформированных файлов с истёкшим сроком; ежедневные напоминания о сроке доработки |
| `mail` | 1 | Отправка писем; сервер этой очереди есть, только когда почта включена (`Mail:Enabled`) |

Повторяющиеся задачи:

| Задача | Расписание | Что делает |
| --- | --- | --- |
| `generated-files-cleanup` | Раз в сутки, в 00:00 UTC | Удаляет сформированные файлы старше `Generation:RetentionDays` |
| `notification-mail` | Раз в минуту, если почта включена | Отправляет письма о событиях «сразу», в час `Mail:DigestHour` — дайджесты; повторяет неотправленные, пока им не больше `Mail:MaxAgeHours` |
| `rework-reminders` | Раз в сутки в час `Reminders:Hour` по поясу сервера, если напоминания включены | Предупреждает автора, что срок доработки истекает, и сообщает заведующему кафедрой и методистам о просроченной доработке |

Неудачная задача автоматически не повторяется: импорт сам пишет итог (в том числе ошибку) в журнал запусков, его видит методист; печать показывает ошибку пользователю, и он запускает её снова. Выключение почты или напоминаний снимает и их расписание, оставшееся от прежнего запуска.

Часовой пояс сервера задаёт переменная `TZ` контейнера (на стенде — `Europe/Moscow` у всех служб): по нему идут дайджест, напоминания и время копий.

<a id="requirements"></a>
### Требования к компьютеру

Кратко — по разделу 1 инструкции стенда:

- Linux с Docker Engine 25 или новее и плагином compose либо Windows 10/11 с Docker Desktop (контейнеры Linux, WSL 2, Engine 25+).
- 4 ядра, 8 ГБ памяти, 30 ГБ свободного места (образы — около 4 ГБ, столько же временно на сборку).
- Интернет — на время установки и обновления; в работе наружу выходит только почта.
- Постоянное имя или адрес в сети кафедры; свободные порты 80 и 443; сон и гибернация выключены.
- На Windows Docker Desktop стартует при входе пользователя: нужен автоматический вход, иначе после перезагрузки стенд не поднимется сам.

Пользователям нужен только браузер (Edge, Chrome, Firefox, Яндекс Браузер последних версий) и установленный корневой сертификат стенда.

<a id="install"></a>
## Установка

Полный порядок — раздел 2 инструкции стенда. Шаги и то, что важно знать системному программисту:

1. **Исходники.** Клонировать репозиторий или распаковать архив, перейти в папку `deploy`.
2. **Настройки.** Скопировать `.env.example` в `.env` и заполнить обязательные строки: `STAND_HOST`, `STAND_IP` (если адрес постоянный), `DB_PASSWORD`, `CERT_PASSWORD`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`. Почту на первом запуске можно оставить выключенной. Все строки `.env` — в разделе [«Настройки стенда (.env)»](#settings-env). Доступ к `.env` — только администратору стенда.
3. **Сертификаты.** `docker compose run --rm certs` выпускает корневой сертификат, сертификат стенда и сертификаты входа в папку `certs`. Запомнить отпечаток корневого из вывода.
4. **Запуск.** `docker compose up -d --build --wait` — первый раз до 15 минут. Хост сам применяет миграции и создаёт роли, клиента OIDC `rpdfos-web` и первого администратора. Тестовых данных в базе нет.
5. **Корневой сертификат** `certs/ca/rpdfos-ca.crt` — на компьютеры кафедры (раздел 3 инструкции): `certutil -addstore -f Root` для всех пользователей компьютера, групповая политика — для домена, Firefox — настройка `security.enterprise_roots.enabled` или импорт.
6. **Проверка.** `https://<имя стенда>/health` отвечает `{"status":"ok"}`, главная страница открывается без предупреждения браузера, все службы в `docker compose ps` — `healthy`.
7. **Первый вход и уборка.** Войти администратором, сменить пароль в профиле, очистить `ADMIN_EMAIL` и `ADMIN_PASSWORD` в `.env`, выполнить `docker compose up -d`. Если строки оставить, а администратор сменит email, при следующем запуске хост создаст второго администратора с паролем из `.env`.
8. **Ключ корневого** `certs/ca/ca.key` — на отдельный носитель, со стенда удалить: он нужен только для перевыпуска.

Дальше администратор создаёт учётные записи и загружает должности сотрудников (раздел [«Администратору»](#admin)), методист — учебные планы и шаблоны.

<a id="certificates"></a>
### Сертификаты

| Сертификат | Файлы | Срок | Для чего |
| --- | --- | --- | --- |
| Корневой | `certs/ca/rpdfos-ca.crt`, `certs/ca/ca.key` | 10 лет | Ставится на компьютеры пользователей; ограничен именем и адресом стенда — другой сайт им не подписать |
| Стенда | `certs/stand/stand.crt`, `stand.key` | 820 дней | HTTPS у `proxy` |
| Входа | `certs/auth/signing.pfx`, `encryption.pfx` | 5 лет | Подпись и шифрование токенов OpenIddict; пароль — `CERT_PASSWORD` |

Сроки и отпечатки — `docker compose run --rm certs show`. Замена каждого, смена имени или адреса стенда, смена паролей — раздел 6 инструкции. Хост не стартует с сертификатом входа, который не действует на сегодня, и называет файл в журнале: замену лучше планировать заранее, по выводу `show`.

Запасной путь — самоподписанный сертификат стенда (`docker compose run --rm certs self-signed`, затем `docker compose restart proxy`): корневой ставить не нужно, но браузер предупреждает на каждом компьютере.

<a id="update"></a>
## Обновление версии

По разделу 4 инструкции стенда:

1. Копия базы: `docker compose run --rm backup now`. Миграции назад не откатываются — без копии к прежней версии не вернуться.
2. Новые исходники: `git pull` или новый архив поверх, **сохранив `.env` и `certs`**.
3. Сравнить `.env.example` с `.env`: новые строки добавить в `.env`.
4. Сборка: `docker compose build --pull api`.
5. Перезапуск: `docker compose up -d --wait`. Прокси, база и конвертер продолжают работать; хост перезапускается за полминуты, применяет новые миграции, входы пользователей сохраняются (ключи — на томе).
6. Пользователям — обновить страницу без кэша (Ctrl+F5).
7. Проверить: `/health`, вход, открыть документ; затем `docker compose run --rm backup verify` по новой копии.

Если после обновления хост не стартует — `docker compose logs api`: сообщение называет настройку или миграцию. Вернуть прежнюю версию: прежние исходники, `docker compose build api`, восстановление копии из шага 1 с `--replace` (раздел [«Восстановление»](#restore)).

Обновление образов служб (`nginx`, `postgres`, `gotenberg`, `postfix`) — сменой версии в `deploy/docker-compose.yml` нового выпуска системы; самостоятельно менять образ базы на другую основную версию PostgreSQL нельзя: файлы базы несовместимы, переход — только через копию и восстановление.

<a id="transfer"></a>
## Перенос на сервер ИТ-службы

Перенос — это установка на новом компьютере по разделу 2 инструкции и восстановление копии по разделу 8. Отдельной процедуры у системы нет.

1. **На старом стенде.** Предупредить пользователей и остановить хост: `docker compose stop api`. Снять копию: `docker compose run --rm backup now`; проверить её: `docker compose run --rm backup verify`. Сохранить ключи Data Protection командой из раздела 8 инструкции (папка `keys-backup`). Взять `deploy/.env`, папку `deploy/certs/` и последний файл `rpdfos-….dump` из папки копий.
2. **На новом компьютере.** Требования — раздел [«Требования к компьютеру»](#requirements). Исходники той же версии, что на старом стенде (обновляться — после переноса). Положить в `deploy` файл `.env` и папку `certs`; если меняется `BACKUP_DIR` — исправить его в `.env`; файл копии положить в папку копий.
3. **Имя и адрес.** Остались прежними (ИТ-служба перевела запись DNS, а `STAND_IP` пуст) — сертификаты те же. Сменились имя или адрес — по разделу 6 инструкции: исправить `STAND_HOST` и `STAND_IP` в `.env`, `docker compose run --rm certs ca`, новый корневой — на компьютеры пользователей (раздел 3), старый удалить. Адреса возврата входа хост обновит сам при запуске.
4. **Восстановление до первого запуска хоста:** `docker compose run --rm backup restore` — команда поднимет пустую базу сама и восстановит последнюю копию из папки (или названную: имя файла вторым словом).
5. **Запуск:** `docker compose up -d --build --wait` — хост применит миграции к восстановленной базе.
6. **Ключи Data Protection.** Остановить хост (`docker compose stop api`), вернуть ключи командой шага 3 раздела «Восстановление» инструкции и запустить его снова: `docker compose start api`. Без ключей данные целы, но пользователям придётся войти заново, а ссылки из уже отправленных писем перестанут действовать. Том `rpdfos-stand_appdata` к этому шагу уже создан запуском.
7. **Проверка:** `/health`, вход, документы, шаблоны, печать PDF; `docker compose ps` — все `healthy`; `docker compose run --rm backup now` — первая копия на новом месте.
8. **Старый стенд** снять после проверки: `docker compose down` (данные остаются в томах до `down -v`).

На сервере ИТ-службы под Linux Docker Engine запускается при включении (`sudo systemctl enable docker`), автоматический вход пользователя не нужен. Если ИТ-служба держит свой обратный прокси с сертификатом организации, служба `proxy` не обязательна, но тогда внешний прокси должен передавать заголовки `X-Forwarded-Proto` и `X-Forwarded-Host`, а `STAND_HOST` — совпадать с именем, которое видят пользователи; такой вариант не проверялся.

<a id="corporate-mail"></a>
## Почта и переход на корпоративный сервер

Письма отправляет хост: уведомления о событиях, дайджест, напоминания — через очередь `mail`; «Забыли пароль?», приглашение, подтверждение смены email — служебные письма, сразу, без очереди (раздел [«Учётные записи»](#admin-users)). Без почты система работает: уведомления видны в интерфейсе, пароли новым пользователям задаёт администратор.

**Своя почта стенда** — служба `mail` (раздел 7 инструкции): `MAIL_ENABLED=true`, `MAIL_FROM`, `MAIL_DOMAIN`, при необходимости `MAIL_HOSTNAME`; `MAIL_HOST`, `MAIL_PORT`, `MAIL_SECURITY` — пустые, затем `docker compose up -d`. Доставка идёт с порта 25 компьютера; если сеть его закрывает — ретранслятор (`MAIL_RELAY`, `MAIL_RELAY_USER`, `MAIL_RELAY_PASSWORD`). Чтобы письма не попадали в спам, нужны имя с обратной записью, SPF и, при своём домене, DKIM (`MAIL_DKIM`).

**Корпоративный сервер** — только настройками `.env`, без пересборки:

| Настройка | Значение |
| --- | --- |
| `MAIL_ENABLED` | `true` |
| `MAIL_HOST`, `MAIL_PORT` | Имя сервера и порт: 587 с `StartTls` или 465 с `SslOnConnect` |
| `MAIL_USER`, `MAIL_PASSWORD` | Вход на сервере; пароль — в одинарных кавычках |
| `MAIL_SECURITY` | `StartTls`, `SslOnConnect`; без входа внутри сети — `None` |
| `MAIL_FROM` | Отправитель, от имени которого сервер принимает письма |

Затем `docker compose up -d` и `docker compose stop mail`. Проверка — «Забыли пароль?» на свой адрес или любое событие с почтой «сразу»; письмо уходит в течение минуты. Ошибки отправки — в журнале хоста (`docker compose logs api`, строки задачи `NotificationMailJob`).

Вход без шифрования (`MAIL_SECURITY=None` при заданном `MAIL_USER`) отправил бы пароль по сети открытым текстом: хост его не запрещает, это выбор настроек — допустим только во внутренней сети по требованию администратора почты.

<a id="settings"></a>
## Настройки

<a id="settings-where"></a>
### Где задаются настройки

Хост читает настройки ASP.NET Core в таком порядке; каждый следующий источник перекрывает предыдущий:

1. `appsettings.json` хоста — значения по умолчанию, лежат в образе.
2. `appsettings.<окружение>.json` — `appsettings.Development.json` (разработка), `appsettings.Testing.json` (тесты). Для окружения `Production` файла нет.
3. user-secrets проекта `RpdFos.Api` — только в окружении Development (компьютер разработчика).
4. Переменные окружения. Двоеточие в имени ключа заменяется двумя подчёркиваниями: `Mail:DigestHour` — переменная `Mail__DigestHour`.

На стенде переменные окружения хоста задаёт `deploy/docker-compose.yml` (служба `api`, раздел `environment`) из значений `.env`; часть задаёт образ (`Dockerfile`, строка `ENV`). Остальное берётся из `appsettings.json` образа.

Настройку, для которой нет строки в `.env` (например, срок доработки), на стенде задают файлом `deploy/docker-compose.override.yml` рядом с compose — Docker Compose читает его сам, а при обновлении из git он не перезаписывается:

```yaml
services:
  api:
    environment:
      Reminders__ReworkDays: "21"
```

После правки `.env` или файла override — `docker compose up -d`: пересоздаются только службы, у которых изменились настройки. Значения проверяются при запуске: при ошибке хост не стартует и называет настройку в журнале (`docker compose logs api`).

Ниже: «По умолчанию» — значение, с которым работает хост, если настройку нигде не задали; «Стенд» — откуда значение берётся на стенде.

<a id="settings-env"></a>
### Настройки стенда (.env)

Файл `deploy/.env`, образец — `deploy/.env.example`. Значение пустое или строки нет — действует умолчание из правого столбца.

| Переменная | Обязательна | Куда попадает | Пусто — значит |
| --- | --- | --- | --- |
| `STAND_HOST` | Да | Имя nginx, `Auth:PublicUrl` и `Mail:PublicUrl` (`https://<STAND_HOST>`), сертификаты, имя почтового сервера | compose не стартует |
| `STAND_IP` | Нет | Сертификат стенда вместе с именем | В сертификате только имя |
| `DB_PASSWORD` | Да | Пароль пользователя `rpdfos` базы, `ConnectionStrings:Default`, служба копий. Только латинские буквы и цифры. Действует с первого запуска: смена в `.env` не меняет пароль созданной базы (раздел 6 инструкции) | compose не стартует |
| `CERT_PASSWORD` | Да | Пароль файлов `signing.pfx` и `encryption.pfx`, `Auth:CertificatePassword` | compose не стартует |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | До первого входа | `Seed:AdminEmail`, `Seed:AdminPassword` — первый администратор | Администратор не создаётся; после первого входа обе строки очищают |
| `MAIL_ENABLED` | Нет | `Mail:Enabled` | `false` — письма не отправляются |
| `MAIL_HOST`, `MAIL_PORT` | Нет | `Mail:Host`, `Mail:Port` | `mail`, `587` — своя почта стенда |
| `MAIL_USER`, `MAIL_PASSWORD` | Нет | `Mail:User`, `Mail:Password` | Без входа |
| `MAIL_SECURITY` | Нет | `Mail:Security` | `None` |
| `MAIL_FROM` | Нет | `Mail:From` | `АС РПД и ФОС <rpdfos@rpdfos.local>` |
| `MAIL_DOMAIN` | Нет | Служба `mail`: принимает письма только от отправителей этого домена | `rpdfos.local` |
| `MAIL_HOSTNAME` | Нет | Служба `mail`: имя в приветствии SMTP | `STAND_HOST` |
| `MAIL_RELAY` | Нет | Служба `mail`: ретранслятор `[сервер]:порт` | Доставка напрямую получателям |
| `MAIL_RELAY_USER`, `MAIL_RELAY_PASSWORD` | Нет | Вход на ретрансляторе | Без входа |
| `MAIL_DKIM` | Нет | Любое значение — подпись DKIM, ключ создаётся на томе | Без подписи |
| `BACKUP_DIR` | Нет | Папка копий на компьютере | `deploy/backups` |
| `BACKUP_TIME` | Нет | Время ежедневной копии, `ЧЧ:ММ` по Москве | `03:00` |
| `BACKUP_KEEP` | Нет | Сколько последних копий хранить | 30 |

Пароль администратора и пароль почты — в одинарных кавычках: тогда `$` и `#` не читаются как служебные знаки.

<a id="settings-host"></a>
### Хост: окружение, адреса, журнал

| Ключ | По умолчанию | Стенд | Смысл |
| --- | --- | --- | --- |
| `ASPNETCORE_ENVIRONMENT` | `Production` (образ) | Образ | Окружение. `Development` — ключи разработки, перенаправление на HTTPS самим хостом, описание API `/openapi/v1.json` и `/swagger`, автомиграции. `Testing` — окружение тестов: ключи разработки, без фоновых задач. Любое другое — нужны сертификаты входа, `Auth:PublicUrl` и `DataProtection:KeysPath`, хост стоит за прокси и читает его заголовки |
| `ASPNETCORE_URLS` | `http://+:8080` (образ) | Образ | Адрес, который слушает хост внутри контейнера. HTTPS завершает nginx |
| `AllowedHosts` | `*` | `appsettings.json` | Допустимые имена в заголовке `Host`. Обращения по другому имени отсекает nginx |
| `Auth:PublicUrl` | `https://localhost:5081` в разработке | `https://<STAND_HOST>` | Адрес системы, по которому её открывают пользователи. Вне разработки обязателен и только `https`. | `DataProtection:KeysPath` | — | `/var/lib/rpdfos/keys` (образ) | Папка ключей Data Protection на томе: ими защищены куки входа и токены ссылок из писем. Вне разработки обязательна; без неё после перезапуска входы и ссылки перестали бы действовать |
| `Logging:LogLevel:Default` | `Information` | `appsettings.json` | Подробность журнала хоста |
| `Logging:LogLevel:Microsoft.AspNetCore` | `Warning` | `appsettings.json` | Журнал самого ASP.NET Core — только предупреждения и ошибки |

Текст каждого запроса к базе пишет в журнал категория `Logging:LogLevel:Microsoft.EntityFrameworkCore.Database.Command`: по умолчанию она следует `Default` (`Information`), на стенде compose ставит `Warning`, чтобы журнал оставался читаемым. Для разбора ошибки базы её можно временно вернуть к `Information`.

### База данных

| Ключ | По умолчанию | Стенд | Смысл |
| --- | --- | --- | --- |

<a id="settings-jobs"></a>
### Фоновые задачи и напоминания

| Ключ | По умолчанию | Смысл |
| --- | --- | --- |
| `Jobs:Enabled` | `true`; `false` в окружении Testing | Сервер фоновых задач и панель `/hangfire`. Без него не идут импорт, печать, почта, напоминания |
| `Jobs:QueuePollSeconds` | 5, от 0,5 до 300 | Как часто сервер задач сам заглядывает в очередь. Печать от опроса не зависит: исполнителя будят сразу; опрос — страховка для задач, вернувшихся в очередь без сигнала. Каждый опрос — запрос к базе |
| `Jobs:GenerationWorkers` | 2, от 1 до 20 | Сколько документов формируется одновременно. Конвертер обрабатывает файлы по очереди: больше двух исполнителей время не сокращают (замер этапа 8) |

На стенде эти ключи берутся из `appsettings.json`; менять — файлом override (раздел [«Где задаются настройки»](#settings-where)).

<a id="settings-generation"></a>
### Печать, файлы и правила проверки

| Ключ | По умолчанию | Стенд | Смысл |
| --- | --- | --- | --- |
| `Converter:Url` | `http://localhost:3000` | `http://converter:3000` | Адрес конвертера Gotenberg |
| `Converter:TimeoutSeconds` | 120 | — | Сколько секунд хост ждёт PDF. nginx ждёт ответа 180 с: поднимая предел, поднять и `proxy_read_timeout` в `deploy/nginx/templates/default.conf.template` |

| `ValidationRules:LiteratureMainMin` | 3 | `appsettings.json` | Записей основной литературы меньше — предупреждение (Положение о рабочих программах, п. 4.1) |

nginx пропускает запрос до 64 МБ (`client_max_body_size`): импорт — три файла одним запросом. Поднимая `Imports:MaxFileBytes` выше 20 МБ, поднять и этот предел.

<a id="settings-fixed"></a>
### Что не настраивается

Эти значения заданы в коде; менять их — изменение программы:

- **Пароль:** не короче 8 символов, заглавная и строчная буквы, цифра, спецсимвол (правила ASP.NET Core Identity); email учётной записи уникален.
- **Блокировка входа:** после 5 неудачных попыток подряд вход блокируется на время, заданное ASP.NET Core Identity по умолчанию (5 минут).
- **Рисунок в документе** — до 2 МБ.
- **Порт хоста** внутри контейнера — 8080, конечные точки входа — `/connect/*`, клиент OIDC — `rpdfos-web`.
- **Очереди и исполнители** импорта и почты — по одному.

<a id="settings-startup"></a>
### Проверки при запуске

Хост не стартует, если настройка неверна, и пишет причину в журнал (`docker compose logs api`):

| Сообщение (начало) | Что исправить |
| --- | --- |
| «Не задана строка подключения ConnectionStrings:Default» | Строку подключения |
| «Не задан пароль сертификатов — настройка Auth:CertificatePassword» | `CERT_PASSWORD` в `.env` |
| «Не задан файл сертификата …», «Файл сертификата … не найден» | Выпустить сертификаты входа: `docker compose run --rm certs auth` |
| «Не удалось прочитать сертификат …: неверный пароль» | `CERT_PASSWORD` не совпадает с паролем выпуска: выпустить заново |
| «Сертификат … не действует на сегодня» | Срок истёк: `docker compose run --rm certs auth`, затем `docker compose restart api` |
| «Не задана папка ключей Data Protection» | `DataProtection:KeysPath` (в образе задана; проверить, не перекрыта ли) |
| «Не задан адрес системы», «нужен абсолютный адрес https» | `Auth:PublicUrl`, то есть `STAND_HOST` |
| «Mail:From — адрес отправителя не разобрать» | `MAIL_FROM` |
| «Mail:DigestHour — час от 0 до 23», «Reminders:Hour — час от 0 до 23» | Час |
| «Reminders:Hour (…) должен быть раньше Mail:DigestHour (…)» | Час напоминаний или дайджеста |
| «Reminders:ReworkDays — не меньше 2 дней…» | Срок доработки и предупреждения |
| «Настройка Jobs:QueuePollSeconds = …», «Настройка Jobs:GenerationWorkers = …» | Значение в допустимых пределах |
| «Не удалось создать администратора: …» | `ADMIN_PASSWORD` не проходит правила пароля |

Compose сам останавливается с «required variable … is missing», если пусты `STAND_HOST`, `DB_PASSWORD` или `CERT_PASSWORD`.

<a id="backup"></a>
## Резервное копирование

Служба `backup` каждую ночь в `BACKUP_TIME` снимает копию базы (`pg_dump`, формат custom) в папку `BACKUP_DIR` под именем `rpdfos-ГГГГММДД-ЧЧММСС.dump` и хранит `BACKUP_KEEP` последних; лишние старые удаляются только после удачной новой. Если компьютер ночью был выключен, копия делается сразу после включения; при ошибке служба повторяет попытку каждый час. Каждая новая копия перед сохранением читается `pg_restore --list`: битый файл не заменяет хорошие.

**Что входит.** Вся база: исходные файлы импорта, шаблоны оформления, рисунки, документы и их версии, справочники, пользователи и роли, уведомления, журнал аудита, очередь задач. Копии базы достаточно, чтобы восстановить систему. Сформированные PDF и DOCX не входят: их формируют заново.

**Что копировать вручную, один раз** и хранить отдельно от компьютера: `deploy/.env`, папку `deploy/certs/` (ключ корневого `ca.key` — отдельно на носителе) и ключи Data Protection (команда в разделе 8 инструкции; обновлять после смены `.env` и раз в квартал). Эти файлы содержат секреты.

**Где хранить.** Папка копий — лучше на другом диске, чем том базы, ещё лучше — сетевая папка или съёмный носитель: копия на том же диске не спасёт от его отказа. Объём: `BACKUP_KEEP` × размер копии; копия базы разработки с 23 учебными планами и 57 документами — около 7 МБ.

| Действие | Команда (в папке `deploy`) |
| --- | --- |
| Копия сейчас | `docker compose run --rm backup now` |
| Список копий | `docker compose run --rm backup list` |
| Проверить последнюю или названную | `docker compose run --rm backup verify [файл]` |
| Восстановить | `docker compose run --rm backup restore [файл] [--replace]` |
| Состояние службы | `docker compose ps backup` — `unhealthy`, если за сутки копии не было |
| Журнал службы | `docker compose logs backup` |

<a id="backup-verify"></a>
### Проверка копий

`verify` восстанавливает копию во временную базу, не трогая базу стенда, и показывает число записей: сотрудников, учебных планов, шаблонов, документов, исходных файлов, рисунков — и последнюю миграцию. Проверять раз в неделю, после каждого обновления и перед переносом. Сверить числа с тем, что видят пользователи: копия, которую не удалось восстановить или в которой нет последних документов, — не копия.

<a id="restore"></a>
### Восстановление

Порядок — раздел 8 инструкции, «Восстановление». Главное:

- Копия сначала разворачивается во временную базу и подменяет базу стенда только после успешного восстановления: неудача базу не тронет.
- Перед восстановлением остановить хост: `docker compose stop api`.
- **База потеряна** (том удалён или повреждён): `docker compose down`, `docker volume rm rpdfos-stand_dbdata`, затем `docker compose run --rm backup restore` — пустая база поднимется сама. Если потеряны и ключи Data Protection — вернуть их. Затем `docker compose up -d --wait`.
- **Вернуться к прежним данным** работающего стенда: `restore <файл> --replace`. Перед заменой команда сохраняет текущие данные копией `before-restore-…` (в 30 хранимых она не входит, удалить вручную). Всё, что внесено после копии, пропадёт — предупредить пользователей.
- Копию старой версии можно восстановить на новой: хост применит миграции при запуске. Копию новой версии на старой — нельзя.
- Сформированные файлы, которых нет на томе, после восстановления не скачать («файл удалён по сроку хранения»): документ формируют заново.

## Журналы и диагностика

<a id="health"></a>
### Состояние служб

| Что проверить | Как |
| --- | --- |
| Хост отвечает | `https://<имя стенда>/health` → `{"status":"ok"}`. Отвечает без входа; базу и конвертер не проверяет |
| Все службы | `docker compose ps`: `healthy` у `proxy`, `api`, `db`, `converter`, `backup`. У `mail` проверки нет — смотреть его журнал |
| Хост изнутри | Проверка образа сама запрашивает `/health` каждые 15 с; `unhealthy` — хост завис или не стартовал |
| Конвертер | `docker compose ps converter`; печать PDF у пользователя |

| Сертификаты | `docker compose run --rm certs show` — сроки |
| Место на диске | `docker system df`; папка копий |

<a id="logs"></a>
### Журналы контейнеров

Журналы — драйвер `json-file`, не больше 50 МБ на службу (5 файлов по 10 МБ), старые записи вытесняются.

```powershell
docker compose logs -f --tail 100 api
```

| Служба | Что искать |
| --- | --- |
| `api` | Ошибки запуска (называют настройку), исключения обработки запросов, сбои задач Hangfire, ошибки отправки писем, предупреждения засева («Администратора нет», «не связана со справочником сотрудников») |
| `proxy` | Запросы: адрес, время, метод, путь, код, размер, длительность. Строки запроса (`?…`) в журнале нет: в ней бывают коды входа и токены ссылок из писем |
| `db` | Ошибки подключения, нехватка места |
| `converter` | Ошибки преобразования DOCX → PDF |
| `mail` | Ответы серверов получателей: `status=sent`, `bounced` с кодом, `Connection timed out` |
| `backup` | Время и размер копий, ошибки |

Журнал хоста пишется на русском, где сообщение формирует система, и на английском у библиотек. Действий с учётными записями (создание, роли, пароли) в журнале аудита нет — их следы ищут здесь.

Очередь почты: `docker compose exec mail postqueue -p` — показать, `docker compose exec mail postqueue -f` — повторить сейчас.

<a id="hangfire"></a>
### Панель фоновых задач

`https://<имя стенда>/hangfire` — панель Hangfire «Фоновые задачи», только для роли «Администратор». Вход — через страницу входа системы (куки входа, а не токен клиента): если вход не выполнен, панель отправит на страницу входа.

В панели видно: очереди `parsing`, `generation`, `mail` и задачи в них; выполненные и неудачные задачи с текстом исключения; повторяющиеся задачи `generated-files-cleanup`, `notification-mail`, `rework-reminders` с временем следующего запуска; серверы — по одному на очередь (`<компьютер>:parsing` и т. д.).

Повторяющуюся задачу можно запустить вручную («Trigger now»), например напоминания после смены их часа. Неудачная задача остаётся в списке «Failed» с текстом ошибки, пока её не удалят в панели: импорт и печать при этом уже сообщили об ошибке пользователю, повторять их из панели не нужно — пользователь запускает их снова.

<a id="database-access"></a>
### Запросы к базе

Для разбора на стенде — `psql` внутри контейнера базы, только для чтения:

```powershell
docker compose exec db psql -U rpdfos -d rpdfos
```

Полезно: `\dt` — таблицы, `select migration_id from "__EFMigrationsHistory" order by 1 desc limit 1;` — последняя миграция, `select status, count(*) from documents group by 1;` — документы по статусам. Изменять данные запросами нельзя: перехватчик версий, журнал аудита и правила статусов работают только через приложение.

<a id="maintenance"></a>
### Регламент обслуживания

| Когда | Что сделать |
| --- | --- |
| Каждый рабочий день | Открывается ли главная страница; `docker compose ps` — все службы `healthy` |
| Раз в неделю | `docker compose run --rm backup verify`; место на диске (`docker system df`, папка копий); при включённой почте — очередь `docker compose exec mail postqueue -p` пуста или почти пуста; панель `/hangfire` — нет ли новых неудачных задач |
| Раз в месяц | Обновления Windows или Linux и Docker — с перезагрузкой в нерабочее время; после неё стенд поднялся сам (`docker compose ps`) |
| Раз в квартал | Копия ключей Data Protection; копия `.env` и `certs` вне компьютера актуальна; сроки сертификатов (`docker compose run --rm certs show`) |
| Перед обновлением версии | Копия базы `backup now` и её проверка; предупредить пользователей |
| После обновления | `/health`, вход, документ, печать PDF; `backup verify` |
| Смена сотрудника-администратора | Передать `.env`, носитель с `ca.key`, доступ к компьютеру; новому администратору — учётную запись с ролью «Администратор», прежнюю отключить |
| Конец апробации | Копия базы; удалить корневой с компьютеров пользователей (`certutil -delstore Root "RPD-FOS stand root (<имя стенда>)"`); снять стенд — `docker compose down`, с данными — `down -v` только после проверенной копии |

<a id="troubleshooting"></a>
### Если не работает

Таблица признаков — раздел 9 инструкции стенда. Дополнительно:

| Признак | Причина и действие |
| --- | --- |
| Главная открывается пустой после обновления | Браузер держит старый клиент: Ctrl+F5. `index.html` хост отдаёт без кэша, остальные файлы — с хешами в имени |
| Импорт или печать «висят» | Панель `/hangfire`: есть ли сервер очереди, нет ли задачи с ошибкой; `docker compose ps converter` |

| После восстановления все вышли из системы, ссылки из писем не работают | Ключи Data Protection не восстановлены: вернуть их из копии или попросить пользователей войти и запросить ссылки заново |

<a id="database"></a>
## База данных

База — PostgreSQL 17, одна база `rpdfos`, пользователь `rpdfos`. Схема `public` — таблицы приложения, Identity и OpenIddict; схема `hangfire` — хранилище фоновых задач, её создаёт и обновляет сам Hangfire. Имена своих таблиц и колонок — snake_case; таблицы Identity и OpenIddict сохраняют имена библиотек (`AspNetUsers`, `OpenIddictTokens`).

Проект схемы — `docs/design/ВКР_2_Структура_данных.md`: контексты — раздел «Предметные области (контексты) схемы», таблицы — «Спецификация сущностей», уточнения — «Правки по ревизии архитектуры».

Хранение гибридное: критичные поля нормализованы (статус, дисциплина, автор, версия), содержимое документа — в колонке `payload` типа `jsonb`, его структуру задаёт JSON Schema шаблона. Оптимистичная блокировка — колонка версии, её увеличивает перехватчик при каждом сохранении. Удаление мягкое: статус `deleted` и флаг `is_deleted`.

| `parser_runs`, `directory_imports` | Запуски разбора учебного плана и компетенций, загрузки файла должностей: статус, итог, замечания |
| `generation_tasks`, `generated_files` | Задачи печати и сформированные файлы: формат, путь на томе, срок хранения |
| `audit_log` | Журнал аудита: кто, когда, действие, объект, подробности |
| `notifications` | Лента уведомлений: адресат, событие, прочитано ли, отправлено ли письмом |

Учётная запись и сотрудник — разные записи: `AspNetUsers` — только для входа (email, хеш пароля, признак обязательной смены пароля), `users` — справочник для документов и подписей. Связь — колонка `users.identity_subject`.

<a id="migrations"></a>
### Миграции

Схема меняется только миграциями EF Core; они лежат в `src/RpdFos.Core/Migrations` (24 миграции, от `20261018082532_Initial` до `20261125060123_DepartmentEditedManually` на момент выпуска руководства). Существующие миграции не правятся, данные миграциями не удаляются.

- На стенде миграции применяет хост при запуске (`Database:AutoMigrate`); обновление версии — это и обновление схемы.
- Применённые миграции — таблица `__EFMigrationsHistory`; последняя видна и в выводе `backup verify`.
- Откат миграции не предусмотрен: вернуться к прежней версии можно только восстановлением копии, снятой до обновления.
- Новую миграцию создаёт разработчик: `dotnet ef migrations add <Имя> -p src/RpdFos.Core -s src/RpdFos.Api`.

Объём данных по оценке проекта — 5–10 ГБ за 5 лет; основной вес — исходные файлы, шаблоны оформления и версии документов.

<a id="api"></a>
## API

API — REST поверх HTTPS, JSON. Все адреса `/api/…` требуют токен доступа (заголовок `Authorization: Bearer …`), роли берутся из токена. Токен выдаёт сервер авторизации хоста по OpenID Connect: описание — `https://<имя стенда>/.well-known/openid-configuration`; зарегистрирован один клиент — веб-приложение `rpdfos-web` (публичный, authorization code с PKCE). Ключей для сторонних программ нет.

Ошибки — в формате ProblemDetails (RFC 9457) с русским заголовком: 401 и 403 — доступ, 404 — не найдено, 409 — конфликт состояния или версии (документ изменил другой пользователь), 422 — неверные данные.

| Группа адресов | Что |
| --- | --- |
| `/api/documents` | Документы РПД и ФОС: создание, содержимое, проверка, переходы статусов, замечания, история |

| `/api/templates` | Шаблоны и файлы оформления |
| `/api/imports`, `/api/curriculum-plans` | Импорт исходных файлов, учебные планы |
| `/api/discipline-assignments` | Закрепление дисциплин |
| `/api/notifications`, `/api/profile` | Уведомления, профиль |
| `/api/directory` | Поиск по справочнику сотрудников |
| `/api/admin/users`, `/api/admin/directory`, `/api/admin/departments` | Администрирование: учётные записи, справочник, кафедры |

<a id="openapi"></a>
### Описание OpenAPI

Описание OpenAPI 3 строит сам хост (NFR-SUP-02), но **только в окружении Development**: на стенде адреса `/openapi/v1.json` и `/swagger` закрыты, чтобы не раскрывать устройство API в сети кафедры.

Получить описание той же версии — на компьютере разработчика: .NET SDK 10, Docker и доверенный сертификат разработки (`dotnet dev-certs https --trust`; подробнее — `README.md`, раздел «Запуск»).

```powershell
docker compose up -d db
```

```powershell
dotnet run --project src/RpdFos.Api
```

Затем `https://localhost:5081/openapi/v1.json` — описание в JSON, `https://localhost:5081/swagger` — его просмотр. Для описания хватает пустой базы разработки; исходники — того же выпуска, что на стенде (`git checkout` тега версии).

<a id="development"></a>
### Разработка и тесты

Для доработки системы нужны .NET SDK 10 (точная версия — `global.json`) и Docker. Подробности — `README.md`, соглашения кода — `CLAUDE.md`.

| Шаг | Команда |
| --- | --- |
| Доверить сертификат разработки (один раз) | `dotnet dev-certs https --trust` |
| База, конвертер, ловушка почты | `docker compose up -d db converter mail` — корневой `docker-compose.yml` |
| Первый администратор (один раз) | `dotnet user-secrets set "Seed:AdminEmail" …` и `"Seed:AdminPassword"` в проекте `src/RpdFos.Api` |
| Запуск | `dotnet run --project src/RpdFos.Api` — профиль `https`, окружение Development, `https://localhost:5081` |
| Сборка | `dotnet build` — без ошибок и предупреждений |
| Тесты | `dotnet test`; интеграционные тесты поднимают PostgreSQL в Testcontainers |
| Новая миграция | `dotnet ef migrations add <Имя> -p src/RpdFos.Core -s src/RpdFos.Api` |
| Образ хоста | `docker build -t rpdfos-api .` из корня репозитория |
| Руководства в PDF | `dotnet run --project tools/RpdFos.Manuals` |

В разработке: ловушка Mailpit принимает все письма и показывает их на `http://localhost:8025` — наружу ничего не уходит; база — на порту 5432 с паролем из `appsettings.json`; описание API и панель задач открыты по адресам из раздела [«Описание OpenAPI»](#openapi) и `/hangfire`. Миграции и начальные данные применяются при запуске (`appsettings.Development.json`).

Сборка образа публикует хост и отдельно клиент и заменяет файлы клиента в образе: если в `index.html` осталась заготовка `{fingerprint}`, сборка останавливается — иначе страница открывалась бы пустой. Образ запускается под пользователем `app` без прав root, слушает порт 8080, окружение — `Production`.

Команда сборки руководств заодно проверяет их: ссылки, якоря разделов, снимки и то, что каждая настройка из `appsettings*.json`, образца `.env`, compose стенда, `Dockerfile` и ключей, которые хост читает в коде, описана в этом руководстве (с `-- --check` — только проверка). Новая настройка без строки в разделе [«Настройки»](#settings) остановит и сборку руководств, и тесты.

<a id="admin"></a>
## Администратору

Раздел — для пользователя с ролью «Администратор». Администратор ведёт учётные записи, справочник сотрудников и кафедры, смотрит журнал аудита и панель фоновых задач. Кроме того, у него права автора документа, импорта и закрепления дисциплин (как у методиста) и принудительная смена статуса документа.

В меню администратора, кроме общих страниц, — «Пользователи», «Справочник сотрудников», «Кафедры», «Журнал аудита». Ссылка на панель фоновых задач — на главной странице.

<a id="admin-roles"></a>
### Роли

| Роль | Что разрешает |
| --- | --- |
| «Преподаватель» | Создавать и заполнять свои РПД и ФОС, печатать, отправлять на проверку; читать документы закреплённых дисциплин |
| «Методист» | Импорт учебных планов и компетенций, шаблоны, проверка документов (принять, вернуть, замечания), закрепление дисциплин, назначение согласующих; видит все документы |
| «Утверждающий» | Очередь «Согласование», отметки там, где он назначен согласующим, замечания |
| «Администратор» | Страницы этого раздела, панель `/hangfire`, принудительная смена статуса; права автора, импорта и закрепления |

У одной учётной записи может быть несколько ролей: заведующий кафедрой — и преподаватель, и утверждающий. Новые роли вошедший пользователь получит при следующем входе.

<a id="admin-users"></a>
### Учётные записи

Страница «Пользователи». В таблице — «Email», «ФИО», «Роли», «Запись справочника сотрудников» («— не связана», если связи нет) и состояние «Учётная запись»: «активна» или «отключена — вход запрещён», с пометками «пароль не задан» и «пароль временный — сменит при входе».

**Создать пользователя** — форма «Новый пользователь»:

1. «Email» — адрес входа и писем; уникален.
2. «ФИО полностью».
3. «Временный пароль» — необязательно. Задан — сообщите его человеку, при первом входе он задаст свой. Не задан — войти нельзя, пока человек не задаст пароль по приглашению.
4. «Роли» — хотя бы одна. Роль «Преподаватель» отмечена заранее: снимите её, если она не нужна.
5. «Запись справочника сотрудников» — если человек уже есть в справочнике (например, заведующий из файла должностей), найдите его по фамилии и нажмите «Выбрать»: учётная запись будет связана с этой записью. Ищутся только активные записи без учётной записи. Не выбрана — будет создана новая запись справочника.
6. «Создать». Учётная запись, роли и запись справочника создаются вместе: при ошибке не создаётся ничего.

Приглашение при создании само не отправляется: если пароль не задан, система напомнит «отправьте приглашение кнопкой в строке пользователя».

**Как человек получает пароль** — два способа:

- **Временный пароль** — при создании или кнопкой «Новый пароль» в строке пользователя. При входе с ним человек попадает на страницу «Смена пароля» («Администратор задал вам временный пароль. Задайте свой, и вход продолжится.») и задаёт свой — он должен отличаться от временного. Пока пароль не сменён, работать в системе нельзя. Любой пароль, заданный администратором, — временный: постоянного пароля за человека администратор не задаёт. «Новый пароль» заодно снимает временную блокировку после неудачных попыток. Этот способ работает без почты — на апробации он основной.
- **Приглашение** — кнопка «Отправить приглашение» у активной учётной записи. Письмо «Приглашение в систему создания РПД и ФОС — задайте пароль» со ссылкой на страницу «Новый пароль»; ссылка одноразовая и действует `Accounts:InviteLinkHours` часов (трое суток). Отправить можно повторно. Если письмо не ушло, система называет причину: «Не задан адрес системы» (нет `Mail:PublicUrl`), «Почтовый сервер не принял письмо» — «Проверьте адрес…», «Почтовый сервер недоступен» — повторить позже или задать временный пароль.

Приглашение, «Забыли пароль?» и подтверждение смены email — служебные письма: они уходят сразу через сервер из настроек `Mail:Host` и `Mail:Port`, без очереди и без настроек уведомлений, **в том числе при `Mail:Enabled=false`** — эта настройка выключает только письма уведомлений. На стенде с пустым `MAIL_ENABLED` служебные письма отдаются службе `mail`.

**Правила пароля:** не короче 8 символов, заглавная и строчная буквы, цифра и знак, не буква и не цифра (например, «-» или «!»). Ошибки называют правило: «В пароле нужна хотя бы одна цифра.» и т. п.

**Блокировка.** После 5 неудачных попыток входа подряд — «Учётная запись временно заблокирована после нескольких неудачных попыток.» на 5 минут. Отдельной кнопки разблокировки нет: блокировка снимается сама, «Новым паролем» или паролем, заданным по ссылке из письма. В таблице временно заблокированная запись показана как «активна».

**Изменить роли** — кнопка в строке, флажки, «Сохранить». Новый набор заменяет прежний. Снять роль администратора с себя нельзя.

**Отключить и вернуть.** «Отключить» запрещает вход бессрочно и прерывает действующие сеансы; запись справочника, документы и подписи остаются. При входе человек видит «Учётная запись отключена администратором.» «Вернуть» снимает запрет. Отключить себя нельзя. Удаления учётных записей нет: уволенного сотрудника отключают, а его должность передают в справочнике.

**Email** человек меняет сам в профиле, с подтверждением по старому и новому адресу; ФИО, кафедру, должность и степень — администратор в справочнике сотрудников.

<a id="admin-employees"></a>
### Справочник сотрудников

Страница «Справочник сотрудников». Справочник — это люди для документов: авторы, заведующие, директора институтов, председатели УМК, руководители служб, которые подписывают листы согласования. В нём есть и люди без входа в систему — подписанты. Учётная запись и запись справочника — разные вещи, связь у них одна к одной.

Чтобы менять справочник, у самого администратора должна быть запись в нём (у первого администратора она создаётся при запуске); иначе — «Нет записи в справочнике сотрудников».

**Файл должностей.** Карточка «Загрузить файл должностей (.xlsx)», кнопка «Загрузить». Разбор идёт в фоне (очередь `parsing`); итог — «Последняя загрузка: …», «добавлено X, обновлено Y, снято с должности Z» и «Замечания» со списком. Записи добавляются и обновляются по официальному названию должности; если на должности сменился человек, прежняя запись освобождается; записей, которых нет в файле, загрузка не трогает. Кафедры берутся только из справочника кафедр учебного плана: план загружают раньше файла должностей. Тот же файл повторно не сохраняется. Предел размера — `Imports:MaxFileBytes`.

**Поиск.** «Фамилия», «Категория подписанта», «показывать неактивные», «Найти». Колонки: «Фамилия И. О.», «Подпись в документах», «Должность», «Официальное название», «Кафедра / институт / направление», «Категория подписанта», «Учётная запись», «Активна».

**Запись** — «Добавить запись» или «Изменить»: «Фамилия И. О.» (обязательно), «Подпись в документах» (по умолчанию «И. О. Фамилия»), «ФИО полностью», «Должность», «Учёная степень», «Email», «Официальное название (место)», «Категория подписанта». У записи, связанной с учётной записью, email — адрес входа, здесь он не меняется. Записи, созданные здесь, — без входа; вход даёт учётная запись на странице «Пользователи».

Категория подписанта определяет, в какой лист согласования человек попадёт: «Заведующий кафедрой» и «Исполняющий обязанности заведующего кафедрой» (нужна кафедра), «Директор института» (нужен институт), «Председатель учебно-методической комиссии» (нужно направление подготовки: он подписывает листы РПД и ФОС этого направления), «Ректор», «Проректор по образовательной деятельности», «Начальник учебно-методического управления», «Директор научно-технической библиотеки», «Начальник управления информационно-технической поддержки». Место подписанта одно: один заведующий на кафедру, один директор на институт, один председатель на направление.

**Смена человека на должности** — «Сменить сотрудника» в строке: выбрать запись справочника без должности или ввести нового сотрудника. Прежняя запись теряет место; без учётной записи она становится неактивной, с учётной записью — остаётся активной. Занять официальное название, которое уже у другого, можно только так — иначе «Официальное название занято».

**Деактивировать и вернуть.** Неактивная запись не предлагается в подписанты и при связывании; созданные документы с ней не меняются.

Если подписант не найден при согласовании или в печати — проверить категорию, кафедру (институт, направление) и активность записи.

<a id="admin-departments"></a>
### Кафедры

Страница «Кафедры»: «Номер», «Название», «Краткое название», «Институт». Номер и институт приходят из учебного плана и файла должностей; администратор правит только название (до 255 знаков) и краткое название (до 50) — кнопка «Изменить», «Сохранить». Названия и краткие названия кафедр не повторяются.

Исправленное вручную название помечено значком «исправлено»: импорт плана его не переписывает, а пишет предупреждение «…оставлено исправленное». Новое название получают новые документы; в созданных остаётся то, что было при создании (поля из плана в документе правит методист). Заведующий кафедрой задаётся в справочнике сотрудников, а не здесь.

<a id="admin-audit"></a>
### Журнал аудита

Страница «Журнал аудита» — значимые действия с документами и справочниками (FR-ADM-02): кто, когда, что сделал и с каким объектом. Фильтры: «Пользователь», «С», «По (включительно)», «Событие»; «Показать», «Сбросить». Границы суток — по поясу сервера. Записи подгружаются по 50 кнопкой «Показать ещё»; документ открывается ссылкой из колонки «Объект». Действия системы помечены «система».

Что записывается: исправление полей учебного плана в документе, удаление черновика, возврат на исправление, принудительная смена статуса, архив, передача другому автору, создание на основе, пометка «устарел», обновление снимка РПД, перенумерация банка заданий, круг согласования (начало, отметки, возврат, назначение согласующего), закрепление дисциплин, изменения справочника сотрудников и кафедр, привязка строк матрицы. Переходы статусов документа видны и в разделе «История» на странице документа.

Чего в журнале нет: входов в систему и действий с учётными записями (создание, роли, пароли, отключение). Журнал только для чтения и не очищается; экспорт — перспектива (FR-ADM-07).

<a id="admin-status"></a>
### Принудительная смена статуса

На странице документа у администратора — «Сменить статус»: для нештатных ситуаций, только назад — в «Сохранённый черновик», «На доработке» или «На проверке», из любого статуса, кроме удалённого. Комментарий обязателен. Переход записывается в историю статусов и журнал аудита, автор и методисты получают уведомление; с согласования круг прерывается, как при возврате. Обычная работа с документом — по [руководству методиста](methodist.md).
