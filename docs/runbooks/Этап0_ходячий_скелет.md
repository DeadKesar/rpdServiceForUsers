# Прототип. Этап 0: ходячий скелет (runbook, скелет v2)

*Рабочий документ этапа реализации и материал для главы 4 (организация разработки). Скелет — в `rpd-fos-skeleton-v2.zip`.*

## Как стартуют проект в индустрии — и как это ложится на нас

**Ходячий скелет (walking skeleton).** Первая цель — не функциональность, а тончайший сквозной путь через все слои: запрос → API → база данных → ответ, при инфраструктуре, которая поднимается одной командой. Стыковые риски (фреймворки, миграции, конфигурация) проявляются в первые дни, когда исправление дёшево.

**Порядок по риску.** После скелета делается самое рискованное: связка Blazor и сервера аутентификации (риск 4) — этап 1.

**Вертикальные срезы.** Каждый инкремент — целая ниточка: эндпоинт + миграция + страница. Первые два среза уже в скелете: создание шаблона и его публикация.

**Дисциплина с первого коммита.** База данных меняется только миграциями. Оптимистичная блокировка и единая обработка ошибок работают с первого дня. Тесты — с первого дня. Мелкие коммиты, тег на каждую веху.

**Критерий готовности среза:** компилируется; миграция применяется на чистой базе; эндпоинт работает в Swagger UI; тесты зелёные; закоммичено с осмысленным сообщением.

## Что изменилось в v2

1. **Два проекта.** `RpdFos.Core` (сущности, `AppDbContext`, миграции, сквозные механизмы) и `RpdFos.Api` (хост и модули Carter). Это общее прикладное ядро из ревизии архитектуры: на этапе 2 его подключит фоновый обработчик, и миграции не придётся переносить.
2. **Swagger UI вместо Scalar.** Описание API строит встроенный `Microsoft.AspNetCore.OpenApi`, страница — `/swagger`.
3. **Перехватчик версий** `VersioningInterceptor`: при каждом сохранении сам увеличивает `Version` и проставляет `UpdatedAt`.
4. **Единая обработка ошибок.** Ответы об ошибках — в формате ProblemDetails; конфликт версий превращается в 409 в одном месте (`ConcurrencyExceptionHandler`), без `try/catch` в эндпоинтах.
5. **Второй срез — публикация шаблона** из нашего урока: образец «смена статуса + проверка версии».

Мелочи: тест правил переходов; `global.json` фиксирует SDK .NET 10; `.gitattributes` нормализует окончания строк для Windows; строка подключения для разработки — в `appsettings.json`; создание Blazor-проекта перенесено на этап 1.

## Шаги этапа 0

**0. Префлайт.** `dotnet --version` → 10.x. Docker Desktop запущен. Порт 5432 свободен. Проект — в папке без пробелов и кириллицы, например `C:\work\rpd-fos`: некоторые инструменты сборки и Docker плохо переносят такие пути.

**1. Репозиторий.**
```
cd C:\work
# распаковать сюда rpd-fos-skeleton-v2.zip -> C:\work\rpd-fos
cd rpd-fos
git init -b main
git add -A
git commit -m "chore: walking skeleton v2"
```
Создать приватный репозиторий на GitHub и выполнить `git remote add origin <адрес>` и `git push -u origin main`.

**2. Solution.**
```
dotnet new sln -n RpdFos
dotnet sln add src/RpdFos.Core src/RpdFos.Api tests/RpdFos.Api.Tests
```

**3. База данных.**
```
docker compose up -d db
docker compose ps        # ждать состояния healthy
```

**4. Зависимости.** Версии пакетов в csproj ориентировочные — сначала их актуализировать:
```
dotnet restore
dotnet list package --outdated
```
Поднять версии в csproj до последних стабильных и повторить `dotnet restore`.

**5. Первая миграция.** Миграции живут в ядре (`-p`), а строку подключения и регистрацию берут из хоста (`-s`):
```
dotnet tool install --global dotnet-ef
dotnet ef migrations add Initial -p src/RpdFos.Core -s src/RpdFos.Api
```
Миграция появится в `src/RpdFos.Core/Migrations`. Прочитать её метод `Up` глазами: таблица `document_templates`, колонки в snake_case.

**6. Запуск.**
```
dotnet run --project src/RpdFos.Api
```
Откроется http://localhost:5080/swagger. Миграция применится сама: в окружении Development включено автоприменение.
- http://localhost:5080/health → `{"status":"ok"}`.
- Таблица в базе: `docker compose exec db psql -U rpdfos -c "\dt"` → `document_templates`.

**7. Проверка срезов** через Swagger UI:

| Запрос | Ожидаемый ответ |
| --- | --- |
| `POST /api/templates` с `{"type":"rpd","name":"Тест","year":2026}` | 201, `status: empty`, `version: 1` — скопировать `id` |
| `POST /api/templates/{id}/publish` с `{"version":1}` | 200, `status: published`, `version: 2` — версию увеличил перехватчик |
| Тот же запрос ещё раз | 409 «Переход статуса невозможен» |
| Новый шаблон, публикация с `{"version":999}` | 409 «Конфликт версий» — от `ConcurrencyExceptionHandler` |
| `POST /api/templates/00000000-0000-0000-0000-000000000000/publish` | 404 |
| `POST /api/templates` с `{"type":"xxx","name":"Тест","year":2026}` | 422 «Неизвестный тип документа» |

**8. Тесты.** `dotnet test` → 7 тестов зелёные: smoke-тест и шесть случаев правила публикации.

**9. Веха.**
```
git add -A
git commit -m "feat: walking skeleton v2 - api, core, db, two slices"
git tag -a v0.1 -m "Этап 0: ходячий скелет"
git push --follow-tags
```

## Упражнение: архивирование

Эндпоинт `POST /api/templates/{id}/archive` (Опубликован → Архивный) по образцу публикации:
1. В `TemplateTransitions` — правило `CanArchive`.
2. В `TemplateTransitionsTests` — случаи для него.
3. В `TemplatesModule` — эндпоинт той же формы: загрузить → 404 → правило (409) → изменить → сохранить.
4. Проверить через Swagger UI: 200 для опубликованного, 409 для неопубликованного, 409 при чужой версии.

## Если что-то не так

| Симптом | Что делать |
| --- | --- |
| `restore`: не найдена версия пакета | `dotnet add src/RpdFos.Api package <имя>` без версии поставит последнюю |
| «A compatible .NET SDK was not found» | Установить .NET 10 SDK (его требует `global.json`) |
| `dotnet ef`: «Unable to create a DbContext» | Проверить ключ `-s src/RpdFos.Api` и что решение собирается (`dotnet build`) |
| Порт 5432 занят | В `docker-compose.yml` — `"5433:5432"`, в `appsettings.json` — `Port=5433` |
| Миграция не применилась при запуске | Окружение должно быть Development: запускать через `dotnet run`, профиль из `launchSettings.json` |

## Git-конвенции (соло-режим)

Ветка `main`, trunk-based; feature-ветки — по желанию для крупных кусков. Сообщения коммитов: `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`. Тег на каждую веху плана: `v0.1` … `v0.7`, только аннотированный (`git tag -a v0.2 -m "…"`): `--follow-tags` отправляет на GitHub только такие, а их дата и описание — готовая хронология для главы 4. Push — каждый день: это и резервная копия, и хронология для главы 4.

## Этап 1: PoC аутентификации

1. По итогам проверки лицензии выбрать сервер аутентификации: Duende IdentityServer (отдельный хост) или OpenIddict (внутри хоста API).
2. Решить, где хранить токен. Рекомендация — BFF: сессия в cookie, токены на сервере. От этого решения зависит шаблон Blazor-проекта: при BFF — `dotnet new blazor --interactivity WebAssembly`, без BFF — `dotnet new blazorwasm`.
3. Роли: teacher, methodist, approver, admin; `RequireAuthorization()` на изменяющих эндпоинтах.
4. Чекпойнт: вход тестовым пользователем — создание шаблона проходит; без входа — 401. Тег `v0.2`.
