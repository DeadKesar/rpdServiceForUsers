## Часть B. Этап 2 — парсер и справочники

**Цель:** методист загружает четыре реальных файла, система разбирает их в фоне и заполняет справочники. Ошибки разбора видны с привязкой к файлу, листу и строке.

**Входные материалы:**
- **Код генератора-предшественника** (автор тот же): https://github.com/DeadKesar/rpd. Логика разбора — в `DisciplineWorkProgram/Models/`: `Sections/Section.cs`, `Helpers.cs`, `Employee.cs`, `Discipline.cs`, `DisciplineDetails.cs`, `Sections/Helpers/*`, `Sections/RegexPatterns.cs`, а также чтение Excel и Word.
- **Реальные файлы** — у автора в `C:\work VKR\АКТ ВЕРС\recovery\04_Исходные_данные`: учебный план (`.xlsx`), список компетенций (`.docx`), матрица компетенций (`.docx`), должности (`.xlsx`).
- **Модель данных** — `docs/design/ВКР_2_Структура_данных.md`: контексты Reference и Infrastructure, а также раздел «Правки по ревизии архитектуры» в конце файла.

### B1. Интеграционные тесты с базой

Testcontainers (PostgreSQL 17) + `WebApplicationFactory`; фикстура применяет миграции. Тесты:
- публикация шаблона увеличивает версию;
- публикация с устаревшей версией → 409;
- преподаватель получает 403 на создание шаблона, методист — 201.

Аутентификацию подменить тестовой схемой только в тестовом проекте. Рабочие политики не менять.

### B2. Библиотека разбора `src/DisciplineDataExtractor`

Class library без зависимостей от `RpdFos.*`. Перенос логики генератора с исправлениями:
- **без статического состояния** — экземпляр на один разбор, параллельные разборы безопасны;
- **типизированный результат** вместо JSON-строки;
- ClosedXML для `.xlsx`, DocumentFormat.OpenXml для `.docx`; NPOI не подключать, если формат `.xls` не нужен;
- **ошибки — списком** `{файл, лист, строка, сообщение}` вместо исключений; частичный результат допустим.

Состав результата:
- **план:** направление, профиль, уровень, форма обучения, год набора, кафедры;
- **дисциплины:** индекс, название, блок (Б1/Б2/Б3/ФТД), часть, родитель (модуль или группа элективов), кафедра, ЗЕТ; по семестрам — часы по видам занятий и вид промежуточной аттестации;
- **компетенции:** код, формулировка, категория (для УК); индикаторы с типом (знать / уметь / владеть);
- **матрица:** связи дисциплина — компетенция — индикатор;
- **сотрудники:** ФИО, должность, формулировка должности для документа, институт или кафедра.

Тесты — проект `tests/DisciplineDataExtractor.Tests`, на реальных файлах: счётчики и точечные проверки (конкретная дисциплина, её часы по семестрам, её компетенции). Файлы плана и компетенций положить в `tests/fixtures/`. **Файл должностей — только обезличенная копия** (ФИО заменить), оригинал в репозиторий не попадает.

**Стоп — показать сводку разбора реальных файлов:** сколько дисциплин, компетенций, индикаторов, связей матрицы, сотрудников; список ошибок.

### B3. Модель справочников и миграция `AddReference`

Таблицы по `docs/design/ВКР_2_Структура_данных.md`:
- `institutes`, `departments`, `study_directions`, `study_profiles`, `fgos`;
- `competences`, `competence_indicators`;
- `curriculum_plans`, `disciplines` (иерархия `parent_id`; `block`, `part_type`, `entry_kind`), `discipline_semester_details`, `competence_matrix`;
- `users` — справочник сотрудников: `can_login`, `signatory_role`, `department_id`, `institute_id`, `identity_subject`;
- `uploaded_files` (`content bytea`, `checksum`), `parser_runs` (статус, счётчики, `errors_log jsonb`).

Отступления от документа — только по согласованию.

### B4. Конвейер импорта в Core

Результат разбора → справочники, в одной транзакции. Правила:
- **данные плана** (`curriculum_plans` и всё, что от него зависит) — новая версия плана на каждую загрузку;
- **общие справочники** (институты, кафедры, ФГОС, компетенции, индикаторы, сотрудники) — upsert по естественным ключам, без дублей при повторной загрузке;
- **журнал** — в `parser_runs`: `succeeded` / `partial` / `failed`, счётчики, ошибки.

Интеграционные тесты на реальных фикстурах, включая повторную загрузку тех же файлов.

**Стоп — показать, сколько строк появилось в каждой таблице после импорта реальных файлов.**

### B5. Hangfire в хосте API

- Хранилище — та же PostgreSQL, отдельная схема.
- Отдельная очередь разбора с одним исполнителем.
- Задача: прочитать файлы из `uploaded_files` → разбор → конвейер импорта.
- Панель Hangfire — только администратору.

### B6. API — модуль `Imports`

- `POST /api/imports` — multipart, четыре файла, роли methodist и admin. Проверка расширения, размера и дубликатов по `checksum`. Ответ — 202 и id запуска.
- `GET /api/imports/{id}` — статус, счётчики, ошибки.
- `GET /api/imports` — последние запуски.

### B7. Клиент — страница «Импорт данных»

Для методиста и администратора: выбор четырёх файлов, отправка, опрос статуса, сводка и таблица ошибок.

## Готово, когда

- Четыре реальных файла загружаются через страницу «Импорт данных», разбор идёт в фоне, справочники заполнены.
- Ошибки разбора видны с файлом, листом и строкой.
- Повторная загрузка тех же файлов не дублирует общие справочники и создаёт новую версию плана.
- Тесты: парсер на фикстурах, импорт с базой, механика версий, 409 и ролей. Сборка и тесты — без предупреждений.

**Вне этапа:** шаблоны (этап 3), документы, генерация; отметка документов, затронутых повторным импортом (перспектива).
