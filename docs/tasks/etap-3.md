## Часть A. Доработки этапа 2

**A1. Место подписанта отдельно от человека.** Сейчас при смене человека на должности прежняя запись справочника деактивируется целиком. Если за ней стоит учётная запись, человек теряет доступ: бывший заведующий, оставшийся преподавателем, получит 403. Новое правило:
- смена человека снимает с прежней записи место: `official_designation` и `signatory_role`;
- запись без учётной записи (`identity_subject IS NULL`) дополнительно получает `is_active = false`;
- запись с учётной записью остаётся активной.

История согласований не страдает: роль хранится в `document_signatures.role`, ссылка ведёт на того же человека. Тесты на оба случая; уточнение — в журнал.

**A2. Привязка к справочнику в интерфейсе.**
- `GET /api/admin/users` — список учётных записей: email, ФИО, роль, связанная запись справочника.
- Страница «Пользователи»: список учётных записей. При создании — необязательный выбор существующей записи справочника (поиск по фамилии среди записей без учётной записи) → `directoryUserId`.

Без этого заведующие и директора из файла должностей не смогут войти «самими собой» на этапе 6 (согласование).

## Часть B. Этап 3 — шаблоны

**Цель:** методист создаёт шаблон РПД для импортированного учебного плана, загружает DOCX-шаблон оформления, видит все закладки сопоставленными и публикует шаблон. Шаблон проходит жизненный цикл из шести состояний. Новая редакция опубликованного шаблона создаётся без потери прежней. То же — для ФОС.

### B1. Структуры типов документов — файлами

В ядре: `DocumentTypes/rpd.schema.json` и `fos.schema.json` — JSON Schema 2020-12 с x-расширениями, по `docs/design` с учётом правок по сверке. Подключить как встроенные ресурсы.

Реестр типов документов: тип → схема, сопоставление закладок по умолчанию (B2), лист согласования по умолчанию (B2).

Тесты:
- схемы корректны как JSON Schema 2020-12 — библиотекой с поддержкой 2020-12, например JsonSchema.Net (MIT); x-расширения допускаются;
- каждый `x-source` указывает на известный источник данных плана или справочников;
- каждый `x-validation-rule` — на имя из каталога правил. Сами правила реализуются на этапе 5, сейчас — только список имён.

### B2. Сопоставление закладок и лист согласования по умолчанию

Файлы рядом со схемами:
- `rpd.print-mapping.json`, `fos.print-mapping.json` — по каталогу закладок. Базовое имя закладки (без числового суффикса) → цель одного из видов:
  - `source` — данные плана и справочников (те же пути, что в `x-source`);
  - `field` — поле содержимого документа (JSON Pointer в схеме);
  - `signature` — место листа согласования: ФИО или должность;
  - `table` — именованный построитель таблицы: компетенции, трудоёмкость, разделы, практические занятия, лабораторные работы. Сами построители — этап 5;
  - `text` — стандартная формулировка с подстановкой.
- `rpd.signatures.json`, `fos.signatures.json` — места подписантов по реальным документам: роль, правило определения (только имя резолвера, выполнение — этап 6), участие в электронном согласовании, размещение (гриф «УТВЕРЖДАЮ» на титуле или лист согласования). Электронные места в прототипе — заведующий кафедрой дисциплины и начальник УМУ (граница прототипа: одна кафедра и методический отдел), остальные — бумажные.

Тесты:
- каждая закладка реальных шаблонов DWP и FOS имеет сопоставление;
- каждая цель существует: поле — в схеме, место — в листе согласования, построитель — в списке.

### B4. Модель шаблона и миграция

`document_templates`:
- `curriculum_plan_id` → `curriculum_plans` — шаблон создаётся для конкретной версии учебного плана;
- `schema`, `signatures_config` — jsonb, снимок из реестра типов в момент создания;
- `print_template_file_id` → `uploaded_files`, `print_mapping` — jsonb;
- `created_by` → `users`, `published_at`;
- **`revision`** (int) — редакция шаблона и **`lineage_id`** (uuid) — общий для всех редакций одного шаблона.

Отступление от проекта — записать в журнал: в проекте `version` означает редакцию шаблона, но в коде `Version` занята оптимистичной блокировкой. Поэтому редакция — отдельное поле `revision`. Редакции связываются `lineage_id`, а не через совпадение типа и названия, как в проекте: переименование не должно рвать связь.

### B5. Жизненный цикл в ядре

Правила переходов — в `TemplateTransitions`, с тестами:
- создание (тип, название, учебный план) → `empty`;
- загрузка DOCX-шаблона оформления → `draft`;
- «Сохранить» → `saved_draft`;
- публикация из `draft` или `saved_draft` при успешной проверке → `published`, ставится `published_at`. Публикация из `empty` запрещена — обновить правило и тест этапа 0;
- архивирование: `published` → `archived`;
- удаление (мягкое) из `empty`, `draft`, `saved_draft` → `deleted` — статус и `IsDeleted` вместе, одним методом;
- новая редакция опубликованного шаблона — новая запись: тот же `lineage_id`, `revision + 1`, копия схемы, сопоставления и листа согласования, ссылка на тот же файл оформления, статус `draft`. Прежняя остаётся `published` до публикации новой, а при публикации новой уходит в `archived`.

Проверка перед публикацией (FR-TPL-11, FR-TPL-13), ошибки — списком, ответ 422:
- учебный план привязан;
- DOCX-шаблон загружен;
- каждая закладка сопоставлена, и каждая цель существует;
- в листе согласования — только известные правила.

### B6. API — модуль `Templates`

- `GET /api/templates` — фильтры: тип, статус, план.
- `GET /api/templates/{id}` — вместе с результатом проверки перед публикацией.
- `POST /api/templates` — тип, название, план.
- `POST /api/templates/{id}/print-template` — multipart `.docx` → `uploaded_files`, чтение закладок, сопоставление по умолчанию из реестра → `print_mapping`.
- `POST /api/templates/{id}/save`, `/publish`, `/archive`, `/revisions` (новая редакция); `DELETE /api/templates/{id}`.

Все изменения — методист и администратор, с версией клиента (оптимистичная блокировка, 409). Прежний контракт создания из этапа 0 заменить новым, тесты обновить.

### B7. Клиент

- Страница «Шаблоны»: список с типом, планом, редакцией и статусом, фильтр.
- Страница шаблона:
  - создание: тип, название, выбор импортированного плана (направление, профиль, год набора, версия плана);

  - кнопки по статусу: «Сохранить», «Опубликовать» (с перечнем ошибок проверки), «Архивировать», «Новая редакция», «Удалить».

- Методист создаёт шаблон РПД для импортированного плана, загружает DWP-шаблон, видит все закладки сопоставленными и публикует. То же — для ФОС с FOS-шаблоном.

- Тесты зелёные, сборка без предупреждений.
